主数据管理模块 · 产品设计

文档编号：PRD-MDM-001 ｜ 版本：v0.1（评审稿）｜ 日期：2026-10-02

读者：业务负责人、车队长/运营人员、产品、设计、开发、测试

配套技术文档：MOD-MDM-001《主数据管理模块设计》（数据库、接口、工程结构见该文档）

一句话说明：本模块用来管理平台里最基础的四本"台账"——哪些单位、哪些车、哪些设备、哪些司机，以及"车装了哪台设备、谁在开"的对应关系。它不产生报警、不做监控，但监控、回放、预警、未来接入真实北斗设备，全都要以它为准。

一、为什么要做主数据管理

1.1 业务背景

平台当前可以演示车辆监控、轨迹回放和风险预警，但车辆、终端、司机数据是数据库里预置的 5 条示例，业务人员没有任何页面可以自己登记和维护。一旦投入真实使用，新购车辆、新装北斗终端、新入职司机、人员换班、设备换装、车辆报废等每天都在发生，没有台账管理功能，平台数据很快就会与实际情况脱节。

同时，系统规划下一步要接入真实的北斗车载终端（JT/T 808）。终端上报数据时只带"终端编号"，平台必须查"这台终端装在哪台车上、车牌是什么"，才能把轨迹挂到正确的车辆上——绑定关系是未来设备接入的前提。

1.2 现在的问题

问题具体表现导致的业务后果
台账没法维护车辆、终端、司机只能看不能改，新增一辆车必须找技术人员直接操作数据库业务无法自助开展，上线即停摆
没有单位概念车辆表预留了"所属单位"字段，但系统里没有单位台账，示例数据里的单位只是数字编号无法按公司/车队筛选车辆，未来"企业只能看自己的车"也无据可依
绑定关系不可管车装了哪台终端、当前谁在开，页面上查不到、也不能换绑设备换装、司机换班后，监控里车牌与司机会对不上
重复与错误无约束没有录入校验的话，同一台车可能被登记两次、一台终端可能同时绑两台车轨迹错乱、统计失真、责任无法追溯

1.3 做成后的价值

  • 业务自助：车队长/运营人员在页面上即可完成全部档案登记与变更，无需技术介入。
  • 数据可信：车牌、终端号、驾驶证号唯一性校验，绑定互斥规则保证"一车一机、人车对应"。
  • 全程留痕：谁在什么时候登记、修改、解绑都有记录；绑定历史可追溯，事故追责时能查到"事发时谁在开车、装的哪台设备"。
  • 为接入铺路：真实北斗终端接入后，上报数据可自动解析到正确车辆；按组织做数据隔离也有了组织基础。

五、组织架构管理

5.1 管理什么

维护运输企业及其下属车队/部门的树形结构，最多支持 5 级（例如：集团公司 → 区域分公司 → 运输车队 → 班组）。车辆登记时必须选择所属单位。

5.2 档案信息项

信息项说明是否必填
上级单位树中选择；顶级单位不选选填
单位名称同一上级下不可重名必填
单位类型运输企业 / 车队·部门必填
单位编码企业内部编码，启用后全平台唯一选填
联系人/联系电话单位日常对接人选填
所在地区/详细地址省、市、区 + 详细地址选填
排序号控制同级单位显示先后选填

5.3 业务规则

  • 单位下还有未删除的下级单位或有效车辆时，不允许删除，系统会明确提示原因（如"该单位下还有 3 台有效车辆"）。
  • 删除采用"停用/失效"方式，历史数据和统计中仍然保留该单位名称，保证可追溯。

六、车辆档案管理

6.1 档案信息项

信息项说明是否必填
车牌号与车牌颜色组合后全平台唯一，如"京A12345+蓝色"必填
车牌颜色蓝/黄/绿/白/黑（新能源货车多为绿色）必填
所属单位从组织树选择选填
车辆类型重型货车、中型货车、轻型货车、冷链车等选填
运营类型货运 / 客运 / 危化品 / 其他（危化品车辆后续适用更严的风控规则）选填
车身颜色、品牌辅助辨识选填
VIN 车架号17 位，录入时做格式校验选填
道路运输证号营运资质信息选填
所属行业如普货、冷链、渣土等选填
车主名称/联系电话登记车主信息；电话做格式校验选填
所在地区、备注补充说明选填

6.2 可以做什么

  1. 查：按车牌号/VIN 关键字、所属单位（含其下级）、车牌颜色、运营类型组合筛选，分页浏览。
  2. 看详情：一辆车的完整档案 + 当前安装的终端 + 当前主/副班司机，一页看清。
  3. 增/改：登记表单分组填写，必填与格式不合格当场提示。
  4. 删（停用）：车上还装着终端或还有在班司机时禁止删除，必须先解绑；防止误删导致轨迹成"无主数据"。

七、终端档案管理

7.1 档案信息项

信息项说明是否必填
终端编号设备出厂/入网唯一身份，真实终端上报数据即以此识别，全平台唯一必填
设备厂商、型号如 GT06N；用于设备质量追踪选填
设备 MAC 地址硬件标识选填
SIM 卡号/账号设备流量卡信息，欠费排查时使用选填
通信协议JT808 / JT1078 / 其他选填
设备类型一体机 / 分体机 / 视频智能终端选填
视频通道数0 表示纯定位设备； DSM/ADAS 设备通常 2~4 路选填
设备状态正常 / 维修停用 / 报废必填
备注如返修记录选填

7.2 业务规则

  • 终端编号不可重复登记。
  • 只有"正常"状态的终端才能被绑定到车辆；维修停用、报废状态不可绑定。
  • 终端已装车时不允许停用或删除，需先从车上解绑。

八、驾驶员档案管理

8.1 档案信息项

信息项说明是否必填
姓名司机真实姓名必填
驾驶证号全平台唯一，是司机的业务身份必填
性别男/女选填
联系电话坐席干预、应急联系使用；格式校验选填
准驾车型如 A2、B2、C1，应与所驾车型匹配（本期提示不强制）选填
身份证号、司机照片本期支持身份证号文本录入；照片仅登记地址，上传功能后续随文件服务建设选填
在职状态在岗 / 离岗 / 停用必填
备注如安全培训记录选填

8.2 业务规则

  • 驾驶证号不可重复登记。
  • 只有"在岗"司机可以被绑定到车辆。
  • 司机仍在某台车上当班时不可停用/删除，需先解绑。

九、绑定关系管理（本模块的核心）

档案回答"有什么"，绑定关系回答"现在是谁和谁在一起"。平台所有实时数据都依赖绑定关系才能挂到正确的业务对象上。

9.1 两类绑定关系的业务口径

关系数量口径业务含义
车 ↔ 终端严格一对一一台车同一时刻只装一台终端，一台终端同一时刻只能装在一台车上；换装时"先卸旧机、再装新机"。
车 → 主班司机一车一名主班车辆的第一责任人，风险统计、考核默认归属主班。
车 → 副班司机一车可多名副班双驾长途等场景的轮换司机。
司机 → 车一人同时只在一台车上无论主班副班，一名司机同一时刻只能有一条有效绑定，换车前先解绑。

9.2 绑定时需要记录的信息

  • 车-终端：绑定类型（正式安装/临时换装）、安装时间、安装人、备注；解绑时记录解绑时间与备注。
  • 车-司机：司机角色（主班/副班）、绑定时间、备注；解绑时记录解绑时间。

9.3 系统会自动拦截的错误操作

操作场景系统反应
把已装在 B 车上的终端绑给 A 车拦截并提示"该终端已绑定车辆 京Bxxxx，请先解绑"
给已有终端的车再装一台终端提示先解绑旧终端；也可直接使用"换绑"，系统自动一步完成旧机解绑+新机绑定
给一台车安排第二名主班司机拦截，提示一车仅一名主班（可先把原主班改为解绑或设为副班）
把已在别的车上当班的司机绑到本车拦截，提示该司机当前绑定车辆
绑定"维修/报废"终端或"离岗"司机拦截，提示对象状态不可绑定
两人同时操作同一台车的绑定系统保证最终只生效一条，不会出现一车两机

9.4 历史记录怎么保留

只追加、不抹除：解绑不会删除旧关系，而是在记录上写明解绑时间。车辆详情页以"时间线"展示全部历史——例如可查到 2026 年 3 月前装的是旧终端、3 月换装新终端；某事故时段的当班司机是谁。重新绑定会生成一条新记录，旧记录不可"复活"。

十、四个典型业务流程

流程一：新车入网

登记车辆
填写车牌、车型、所属单位等信息
登记终端
若设备未入库，先建终端档案
车装终端
车辆详情页绑定终端，记录安装人与时间
安排司机
绑定主班司机（必要时加副班）
上线可见
设备开始上报后，监控页出现该车

流程二：终端故障换装

故障登记
旧终端状态改为"维修停用"
执行换绑
车辆详情页选择备用终端做"换绑"，系统自动解绑旧机、绑定新机
数据不断档
新终端上报即挂到同一车牌，历史轨迹仍可按时间回放

流程三：司机换班/换车

解绑原司机
在原车辆上解绑（记录解绑时间）
绑定新司机
绑定到新车辆并指定主班/副班
责任清晰
报警与风险按事发时间的当班司机归属

流程四：车辆报废退出

解绑终端
拆除设备，终端可回收再利用
解绑司机
司机转为可派往其他车辆
停用车辆
车辆档案失效，不再出现在监控与新增业务中，历史记录保留

十一、业务规则汇总

类别规则不满足时的提示口径
唯一性车牌号+车牌颜色唯一；终端编号唯一；驾驶证号唯一；同级单位名称不重复提示具体重复对象
录入校验必填项完整；手机号、VIN、驾驶证号格式合法在对应字段下方提示
绑定互斥一车一终端、一终端一车；一车一主班；一司机同时一台车提示冲突对象当前归属
状态前置只能绑定"正常"终端与"在岗"司机；有有效绑定的档案不可停用/删除提示先完成解绑
组织删除存在下级单位或有效车辆时不可删除提示占用数量
留痕所有登记/修改/绑定/解绑自动记录操作人与时间；解绑历史永久保留—（系统自动）
删除方式全部为失效式"软删除"，不提供物理删除入口—（系统自动）

十四、本期做与不做

范围内容
本期做组织树、车辆/终端/司机三本档案的单条增删改查、状态管理、绑定/换绑/解绑与历史、业务规则校验、操作留痕
本期不做Excel 批量导入导出（档案量小时单条维护即可，后续按需补）
本期不做司机照片/证件附件上传（依赖文件存储服务，后续随系统配置模块建设）
本期不做用户账号、角色、菜单权限的真实拦截（仅预留权限标识，随 IAM 权限模块落地）
本期不做按单位强制数据隔离（组织树与筛选先就位，隔离规则随权限模块启用）
不改动现有监控、回放、风险预警、模拟器、样例导入等已上线功能保持不变

十五、业务验收标准

上线后由业务人员按以下口径逐条验收（全部通过方可交付）：

  1. 能新建"公司→车队"两级单位，并能在车辆登记时选到；单位下有车时删除会被拒绝并看到原因。
  2. 能完成一辆新车从登记车辆、登记/绑定终端、绑定主班司机到在监控相关列表中可查的全过程。
  3. 同一车牌+颜色、同一终端编号、同一驾驶证号重复登记时均被拒绝。
  4. 一台终端绑给第二辆车、一辆车安排两名主班、一名司机同时绑两台车，均被拦截且提示清晰。
  5. "换绑"操作一步完成：旧关系带解绑时间、新关系生效，全程不出现一车两机。
  6. 车辆详情能看清当前终端、在班司机和完整绑定历史时间线。
  7. 有绑定关系的车辆/终端/司机不能直接删除，解绑后可以停用；停用后历史轨迹与风险记录仍可查。
  8. 每条新增/修改/绑定记录都能查到操作人与操作时间。
  9. 原有监控、轨迹回放、风险预警、模拟器演示流程不受任何影响。

十六、待业务方确认的事项

#待确认问题产品侧建议默认值

4准驾车型与车辆类型不符时是"强拦截"还是"仅提示"？本期仅提示，运营成熟后再改为强校验
5档案删除是否需要审批流？本期不需要，二次确认 + 软删除留痕即可；审批随权限体系建设
6本期是否需要 Excel 批量导入（初次建档车辆较多时常用）？默认不做，可按实际建档量评审是否提前
