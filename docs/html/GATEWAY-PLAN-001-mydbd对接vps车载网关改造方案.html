GATEWAY-PLAN-001
mydbd 对接 vps 车载网关改造方案

编号：GATEWAY-PLAN-001 ｜ 日期：2026-10-05 ｜ 状态：待审批（审批通过前不改动业务代码）
依据：对本仓库实际代码的逐模块盘点 + GATEWAY-REF-001（网关协议分析）+ GATEWAY-CMP-001（对接对比决策稿）

0. 结论摘要

一句话结论

mydbd 现有的轨迹、监控、报警、工单、推送体系已具备承接真实网关数据的骨架，对接不是另起炉灶，而是"加一条 Kafka 数据面通道 + 补齐网关特有的标识/字典/附件/指令四类缺口"。一期数据面可做到现有页面零新增即可看真车、真报警；二期再点亮前端已预留的视频/拍照按钮。

  • 能直接复用：轨迹点表与轨迹回放、Web 实时推送、车辆面板、风险事件/工单/SLA、CEP 引擎、组织数据权限框架——网关数据按相同口径落库即自动生效。
  • 必须改造：① 新增 Kafka 消费通道（processing 服务，现无任何 MQ 依赖）；② 终端双标识（手机号 + 网关 truckId）与未登记车辆隔离；③ 报警类型字典从 5 类扩到网关 29 类，否则报警中心显示"类型 101001"；④ 报警附件落库与平台鉴权查看；⑤ 在线状态口径（现 3 处独立"最近 5 分钟有点"判定，无在线态字段）。
  • 二期建设：Java 侧新增指令面模块对接网关 18001（视频/回放/拍照），前端激活已预留的三个按钮并引入 flv.js。
  • 关键外部依赖：网关主动拍照无"拍照完成"事件出口，需对方配合（影响二期拍照体验，不影响一期）。

1. 背景、目标与范围

1.1 业务背景

mydbd 当前定位/报警数据来自模拟器与 HTTP 推送（processing-service/app/services/simulator.py、POST /api/ingest/traj），用于演示与算法验证。现场已部署 vps 车载网关，承担真实 JT/T 808 终端接入：实时定位、苏标主动安全报警（ADAS/DSM/盲区/激烈驾驶）、报警图片音视频、终端上下线、远程视频/拍照/TTS 指令。

本次目标：让 mydbd 从"演示系统"变为"真实在网车辆监控平台"，同时不重做已有的组织权限、工单、通知、大屏、评分能力。

1.2 产品目标与验收指标

产品目标验收指标
真实车辆实时可见网关在网车辆位置 ≤5s 上屏；在线/离线准确，离线感知 ≤60s；现有大屏、监控页、回放页直接呈现
主动安全报警可用ADAS/DSM 等 29 类报警自动进入报警中心与风险事件并自动建工单；开始/结束闭环可追踪；类型名/级别正确
报警有证据报警详情可查看关联图片/音视频，经平台鉴权，按归属组织隔离，不暴露网关裸地址
不重做、不影响现网总开关关闭时现有功能 100% 保持；权限仍锚定车辆归属组织，不新增按车牌省份过滤路径
可规模验证500 车 × 0.2Hz 定位持续 30 分钟，消费滞后 <5s、无死信积压

1.3 范围分三期

  • P0 一期 数据面：真实定位、在线/离线、车辆对照与未登记隔离、接入状态运维。
  • P1 一期 报警面：29 类报警映射与开闭环、工单去重、报警附件转存与鉴权查看。
  • P2 二期 指令面：实时视频/历史回放/对讲、远程拍照。
  • P3 三期 增强：TTS 语音下发联动通知、原始报文留存、接入监控告警。

2.2 与对接直接相关的 6 个代码级事实

  1. 报警类型字典只有 5 类：base_warn_type 种子仅 1 超速 / 2 疲劳 / 3 围栏越界 / 4 紧急求助 / 5 设备故障。报警中心列表、滚动、统计、下拉的 SQL 全部 JOIN 此表。网关 typeId=101001…105007 无对应行，页面会退化为"类型 101001"，等级也无法显示。
  2. 在线判定没有状态字段，且散落在 3 处：DashboardMapper.selectOnline（max(gps_time) 窗口）、WarnInfoMapper.countActiveVehicles（EXISTS 有点）、VehiclePanelService（常量 5 分钟）。网关离线事件只携带 truckId，现有口径无法感知"网关侧已离线但残留旧点"的状态。
  3. 终端标识现以 identity_code 为唯一键（uk_traj_terminal_identity），另有 sim_account 列存手机号；无网关 truckId 列。
  4. 轨迹点 alarm_flag 是 smallint：网关 alarmFlag 为 32 位位图 Long，存不下；速度表列为 integer km/h、里程 numeric km，与网关 m/h、米口径不同，必须换算。
  5. 附件体系基本空白：traj_gps_photo 表已预留但无任何写入入口与接口；risk_event.media_url 为单值 varchar(255)；前端没有图片/视频查看组件（无 flv.js 依赖）。
  6. 网关无应用鉴权的端口有 3 个：18001 指令、18009 静态附件、20780-82 ws-flv。前端工单详情当前直接打开裸链的做法不能沿用到网关地址。

3.3 功能详述

F1 真实车辆实时定位 P0

  • 用户故事：监控员打开现有监控页/大屏，真实在网车辆按实际上报位置显示，点击可见速度、方向、定位时间；回放页可回放真实历史轨迹。
  • 业务规则：消费 jt808_gps_topic 自动入库；速度 m/h÷100→km/h、里程米÷1000→km；坐标保留 WGS-84，出图沿用现有高德转换；补报数据（delay）入库可区分、不顶替最新点；同终端同 trackId 幂等；(0,0)/越界点丢弃计异常。
  • 入口：零新页面——大屏、实时监控、轨迹回放、车辆面板、WS 推送在数据落库后自动呈现真实数据。

F2 终端在线/离线状态 P0

  • 用户故事：在线/离线一目了然，离线车辆显示最近离线时间，在线率统计真实可信。
  • 业务规则：0102 鉴权/0002 心跳→在线；jt808_offline_topic（仅 truckId）→离线；在线态写终端档案；三处读取口径统一切换为"在线态列优先、最近点兜底"；网关只发离线不发上线，以 0102 近似上线。

F3 车辆对照与未登记隔离 P0

  • 用户故事：有车在跑却看不到时，运维在"未登记终端"清单找到它，补建档案/绑定后数据自动归位。
  • 业务规则：网关标识分层（协议/会话层=终端手机号，业务层=truckId，Kafka key=truckId，离线事件仅 truckId）；平台双锚点——手机号两级解析（identity_code，其次 sim_account）+ 回填 gateway_truck_id，离线事件按 truckId 反查；查不到的消息不入库不丢弃，进隔离区（手机号/truckId/车牌/最近出现/次数）；"终端手机号是否等于 SIM 卡号"列为联调首验项。

F4 主动安全报警闭环 P1 · 核心

  • 用户故事：疲劳、接打电话、前向碰撞等发生时，报警中心出现类型正确、级别正确的报警，同时风险事件自动建工单，监控员确认/解除并闭环。
  • 业务规则：消费 jt808_warn_topic，覆盖 ADAS 10 类、DSM 9 类、盲区 3 类、激烈驾驶 7 类；经网关字典映射为平台事件码（101001→ADAS_FCW、102001→DSM_FATIGUE 等）；苏标级别 1高/2低 反转为平台 3高/2中；开始标志建 risk_event+工单（复用现有自动建工单链路），结束标志回填、不重复建单；网关事件固定来源标识，绕过 CEP 二次判定，防重复告警/计分；沿用现有双写形态，同时写 traj_warn_info（报警中心）与 risk_event（风险/工单）。

F5 报警证据附件查看 P1

  • 用户故事：打开报警/工单详情，直接看到终端抓拍的图片/音视频作为处置证据。
  • 业务规则：消费 jt808_warn_media_topic，仅 fileStatus=完成 转存平台数据卷；按 warnId 与报警关联、支持多附件；平台提供鉴权取图接口并校验归属，不下发光关裸地址；工单详情现有裸链组件同步改为鉴权地址。

F6 实时视频 / 历史回放 / 对讲 P2

  • 用户故事：监控页车辆弹窗点"实时视频"即看、可回放、可对讲；操作全部留痕。前端三个预留按钮本就是为此设计。
  • 业务规则：Java 平台经网关 18001 下发（9101/9102 等），视频流经 nginx 反代收敛；flv.js 播放，H265 依赖网关私有增强需实测；接口走 JWT + 权限码 + 归属校验 + 审计。

F7 远程拍照 P2

  • 用户故事：点"立即拍照"，照片回传并在平台查看。
  • 缺口：网关有 cameraShot 指令，但无拍照完成 Kafka 事件。首选推动网关补事件；过渡期用 gpsType=11 图片点关联，功能标"受限"。

F8 TTS 语音下发 P3

复用 NotifyChannel 扩展点新增 JT808_TTS 渠道，经网关 /tts 向终端语音喊话（如疲劳干预）；终端离线回执失败并记录。

F9 网关接入状态（运维） P0

服务令牌保护的只读状态：开关、各 topic 最近处理时间/处理数/失败数、消费积压、死信条数、未登记终端入口。配合一个系统管理菜单页。

F10 原始报文留存 P3 · 可选

订阅 jt808_raw_hex_topic 落冷存储，供事后排障与协议审计。

3.4 明确不做

  • 不自建 JT/T 808/1078 协议栈、不直连车载终端；只对接 vps 网关。
  • 不改变数据权限模型（不按车牌省份建过滤路径）。
  • 不改造模拟器/HTTP 入口与既有页面操作习惯；新增事件码一律先登记字典。
  • 一期不做视频/拍照/TTS。

5. 技术方案

5.1 目标架构与原则

                         ┌──────────────────────────── mydbd ────────────────────────────┐

  gps/warn/warn_media/    │   consumer(长轮询守护线程) → mappers(单位/码表/级别换算)        │
  heartbeat/offline/      │     → 复用 db.insert_gps_points / cep_engine.evaluate_points   │
  command(0102上线)        │     → 新增写：报警开闭环 / 终端在线态 / 附件 / 死信            │

 vps 18001 REST ◀─────────│ platform-app: module-gateway（二期新增）                       │

                          └────────────────────────────────────────────────────────────────┘

原则：① 开关驱动，不配 Kafka 全功能行为不变；② 数据面（Python，复用入库/CEP/工单）与指令面（Java，复用鉴权/权限/审计）分离；③ 权限锚点保持车辆归属组织；④ 幂等（trackId/warnId）+ 手动位点 + 毒消息死信不阻塞；⑤ 不重复建设协议栈。

部署形态：数据面消费者内置于 processing 同进程守护线程（复用已验证入库契约，避免新增容器；384M 内存下用纯 Python 客户端、批量插入、有界流式下载），子包不依赖 FastAPI，未来可平移独立服务。

5.3 数据库改造（新增 18 号迁移脚本，幂等可重复执行）

  • traj_gps_point：alarm_flag→bigint；新增 ext jsonb（trackId/gpsType/delay/status/recordSpeed/additions 等原始字段）；部分唯一索引 (identity_code, ext->>'trackId') 幂等。
  • traj_terminal：gateway_truck_id、online_status、last_heartbeat_time、last_online_time、last_offline_time。
  • traj_gps_photo：warn_id、media_type、file_status、source（gpsType=11 图片点复用）。
  • 新表：traj_warn_media（报警附件，warn_id+file_name 唯一）、gateway_event_map（29 类映射种子）、gateway_dlq（死信）、gateway_ingest_stat（消费统计）、gateway_unknown_terminal（未登记隔离）。
  • mon.risk_event 增 source_id（warnId 去重锚点）+ 部分唯一索引，防重复建单。
  • base_warn_type 补 29 类种子（id=网关 typeId，grade_level 用平台口径），使报警中心现有 JOIN 直接生效；事件码映射同时落 gateway_event_map 供消费者使用。

5.4 数据面改造（processing-service，P0/P1 主体）

  • 依赖：kafka-python>=2.0（纯 Python，适配 slim 镜像与 384M 限制；消费逻辑接口隔离，可替换客户端）。

9. 待审批决策

  1. Kafka 部署：直连网关既有集群+独立消费组只读 ACL（推荐）／平台自建 broker 要求网关改投递。
  2. 终端标识口径：双锚点——新终端以手机号为 identity_code、存量经 sim_account 两级解析，并回填 gateway_truck_id（推荐）／保留 TERM_xxx 仅反查。
  3. 附件存储：首期转存 mydbd-data 卷、平台鉴权接口提供（推荐）／仅反代 18009／上 MinIO。
  4. 主动拍照出口：协调网关补拍照完成事件（推荐）／接受过渡关联并标受限。
  5. 实施范围：先做 P0+P1 数据面闭环（推荐）／P0–P2 连续推进。
  6. Kafka 客户端：纯 Python kafka-python（推荐）／confluent-kafka（需系统依赖）。
  7. 报警字典承载方式：base_warn_type 直接扩 29 类（推荐，现有 JOIN 零改动）／单独维护网关字典并改 5 处 SQL。
