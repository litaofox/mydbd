处置工单流转（F20）
风险事件"待处理 → 处理中 → 已闭环"全流程闭环 · 分派 · 时限 · 超时升级

文档编号：PRD-RISK-002　|　所属功能：F20（第一波）　|　版本：v1.0　|　日期：2026-10-02　|　状态：已上线

上游依赖：F18 风控规则引擎（CEP）产生风险事件　|　下游预留：F19 多渠道通知、F21 坐席干预记录、F14 WebSocket 秒级推送

1. 背景与目标

F18 上线后平台可持续产生分级风险事件，但当前事件只有 未处置 / 已处置 一个布尔标记和一条处置意见，"谁在处理、处理到哪一步、有没有超时、超时谁来兜底"全部不可见，无法满足企业对安全运营闭环的考核要求。

F20 在不改变 F18 事件产生链路的前提下，为每一条风险事件挂载一张处置工单，实现：

  • 状态可管：待处理 → 处理中 → 已闭环，状态流转全程留痕；
  • 责任到人：支持主管分派、坐席认领、转派，工单始终有唯一负责人；
  • 时限可控：按风险等级配置处置时限（SLA），临期/超时实时可见；
  • 超时可升级：超时未闭环自动标记升级，进入安全主管督办队列；
  • 闭环可溯：闭环必须选择处置结果并填写说明，形成可审计的运营档案（F21 干预动作、F23 画像统计的数据基础）。

本期范围：工单模型、状态机、分派/认领/转派/闭环、SLA 时限与超时升级、工单列表与详情、与风险事件页打通。不包含：短信/语音/App 外发通知（F19）、WebSocket 实时弹窗（F14，上线后工单列表自动受益于推送）、干预动作细分统计（F21）。

2. 角色与职责

3. 工单生成与来源

  • 自动生成：F18 CEP 引擎每落一条 mon.risk_event，在同一事务内自动创建一张工单（状态=待处理），并按事件风险等级套用 SLA 计算应闭环时限（deadline）。事件与工单 1:1。
  • 历史补齐：上线迁移时，对存量 handle_status=0（未处置） 的事件批量补建待处理工单；已处置历史事件不补单（保留原处置意见，视为历史数据）。
  • 懒补建：任何入口（如老版本事件页）发现事件无工单且未处置时，可触发补建，保证"无死角"。

工单是事件的运营视图，事件标题、车牌、等级等关键信息在工单上做快照；事件被清理（本期不做事件物理删除）不影响工单档案的完整性。

4. 状态机与操作

待处理 PENDING
新建/分派/退回后的初始态。可被认领或被主管分派；显示 SLA 倒计时。
处理中 PROCESSING
坐席认领或主管分派后进入。可转派（负责人变更，状态不变）、闭环。
已闭环 CLOSED
终态。必须选择处置结果 + 填写说明；回写事件"已处置"。不可再编辑。
操作起始状态结束状态权限必填/规则
认领待处理（未指派人）处理中risk:order:handle负责人=当前用户；记录认领时间
分派待处理 / 处理中处理中risk:order:assign从"有处置权限的启用用户"中选择；可填分派备注
转派处理中处理中risk:order:handle选择新负责人 + 转派原因；原负责人、转派链路全部留痕
开始处理待处理（已被分派但尚未接单）处理中负责人本人 risk:order:handle记录接单时间；分派后未"开始"也允许直接闭环（接单与闭环合并）
闭环待处理 / 处理中已闭环risk:order:handle必选处置结果、必填闭环说明；同步事件 handle_status=1

每次状态/负责人变化写一条 工单流转日志（动作、前后状态、前后负责人、操作人、备注、时间），详情页按时间线展示。闭环工单的日志与快照长期保留（F34 审计之外的业务级轨迹）。

5. 处置时限与超时升级

按风险等级配置 SLA（安全管理员可在工单页"SLA 配置"入口维护，变更只影响此后新建工单）：

风险等级默认处置时限升级宽限期业务含义
高风险15 分钟超时后 +10 分钟疲劳、严重超速、FCW 等高风险，必须立即干预
中风险60 分钟超时后 +30 分钟当班内完成处置
低风险240 分钟超时后 +60 分钟当日内完成处置
  • 剩余时限：列表显示倒计时（如 剩余 08:32）；剩余 ≤ 20% 时限变橙色提醒（临期）。
  • 超时 overdue：当前时间 > deadline 且未闭环 → 红色"已超时"，统计条与筛选均可定位。
  • 升级 escalated：超过 deadline + 宽限期仍未闭环 → 自动置"已升级"标记：
    1. 列表置顶进入安全主管的督办队列（默认筛选"已升级"）；
    2. 工单出现醒目标记，主管可直接改派/督办并留言；
    3. 预留 F19 通知钩子（本期只落数据与页面标记，不发短信）。
  • 由平台定时任务每分钟扫描一次（兜底），列表/详情打开时也实时计算，避免等扫描。

6. 闭环与留痕

闭环时必须选择处置结果（单选，用于后续 F21/F23 统计）：

结果码名称说明
PHONE_REMIND电话提醒已电话联系驾驶员/企业提醒纠正
EDUCATION安全教育约谈、教育培训、书面警示
SUSPEND停运整改车辆/驾驶员停运整改
FALSE_ALARM误报排除经核实为设备误报/数据异常，不做处置
OTHER其他其他处置方式（必须在说明中写明）
  • 闭环说明必填，10~255 字（防止"已处理"式无效闭环）；
  • 闭环即终态，不提供"反闭环"；若闭环有误，由安全管理员走审计可追溯的重新打开（权限 risk:order:assign，二次确认并强制填写原因，日志保留 REOPEN 记录）；
  • 闭环同时回写风险事件：handle_status=1、handle_remark=结果名 + 闭环说明，保持事件页与工单页口径一致。

7.3 风险预警分析页（F18 页面改造）

  • 未处置事件的操作由"处置"改为"去处理"：点击后确保工单存在（无则补建）并直接打开该工单详情抽屉；
  • 已处置事件显示闭环结果 tag（电话提醒/误报排除等），悬浮显示闭环说明；
  • 事件页仍保留只读，处置动作统一收归工单，避免两个入口口径不一致。

三个等级各自维护"处置时限（分钟）/升级宽限（分钟）"，保存审计留痕；修改后列表顶部短暂提示"仅对新工单生效"。

9. 业务规则与边界

  1. 事件与工单严格 1:1：唯一索引 uk_order_event(event_id)；并发补建靠唯一约束兜底，不报用户错误。
  2. 状态扭转非法操作返回业务错误（如闭环后再闭环：40901 工单已闭环）。
  3. 不能分派给停用/无处置权限的用户；分派下拉只列有效用户。
  4. SLA 只存分钟正整数（时限 1~10080，宽限 0~1440）；修改只影响新单。
  5. 超时/升级是可重算状态：以 deadline 实时计算为准，定时任务只做升级标记与督办排序所需物化字段；误调服务器时间后下一轮扫描自动纠正。
  6. 历史已处置事件无工单：详情不展示工单入口，仅显示原 handle_remark。
  7. 工单不做物理删除；事件被规则引擎持续写入，工单创建失败不得影响事件入库（事件入库为主事务，工单为同事务内动作——若工单写入异常则整体回滚并由引擎旁路捕获记录错误日志，事件不丢的设计见 MOD 说明）。

10. 验收标准

  1. CEP 新产生的每条事件在 1 秒内可在工单列表看到对应"待处理"工单，deadline 按等级正确（高 15/中 60/低 240 分钟）。
  2. 坐席认领 → 处理中；主管分派给指定坐席，负责人与流转日志正确；转派链路完整可查。
  3. 闭环必须选结果+≥10 字说明，否则前端拦截、后端 40001；闭环后事件页状态同步为已处置且显示结果。
  4. 构造过期工单：超时显示红色倒计时为负；超过宽限期自动出现"已升级"并进入主管督办视图。
  5. 统计条数字与库内一致；平均闭环时长按当日已闭环单计算。
  6. 安全管理员可改 SLA，改后新建工单 deadline 立即按新值；旧单不变。
  7. 重新打开仅 SAFE_ADMIN 可用，强制填原因，日志含 REOPEN；重开后可再次闭环。
  8. DISPATCHER 无 SLA 配置/重开入口；无 risk:order:view 的角色（如纯 MDM 角色）菜单不可见、直访被路由守卫拦截、直调 API 40301。
  9. 存量未处置事件迁移后均有工单；已处置历史事件不产生工单。
  10. 全部分派/闭环/重开/SLA 操作在审计日志可检索。
