MOD-DBD-014 终端通信网关（规划）

编号：MOD-DBD-014｜版本：v1.3.0｜日期：2026-10-06｜ 状态：部分具备（P0 数据面 + P1 报警附件一期已上线）｜覆盖功能项：F01～F07｜ 代码锚点：processing-service/app/gateway/（consumer、mock_producer、terminal_resolver、mappers、media_store、runner）、app/routes/gateway.py；module-monitor 的 controller/GatewayStatusController.java、controller/MediaController.java、gateway/ProcessingClient.java；frontend/src/views/system/GatewayStatus.vue
产品篇

1. 模块定位与范围

终端通信网关是平台与车载终端之间的设备接入面：对上承接北斗/GNSS 车载终端（部标机、ADAS/DSM 智能终端、油耗/温控传感器）的长连接与报文，对下向平台轨迹、风控、监控、视频、报表各模块输出标准化的位置、报警、媒体、车况数据流，并承担平台到终端的指令下行通道。

本模块覆盖功能项 F01～F07，2026-10-05 时点均未实现，当时仅有服务令牌 HTTP 批量点接入与进程内数据模拟器。2026-10-06 按 GATEWAY-PLAN-001 完成"对接 vps 网关"近期路径的一期实施（P0+P1），当前功能项状态：F01 部分具备（外部网关 Kafka 数据面已接入，自建 Netty 仍为终态蓝图）、F02 部分具备（在线态字段/上线下线事件/三处读路径已切换，离线判定为网关显式事件口径而非本地 3 周期超时）、F07 部分具备（29 类报警抓拍图接收与鉴权查看已上线，1078 片段按需调阅未建）、F03/F04/F05/F06 待建设。一期实施细节、性能验证与遗留事项见 GATEWAY-PLAN-001 第 10 章 一期实施记录。本文产品与技术方案仍按终态口径描述，作为后续 P2/P3 建设依据。

一期已上线（2026-10-06，mock 500 车全链路验证通过）：Kafka 数据面消费（GATEWAY_MODE 三模式 simulator/mock/gateway）、双标识解析与未登记终端隔离区、29 类报警映射建单、报警附件转存与 JWT 鉴权查看、在线状态三处读路径收口、运行模式页（菜单 925，/system/gateway，上线时名「网关接入状态」）、死信队列与分 topic 运行统计。实测吞吐约 184 msg/s、lag 连续 3 分钟为 0、0 死信。

二轮增强（2026-10-06，测试模式治理）：测试模式（mock）报警改为 60 秒窗口令牌桶全局限频 ≤2 起/分钟（风险事件、工单、通知同源联动自然受限），GPS 报警位置清零；仿真投递支持运行时启停（/api/simulator/mock/start|stop|status，开关经 sys_config 键 gateway.mock-delivery-enabled 持久化，重启后保持）；运行模式页新增「清除模拟数据」按钮（/api/ingest/dataset/clear-runtime，清空运行数据含通知痕迹，保留基础数据）；菜单 925 由「网关接入状态」更名为「运行模式」。

三轮修复（2026-10-06，JWT 算法契约对齐）：修复打开本页（运行模式）即被踢回登录页的问题：页面挂载会让浏览器直接带 JWT 调 processing 的 /api/simulator/status、/api/simulator/mock/status、/api/ingest/dataset/status；Java 签发在 50 字节密钥下被 JJWT 自选为 HS384，而 processing 仅放行 HS256 致 401。已将 Java 签发显式钉死 HS256、processing 验签放宽为 HS256/HS384/HS512（兼容存量令牌、无需重登）。详见 方案存档 与 DEP-DBD-001 FAQ Q15。

2. 术语与协议

术语 / 标准号含义
JT/T 808-2019《道路运输车辆卫星定位系统 终端通讯协议及数据格式》。车载终端与平台之间的主通信协议，TCP 长连接，0x7E 分帧、转义、XOR 校验、消息分包。

JT/T 1076/1077-2016车载视频终端 / 平台技术要求；终端选型与平台侧能力对齐时参考。

vps 网关现有外部车载网关系统（jt808-service、jt808-file、vps-video 三进程），已实现 808/1078 编解码并以 Kafka topic 输出；本模块近期对接其数据面，远期以自建网关为终态。
GATEWAY_MODE规划中的接入模式配置：simulator（现有模拟器）/ mock（网关仿真）/ gateway（真实网关）。详见第 10 节。

3. 业务场景

调度员 · 实时监控
车辆上线与位置实时可见
车辆点火、终端注册鉴权后 90 秒内进入在线态；监控页在线数、最后上点时间准确；离线后 3 个心跳周期内在离线报表中体现。
安全管理员 · 主动安全
DSM/ADAS 报警带图到达
疲劳驾驶、接打手机、抽烟、前向碰撞、车道偏离事件随定位上报，附带 1～3 张带水印抓拍图，可直接在风险事件详情查看。
调度员 · 应急处置
对单车下发文本/监听/拍照指令
平台选车下发参数设置或终端控制，界面展示"已下发→终端应答→执行结果"全状态，失败可重试并留痕。
事故调查 · 视频调阅
实时视频与历史片段调阅
经审批后在浏览器直接播放实时视频（H5 无插件），按需拉取报警前后约 10 秒片段，不落地存储全量视频。
车辆进入信号盲区
补传点不污染实时链路
终端本地缓存至少 72 小时位置数据，恢复连接后批量补传；平台按原始定位时间入库并打补发标记，与实时点分区处理，里程统计可回溯修正。
运营分析 · 成本管理
油耗与怠速分析有车况数据支撑
CAN/OBD 的转速、油量、ACC 信号接入后，怠速、加油、油耗报表（F45/F49/F50）才具备真实数据来源。
运维 · 大流量场站
回场 Wi-Fi 批量上传附件
图片/短视频走场站 Wi-Fi 批量续传，断点可恢复，节省蜂窝流量；缺片自动补传。
开发/测试 · 无设备联调
仿真模式切换
通过 GATEWAY_MODE 在模拟器、网关仿真、真实网关三模式间配置切换，开发联调与压测不依赖真车。

4. 目标业务流程

4.1 终端上线主流程（808）

TCP 建链与注册 0x0100
终端上电后建立 TCP 连接，发注册消息（终端手机号、省/市/厂商/型号/终端 ID、车牌颜色、车牌）；网关查白名单（对标 vps_base_truck）后经 0x8100 返回注册结果与鉴权码。
鉴权 0x0102
终端以鉴权码（规划口径：鉴权码=终端手机号，与 vps 现状一致）发鉴权，网关校验通过后连接置为"已鉴权"，双标识映射落缓存。
心跳 0x0002 / 应答 0x8001
终端每 30 秒发心跳，网关回通用应答并刷新最后心跳时间；连续 3 个周期未收到心跳判定离线。
定位上报 0x0200
位置基本信息 + 报警标志/状态/苏标附加项；网关解析、口径换算、双标识换车辆 ID 后送 Kafka 数据面。
下游入库与业务
消费端写 traj_gps_point、旁路推 CEP 引擎、刷新在线状态；报警进入 mon.risk_event 并联动工单。

4.2 指令下行流程

平台发起
运营在前端点"拍照/监听/文本播报/参数设置"，后端生成指令记录（待下发）。
指令编码下发
按终端所在连接路由，0x8103/0x8105/1078 9101/9102/9201/9202 等信令经 TCP 发出，状态置"已下发"。
通用应答关联
终端 0x0001/0x8001 应答按消息流水号关联原指令，置"终端已应答/失败"。
执行结果回收
拍照/视频等异步动作的结果经附件/媒体通道回收，置"已完成"；超时未应答置失败并允许重发。

4.3 补传与附件流程

补传轨迹：终端缓存 → 恢复连接批量上报（补发标志置位，携带原始 gpsTime）→ 网关打 is_backfill 标 → 写实时通道外的补充分支 → 入库 ext.is_backfill=true 并触发 F12 里程/统计回补。
报警附件：边缘算法命中 → 终端抓拍 1～3 张 JPEG（含水印）随 0x0200 附加项或报警媒体 topic 上报 → 平台鉴权转存对象存储 → 回写 risk_event 附件关联；长片段走"按需调阅 + 断点续传"，不做常态全量上传。

6. 业务价值

  • 真实数据闭环：平台从"演示/CSV 数据"升级为真实部标终端实时数据，监控、风控、报表全部业务获得真实数据源。
  • 接入标准化：遵循 JT/T 808/1078 国标体系，终端厂商可替换、可多厂商混接，避免私有协议绑定。
  • 事件可查证：主动安全报警带图、带片段，事故还原从"只有轨迹点"升级为"轨迹 + 图片 + 视频"证据链。
  • 降本：边缘触发 + 按需调阅 + Wi-Fi 回场，不上传全量视频，流量与存储成本可控。
  • 平滑演进：先对接成熟 vps 网关快速获得数据面能力，自建 Netty 网关作为终态，业务侧消费的 Kafka 契约保持不变，切换无感知。

9.1 vps 现状事实（取自 REF 专题）

  • 三进程：jt808-service（TCP 10808 + HTTP 18001）、jt808-file（TCP 10818 + HTTP 18009）、vps-video（TCP 10780-10782 + WS 20780-20782，无鉴权）。
  • 808 帧处理：0x7E 分帧、转义还原、XOR 校验、消息分包；2013 版 BCD[6] 与 2019 版 BCD[10] 手机号自适应。
  • 上线流程：0x0100 注册（白名单 vps_base_truck，authCode=手机号）→ 0x8100 注册应答 → 0x0102 鉴权 → 0x0002 心跳 → 0x8001 应答；0x0200 定位。
  • Kafka topics：jt808_gps_topic（key=truckId）、jt808_warn_topic、jt808_warn_media_topic、jt808_heartbeat_topic、jt808_command_topic、jt808_offline_topic（仅离线 type=1，无上线事件）、jt808_raw_hex_topic；jt808_media_topic 为死代码。
  • 主动安全 typeId：ADAS 101001～101011、DSM 102001～102011、盲区 104001～104003、激烈驾驶 105001～105007；典型如 101001 FCW、102001 疲劳、102002 接打手机、102003 抽烟。
  • 1078 信令：0x9101/9102 实时音视频传输/控制、0x9201/9202/9205 历史音视频回放/控制、0x1205 资源列表、0x9301～9306 平台间转发预留。

9.2 Kafka Topic 对接契约（消费侧）

Topic消息含义消费处理

10. 目标架构与 GATEWAY_MODE

10.1 双路径策略

近期（落地路径，P0～P1）：不改动 vps 网关、不自建协议栈，在 processing-service 新增 app/gateway/ 消费 vps Kafka 数据面，补齐标识映射、报警字典、附件转存、在线状态四个缺口，快速让真实终端数据进入平台。
终态（蓝图，P2+）：Java 侧新建 module-gateway，基于 Netty 自建 JT/T 808-2019 TCP 网关与 1078 信令面，自有连接管理与集群；Kafka 作为统一数据面对下游契约不变，vps 可作为过渡或特定车型兼容通道并行存在。

10.2 GATEWAY_MODE 三模式（任务规划口径）

本节为设计规划，尚未实现。GATEWAY_MODE 目前仅在文档门户关键词中出现，三份 GATEWAY 专题正文与 processing-service 代码中均无该配置项，属本任务书要求纳入的配置化演进设计。
模式数据源用途设计要点
simulator现有 services/simulator.py 进程内模拟器本地开发、功能演示、CI 冒烟默认模式；保持现有 /api/simulator/start 行为不变
mock网关仿真器（规划）：按 808/1078 报文规格生成结构化消息的仿真进程无真车/无 vps 环境下的联调、补传/弱网/报警附件场景构造、500 车级压测报文级仿真（区别于 simulator 的业务点仿真）；支持脚本化场景与时间轴回放
gateway真实网关：近期=vps Kafka 消费；终态=自建 Netty 网关生产与真实终端接入双标识必须全部解析成功；未登记终端进隔离区而非丢弃

配置拟落在 processing-service config.py（如 GATEWAY_MODE=simulator|mock|gateway），模式切换只改变数据入口适配器，下游入库/CEP/在线状态的处理契约保持一致，保证同一套业务代码三模式可跑。

  • 模式为进程级配置，变更后重启 processing-app 生效；不支持运行中热切换（避免位点与会话状态错乱）。
  • simulator 与 mock 模式禁止在生产环境启用，启动时按部署环境变量做保护校验。
  • 三模式输出的内部消息必须通过同一组契约测试（schema、必填字段、口径换算），防止模式间行为漂移。

11. F01 JT/T 808-2019 TCP 网关（设计规划）

本节为设计规划，尚未实现。终态自建网关为蓝图；近期以对接 vps Kafka 数据面落地（GATEWAY-PLAN-001 结论：不自建协议栈、只对接 vps 网关）。

11.1 目标

  • 终态：自有 Netty 网关直接承载终端 TCP 长连接，完成 0x7E 分帧、转义、XOR 校验、分包重组（2013 BCD[6]/2019 BCD[10] 自适应）、注册鉴权、心跳、0x0200 定位及苏标附加项解析。
  • 近期：消费 vps 已解码的结构化 Kafka 消息，mappers.py 做纯函数映射，业务侧先获得真实数据流。

11.2 拟新增组件（终态）

11.3 集群设想

  • 无状态接入节点 + 共享会话路由（Redis）：终端可连任意节点，下行指令按路由表转发至持有连接的节点。
  • 四层负载（LVS/云 NLB）做 TCP 负载均衡；连接与终端解耦，节点故障后终端自动重连到其他节点。
  • 容量目标对齐 F40：一期 500 车 × 0.2Hz 报文回放验证，蓝图百万级长连接（两地三中心，见 MOD-DBD-018 F39）。

11.5 口径换算（GATEWAY-PLAN-001 明确）

  • 速度：vps 单位 m/h ÷ 100 → km/h 整数（traj_gps_point.speed 为 integer km/h）。
  • 里程：vps 单位米 ÷ 1000 → km（mileage numeric(12,2)）。
  • 苏标报警级别反转：苏标 1=高、2=低；平台等级为 3=高、2=中（高→3、低→2），映射在 29 类报警字典中逐类配置。
  • 坐标：终端 WGS-84 经纬度不直接写入现有 GCJ-02 点位链路，在接入层转换（F09 统一转换服务），原始坐标留存 ext.raw_lng/raw_lat。

11.6 依赖与衔接

  • 依赖：F02 双标识映射是入库前置；F09 坐标转换（MOD-DBD-015）是入库前置。
  • 衔接现有类：写入 traj_gps_point 后复用 processing-service 现有 cep_engine.evaluate_points 旁路；在线态收口替换 DashboardMapper.selectOnline 等三处窗口口径。

11.7 验收标准

  1. mock 模式下回放 0x0200 报文（含分包），分帧/转义/校验/重组结果与标准报文一致。
  2. gateway 模式消费 jt808_gps_topic，500 车 × 0.2Hz 持续 30 分钟无丢失（DLQ 为 0，入库点数 = 发送点数）。
  3. 速度/里程/级别换算对 29 类报警抽样逐条与人工计算一致。
  4. 未登记终端消息全部进入 gateway_unknown_terminal，主表不出现脏车辆 ID。
  5. 杀停消费者 5 分钟后重启，手动位点从上次提交继续，无重复入库（幂等键见 18 节）。
  6. 终态：两台网关节点 + NLB，终端被分配到不同节点；杀死任一节点后终端 90 秒内在另一节点恢复上线。

14. F04 轨迹补传（设计规划）

本节为设计规划，尚未实现。

14.1 设计要点

  • 终端侧本地缓存容量 ≥72 小时定位数据（选型要求）；恢复连接后按时间序批量补报。
  • 补报点保留原始 gpsTime（定位时刻）入库，receive_time 为平台接收时刻，二者严格区分；vps 侧补发标志字段为 PositionInfo.delay，映射到内部 ext.is_backfill。
  • 实时点与补传点分通道/打标处理：补传点不触发实时 WebSocket 推送、不重复触发实时报警冷却逻辑；写入 traj_gps_point.ext（jsonb）标记并参与 F41 补点列。
  • 触发 F12 派生统计回补：里程、行驶时长、停留等按 gpsTime 重算受影响日期的统计分片，避免补传点被计为"今天"。

14.2 幂等与乱序

  • 幂等键：(identity_code/plate_no, gps_time) 或终端流水号；重复补传不产生重复点（规划部分唯一索引或 ON CONFLICT）。
  • 乱序：补传点按 gps_time 插入历史位置，查询与统计一律以 gps_time 排序，不以入库顺序为准。

14.3 验收标准

  1. 终端断网 2 小时后恢复，72 小时内缓存点全部补齐，traj_gps_point 中 ext.is_backfill=true 且 gps_time 为原始时刻。
  2. 补传点不出现在实时监控"最新位置"跳变中；大屏最后位置仍为真实最新点。
  3. 同一批次重复投递一次，点数不增加（幂等）。
  4. F42 里程报表对应日期里程随补传正确回补，不记入接收当天。

车速CAN/OBD1～10Hz与定位速度交叉校验、急加速/急减速（评分阈值 2.5m/s²）

油量 / 电量 SOC、充电状态CAN/OBD（新能源）周期油耗 F49、加油 F50、新能源管理

15.2 设计与衔接

  • 协议：808 0x0705 CAN 总线数据上传；信号字典按 SAE J1939 / OBD-II PID 建映射表，不同车型 CAN 矩阵差异用"车型 → 信号映射配置"隔离。
  • 存储：高频信号不建议逐行写入关系库（量大）；规划降采样（如 1Hz）入 traj_gps_point.ext 或新车况快照表，原始高频数据走时序存储（F39 容量评估）。
  • traj_gps_point 现有无油量字段，F49 油耗报表依赖新增油量列（18 号迁移一并规划，见第 18 节）。

15.3 验收标准

  1. 台架回放 0x0705 报文，车速/转速/ACC/油量解析值与 CAN 矩阵表逐信号一致。
  2. 车辆静止且转速>800rpm 持续 5 分钟，F45 怠速口径可识别出该怠速段（F45 上线前以数据样本验证为准）。
  3. 10Hz 信号在 1Hz 降采样后时序连续、无明显缺口；缺口率进入 F36 质量指标。

16. F06 车载视频流媒体接入（设计规划）

本节为设计规划，尚未实现。平台侧无流媒体组件；vps-video 现状为 JavaCV/FFmpeg 自研 WS-FLV 且端口 20780-20782 无鉴权。

16.1 目标架构

终端摄像头
   │ 1078 over 808 TCP（0x9101 实时点播 / 0x9201 历史回放）
   ▼
[近期] vps-video（10780-82）          [终态] module-gateway 信令面
   │ RTP/私有码流推流                      │ 1078 信令
   ▼                                       ▼
ZLMediaKit（规划部署，统一流媒体内核）
   ├─ HLS（低延迟可接受场景）
   ├─ HTTP-FLV / WS-FLV（浏览器 flv.js 实时播放，首屏快）
   └─ WebRTC（超低延迟对讲/应急）
   ▲
 前端 H5 播放器（flv.js）；播放 URL 经后端签发、带时效与鉴权

16.2 选型：ZLMediaKit

  • 理由：单进程同时提供 RTSP/RTMP/HLS/HTTP-FLV/WebRTC 转换，符合"浏览器无插件 + 多终端形态"；开源活跃、C++ 高性能、支持鉴权钩子与录制。
  • 对 vps 现状的改造点：vps-video 的自研 WS-FLV（20780-20782 无鉴权）不直接暴露给浏览器，改为由 ZLMediaKit 统一收口，播放地址由平台后端限时签发（对齐 F25 调阅审批）。
  • 备选：直接沿用 vps WS-FLV（快但无鉴权、无水平扩展）；SRS（能力相近，团队按运维熟悉度二选一，决策点在 P2）。

16.3 信令清单（1078-2016）

0x9101 实时音视频传输请求、0x9102 实时音视频控制、0x9201 历史音视频回放请求、0x9202 回放控制、0x9205 回放进度（拖动）、0x1205 资源列表查询、0x9301～0x9306 平台间转发（预留给 F38）。

16.4 衔接、依赖与风险

  • 前端：Monitor.vue reservedCommand 视频/对讲按钮激活；flv.js 播放器组件规划新建。
  • 依赖：F25 调阅审批与水印（MOD-DBD-016）——无审批单不允许签发播放地址；播放/下载动作走 @AuditLog VIDEO_VIEW。
  • 风险：弱网卡顿与首屏时间需专项测试（F40 流媒体测试指标）；1078-2019 新版本差异（扫描件未逐字核对，见待核实）；vps 拍照无完成事件出口，主动拍照结果回收需补协议约定。

16.5 验收标准

  1. 浏览器（Chrome）发起实时点播，5 秒内出画面，H5 无插件；音视频同步偏差 ≤1 秒。
  2. 未持有效审批单的请求无法获得播放地址；过期地址（规划单次 ≤10 分钟）失效。
  3. 历史回放支持播放/暂停/拖动（0x9201/9202/9205），拖动后 3 秒内出对应画面。
  4. 所有播放发起/停止在审计日志产生 VIDEO_VIEW 记录，含调阅人与终端。
  5. 弱网（限带宽/丢包 5%）下首屏 ≤8 秒、卡顿率满足 F40 流媒体测试基线（基线值在测试方案中固化）。

17. F07 报警附件传输（设计规划）

本节为设计规划，尚未实现。

17.1 设计原则：边缘触发 + 按需调阅，不存全量视频

场景策略
DSM/ADAS 命中瞬间终端边缘算法触发，随预警上报抓拍图 1～3 张 JPEG（含时间/车牌水印），常态只传图不传视频
事件上下文按需调阅报警前后约 10 秒短视频片段（任务书口径；蓝图区间 15～30 秒，最终以产品确认为准）
全量视频不上传、不存储；需要时走 F06 实时/历史回放通道
网络策略回场 Wi-Fi 优先；蜂窝网络仅传事件抓拍小图；断点续传

17.2 协议与续传

  • 图片/附件承载：苏标附加项（0x64 ADAS / 0x65 DSM 等）或 vps jt808_warn_media_topic；jt808-file 进程（TCP 10818）承担文件类传输。
  • 断点续传：苏标码流帧机制 1210/1211（码流/帧上传通知）、1212（文件上传完成）、9212（缺片补传）；平台记录每片接收位图，缺片自动请求补传。

17.3 平台侧组件（media_store.py，P1）

  • 从 vps 文件服务/HTTP 口（18009）带鉴权下载附件（vps 现状下载口无鉴权，平台侧补签名/内网隔离）。
  • 转存对象存储（规划 MinIO，对齐 F26），生成带时效访问 URL；traj_warn_media 存元数据与对象 key，risk_event 与附件 1:N 关联（替代 media_url 单值）。
  • 工单/事件详情的裸链（OrderDetailDrawer 现状）替换为鉴权附件组件。

17.4 依赖与验收

依赖
F01 数据面、F02 双标识；F24 边缘算法（MOD-DBD-016）产生事件；F26 证据保全（MOD-DBD-016）负责留存策略
  1. 模拟疲劳事件，30 秒内平台收到事件 + 1～3 张图，图片水印含车牌与时间，可在风险事件详情打开。
  2. 上传过程中杀断连接，恢复后从缺失片续传，最终文件 MD5 与源文件一致。
  3. 同一事件重复上报（vps 重投）不产生重复附件（source_id 幂等）。
  4. 附件 URL 过期后不可访问；未授权用户无法遍历对象 key。

23. 验收标准汇总（跨分期可测试项）

  1. GATEWAY_MODE 三模式可配置切换，切换后下游业务无需改动即可获得对应数据源。
  2. 真实终端注册→鉴权→心跳→定位全链路：上线 90 秒内可在监控页看到车辆在线与实时位置。
  3. 500 车 × 0.2Hz 回放 30 分钟：无消息丢失、无重复点、DLQ=0、消费 Lag 持续归零。
  4. 29 类报警映射：事件 code、级别（含高低反转）、开闭环属性与字典逐类一致。
  5. 指令下发到应答全状态可追踪，超时/重发/幂等行为符合 13.4。
  6. 补传点带原始时间与补发标记，统计按定位日期回补且不干扰实时链路。
  7. 视频点播 H5 出画面、URL 限时鉴权、调阅全程审计。
  8. 报警图片 1～3 张随事件到达、断点续传文件哈希一致、附件 1:N 关联正确。
  9. 时钟偏差 >30 秒的终端产生质量告警且可在接入状态页列出（移交 F36 质量大盘）。
  10. gateway 模式关闭（切回 simulator）后，消费线程优雅退出、位点已提交，重启无重复消费。
