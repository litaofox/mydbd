MOD-DBD-007 电子围栏

文档编号 MOD-DBD-007|版本 v1.0.0|发布日期 2026-10-05| 状态 已上线|功能编号 F13

事实基准：2026-10-05 源代码与初始化 SQL（07-risk-tables.sql）

主要代码锚点：GeoFenceController / GeoFenceService / RiskGeoFence / RiskGeoFenceMapper（Java，module-risk）；processing-service/app/services/cep_engine.py / app/db.py（Python）；前端 views/system/GeoFenceList.vue、api/risk.ts

1 功能概述

1.1 模块定位与边界

电子围栏模块提供在地图上划定地理区域、对车辆实时位置进行进出判定、并在状态翻转时产生风险事件（GEO_ENTER / GEO_EXIT）的能力。围栏支持两种几何形状：

  • 圆形围栏（CIRCLE）：中心点经纬度 + 半径（50~100000 米），判定使用 PostGIS geography 类型的 ST_DWithin，半径按真实米制大地距离计算；
  • 多边形围栏（POLYGON）：地图手绘顶点（≥3 个顶点，闭合后 ≥4 个点），图形以 geometry(Polygon,4326) 存储，判定使用 ST_Contains。

每个围栏可独立配置触发方向（1=进入报警 / 2=离开报警 / 3=进出都报）、风险等级（1 低 / 2 中 / 3 高）与冷却时间（0~86400 秒，冷却窗口内同车同围栏不重复产生事件）。

一句话边界：围栏档案与图形维护在 Java 平台（/api/risk/fences）；车辆进出的实时判定不在 Java 进程内，而在轨迹处理服务 processing-service（Python FastAPI）中，以 PostGIS 空间函数旁路完成。两侧共享同一套 PostgreSQL/PostGIS 表。

1.3 编号沿革与实现分工（对旧资料的纠正）

旧说法与代码不一致，本文以代码为准：

1. 旧版功能清单曾把电子围栏标注为"待建设"。代码证明该功能已上线：围栏 CRUD、PostGIS 图形存储、车辆实时进出事件链路均完整运行，文档门户卡片亦为"已上线"绿标。

2. Java/Python 代码注释普遍把围栏写作 "F18"（如 07-risk-tables.sql 标题"F18 风控规则引擎（CEP）：规则配置、电子围栏……"、实体注释）。现行功能编号体系中围栏为 F13，F18 是风控规则引擎整体编号（见 MOD-DBD-008）。本文统一使用 F13；历史注释中的 F18 字样属编号沿革遗留，不代表功能未实现。

3. 门户卡片简介"基于 PostGIS 空间查询"属实，但空间判定 SQL 位于 processing-service（Python db.py），不是 Java 平台；Java 侧只通过 ST_GeomFromGeoJSON/ST_AsGeoJSON 维护图形，不含 ST_DWithin/ST_Contains 判定。

1.4 术语与概念

术语含义
围栏（GeoFence）一条 mon.risk_geo_fence 记录，描述一个圆形或多边形地理区域及其触发策略（方向 / 等级 / 冷却）。
触发方向 triggerDir1=仅进入报警，2=仅离开报警，3=进出都报；即使状态发生翻转，方向不匹配也不落事件。
冷却 cooldownSec同车 × 同围栏 × 同事件类型（进入/离开）的最小时间间隔；窗口内重复翻转被丢弃，基准为 risk_fence_state 的 last_enter_time / last_exit_time。
状态翻转本批 inside 与上一状态不同（外 ↔ 内）；只有翻转才可能产生事件，连续在内或连续在外不产生。
首见不补报某车 × 某围栏在状态表无历史记录时，第一个点只初始化 inside，不推断此前是否已发生进出。
EPSG:4326WGS84 经纬度坐标系，多边形图形与前端 Leaflet 统一使用；圆形距离计算时再 ::geography 转型。
热加载 TTLprocessing-service 内 risk_cache_sec（默认 30 秒）的规则 / 围栏缓存寿命，到期懒刷新，无主动失效推送。
软删 valid_mark删除围栏只置 valid_mark=0，配合部分唯一索引使同名围栏可再次创建；历史事件通过 fence_id 保留引用。

2 典型场景

安全管理员
重点区域闯入监控
在化工园区、事故多发路段、港口堆场中心画一个圆形围栏，触发方向设为"进入报警"。车辆一进入区域，坐席界面即收到高风险"进入围栏"事件与工单。
调度监控员
规定路线偏离预警
沿允许行驶走廊绘制多边形围栏，触发方向设为"离开报警"。车辆离开走廊即产生 GEO_EXIT 事件，等价于偏离路线提醒，无需建设专门路线系统。
车队长
禁区/电子围栏考勤
把仓库、客户站点设为围栏并选择"进出都报"，可以从风险事件中还原车辆到离站点时点，用于调度核对；冷却 600 秒可避免停靠期间刷屏。
演示/测试人员
国贸演示围栏
脚本内置种子"演示围栏·国贸（可删）"：圆心 116.404,39.912、半径 3000 米、进出都报、冷却 600 秒，配合内置模拟器车辆游走即可自然产生进出事件。

3 操作流程

菜单路径：系统管理 → 电子围栏（sys_menu id=905，父菜单 900"系统管理"，路由 /system/fences，权限点 risk:fence:view；维护按钮 id=914，权限点 risk:fence:edit）。

3.1 围栏列表与筛选

进入列表
系统管理 → 电子围栏，打开 GeoFenceList.vue，默认分页展示全部有效围栏。
设置筛选
顶部可按围栏名称（fenceName 模糊）、形状（CIRCLE/POLYGON）、状态（启用/停用）组合筛选后查询。
查看列表字段
名称、形状、中心/半径或顶点摘要、触发方向、风险等级、冷却秒数、启停开关、备注、操作列。
进入详情/编辑
点"编辑"打开 720px 抽屉，内嵌 Leaflet 地图回显既有图形，可直接修改后保存。

3.2 新建圆形围栏

点击「新建圆形围栏」
按钮受 v-perm="'risk:fence:edit'" 控制，无维护权限的角色不可见。
地图选点确定中心
抽屉内 Leaflet 地图（高德栅格瓦片底图）点击"地图选点"后在图上点选中心，centerLng/centerLat 自动回填；中国范围校验：经度 73~135、纬度 3~54。
填写半径与策略
半径数字框 50~100000 米；触发方向（进入/离开/进出）、风险等级（低/中/高）、冷却秒数（0~86400）、状态、备注。
保存
后端校验名称在有效围栏中唯一（valid_mark=1 部分唯一索引兜底）；保存成功后前端提示配置约 30 秒内热加载生效。

3.3 新建多边形围栏

开始绘制
点「新建多边形围栏」→ 抽屉地图上点"开始绘制"，逐点单击落顶点。
编辑顶点
"撤销一点"回退最后一个顶点；"清空重画"作废重来；顶点计数 tag 实时显示，至少 3 个顶点。
保存闭合
后端 closedRing() 自动把尾点补成与首点相同形成闭合环（闭合后 ≥4 点），GeoJSON 经 ST_SetSRID(ST_GeomFromGeoJSON,4326) 入库。

3.4 启停 / 编辑 / 删除

  • 启停：列表 switch 调 PUT /api/risk/fences/{id}/status（body {"status": 0|1}）。停用即从 processing-service 的启用围栏缓存中淘汰（TTL 到期后），不再判定。
  • 编辑：PUT /{id}，重新做全套形状与取值校验；多边形重新写 polygon_geom。
  • 删除：DELETE /{id} 为软删（valid_mark=0），同时执行 deleteFenceState 清除 mon.risk_fence_state 中该围栏全部车辆状态。前端二次确认文案明确："历史越界事件保留，围栏状态数据同步清除"。

3.5 进出事件的消费路径

围栏产生的 GEO_ENTER/GEO_EXIT 事件与规则事件结构一致（同落 mon.risk_event，差异仅是 rule_id 为空、fence_id 有值），因此后续消费零定制：

  • 实时监控 → 风险预警分析页（/risk）可按来源"北斗"、等级、车牌、城市查询；
  • 自动生成处置工单（PENDING），进入 MOD-009 的认领/分派/闭环流程；
  • 计入 MOD-010 风险画像的事件趋势、黑点路段与排行（画像事件名兜底表包含 GEO_ENTER/GEO_EXIT）。

  • 单页双抽屉：列表页 views/system/GeoFenceList.vue 内联圆形与多边形两个 720px 抽屉表单，共用一套名称/方向/等级/冷却字段，按 fenceType 切换中心点或顶点编辑区。

  • 权限渲染：新建/编辑/删除按钮统一 v-perm="'risk:fence:edit'"；菜单由 905/914 种子驱动，超级管理员默认可见。

7.2 PostGIS 图形读写（Java 侧）

多边形图形不以顶点数组入库，而是序列化为 GeoJSON 后交给 PostGIS 解析：

-- 写入（RiskGeoFenceMapper.updatePolygonGeom）
UPDATE mon.risk_geo_fence
SET polygon_geom = ST_SetSRID(ST_GeomFromGeoJSON(#{geojson}), 4326)
WHERE id = #{id}

-- 读取（selectPolygonGeoJson）
SELECT ST_AsGeoJSON(polygon_geom) AS geojson FROM mon.risk_geo_fence WHERE id = #{id}

空间索引：CREATE INDEX idx_risk_fence_geom ON mon.risk_geo_fence USING gist (polygon_geom)。圆形围栏不写 polygon_geom，只存中心点与半径。Java 侧没有任何 ST_DWithin/ST_Contains 调用——几何判定全部在 Python 侧。

7.3 实时进出判定 SQL（Python 侧）

db.fences_inside_status(lng, lat) 一条 SQL 同时返回当前点命中的全部启用中围栏，圆形与多边形各用各的空间谓词：

-- 圆形：geography 米制大圆距离
ST_DWithin(
  ST_SetSRID(ST_MakePoint(:lng, :lat), 4326)::geography,
  ST_SetSRID(ST_MakePoint(center_lng, center_lat), 4326)::geography,
  radius_m
)

-- 多边形：4326 平面包含
ST_Contains(f.polygon_geom, ST_SetSRID(ST_MakePoint(:lng, :lat), 4326))

圆形围栏把几何显式 ::geography 转型，ST_DWithin 第三参数半径按米解释，避免把经纬度度数当距离；这是它与"直接用经纬度差估算"的本质区别。

7.4 进出状态机与冷却

状态保存在 mon.risk_fence_state（主键 = identity_code + fence_id），字段 inside、last_point_time、last_enter_time、last_exit_time。cep_engine._evaluate_fences 对每个轨迹点：

① 查当前命中
fences_inside_status(lng,lat) 得到本点 inside=true 的围栏 id 集合。
② 取历史状态
get_fence_states(identity, fence_ids) 取该车上批 inside 与最近进出时间。
③ 首见只初始化
state 为 None（该车第一次接近该围栏）时仅 upsert 当前 inside，不补报任何历史进出事件——表注释明确"首见只初始化不补报"。
④ 状态未变无事件
old==inside（连续在围栏内或连续在围栏外）不产生事件，只更新 last_point_time。
⑤ 翻转 + 方向 + 冷却
false→true 候选 GEO_ENTER，true→false 候选 GEO_EXIT；方向须命中围栏 trigger_dir；_cooled 比对 last_enter_time/last_exit_time，未过 cooldown_sec 放弃。
⑥ 单事务落状态+事件
apply_fence_transitions：ON CONFLICT (identity_code,fence_id) DO UPDATE（COALESCE 保留未更新的冷却时间），同事务 insert mon.risk_event。

围栏事件字段固定写法：event_code=GEO_ENTER/GEO_EXIT、event_source='北斗'、confidence=1.00、fence_id=围栏 id、rule_id=NULL、title=「进入围栏·{围栏名}」/「离开围栏·{围栏名}」、risk_level=围栏配置等级。

7.5 围栏配置热加载

processing-service 不在每个点上查围栏表，cep_engine._fences() 维护 TTL 缓存：

  • TTL 配置项 settings.risk_cache_sec（app/config.py），默认 30 秒；规则表 _rules() 共用同一 TTL。
  • 到期后下次调用重新执行 db.load_enabled_fences()（仅 status=1 且 valid_mark=1）。
  • 因此前端保存围栏后不会瞬间生效，页面提示"约 30 秒内热加载生效"与此一致；无需重启处理服务。

7.6 触发入口与旁路容错

  • 实时路径：POST /api/ingest/traj（服务令牌 verify_service_token）按 5000 点分片入库后，try/except 调 cep_engine.evaluate_points(rows)；CEP 抛异常只 print 日志，不阻断轨迹入库主链路。
  • 批量路径：POST /api/ingest/load-sample 导入 CSV 后只 insert 点（并幂等导入当日 driver_events.json 事件），不调用围栏评估，历史轨迹不会反补围栏事件。
  • 模拟器路径：内置 SimulatorService 每 2 秒走的也是 /api/ingest/traj 同一入口，因此模拟器车辆穿越国贸演示围栏时会真实产生进出事件。

12 技术选型依据

  1. PostGIS 而非自写几何算法：GiST 空间索引 + 成熟的 ST_DWithin/ST_Contains 让"一点对全部围栏"的判定保持在 SQL 单查询内，精度与性能都有保障，避免 Java 应用层实现射线法/距离公式的维护成本。
  2. 圆形用 geography、多边形用 geometry：圆形半径是真实米制业务语义，geography 大圆距离在全国纬度范围内一致；多边形区域本身用经纬度坐标描述，ST_Contains 语义直观且与前端 GeoJSON 坐标系（EPSG:4326）天然一致。
  3. 判定下沉到接入服务而非 Java 平台：processing-service 已是轨迹入库的必经节点，在同进程旁路判定省一次网络跳转，且引擎异常天然隔离于平台事务。
  4. 状态机表而不是滑动窗口查询：每车每围栏一行 inside 状态 + 冷却时间戳，判定复杂度只与"当前点命中的围栏数"相关，不随历史点数增长。
  5. 配置 TTL 缓存而非消息通知：单实例演示阶段 30 秒 TTL 足够，省去 Java→Python 的配置广播通道；热加载对运维零要求。
  6. 图形存 GeoJSON 入 geometry 列、顶点瞬态传输：实体 RiskGeoFence 不绑定 PostGIS Java 类型，points 仅作传输字段，降低 ORM 与空间类型扩展耦合。

15 边界行为与常见问题

画完围栏多久生效？
最长约 30 秒（risk_cache_sec TTL）。Java 保存立即提交，Python 侧下次缓存到期重查后才纳入判定；页面提示与该口径一致。
车辆一开始就在围栏里，会报警吗？
不会。状态表无历史记录（首见）时只初始化 inside 状态、不补报事件；必须发生"外→内"或"内→外"的翻转才报警。
导入历史轨迹为什么没有围栏事件？
/api/ingest/load-sample 批量导入只做轨迹 insert，不调用 cep_engine；围栏判定只挂在实时推送 /api/ingest/traj 链路上。
删除围栏后历史事件还在吗？
在。删除是软删（valid_mark=0），mon.risk_event 历史保留；被清除的只是 mon.risk_fence_state 车辆状态。确认弹窗文案已明确这一点。
停用与删除对状态的影响一样吗？
不一样。停用（status=0）只让围栏退出判定，risk_fence_state 保留，重新启用后沿用原 inside；删除才清状态。因此长期停用后再启用，首个点可能直接触发一次翻转事件。
多边形顶点数有上限吗？
后端只校验 ≥3 个顶点并自动闭合，未设顶点上限（现状）。顶点过多会加大 ST_Contains 与 GiST 比对开销，绘制体验也会下降，管理上建议控制在几十个顶点量级。
圆形半径为什么不用经纬度差？
半径按真实米制业务语义配置，判定把点与圆心都 ::geography 转型后用 ST_DWithin 做大地距离，全国任意纬度半径一致；经纬度 1 度对应的米数随纬度变化，不能直接用。
CEP 评估出错会导致轨迹丢点吗？
不会。ingest.py 中 evaluate_points 被 try/except 包裹，异常仅打印日志，轨迹入库结果照常返回。
围栏事件为什么没有 rule_id？
围栏不是规则引擎的规则，没有 mon.risk_rule 对应行；事件以 fence_id 关联围栏、rule_id 为 NULL，引擎概览"规则事件 TOP5"因此不计围栏事件。
围栏事件会计入驾驶评分扣分吗？
不会。ScoreConstants 的扣分白名单只有 8 个事件码（超速、疲劳、DSM、ADAS、组合码），GEO_ENTER/GEO_EXIT 不在其中；但画像趋势/黑点/排行仍统计围栏事件。
围栏可以按车辆/部门分别配置吗？
现状不可以。围栏是全局生效的地理区域，对所有在线车辆判定；按车/按部门的围栏授权与差异化策略未在当前代码中实现。

2圆形围栏 CRUD合法圆心/半径可保存；越界经纬度、半径越界、重名被后端拒绝；详情回显中心与半径GeoFenceList 抽屉操作
3多边形围栏 CRUD≥3 顶点可保存，尾点自动闭合；ST_AsGeoJSON 回读顶点与绘制一致；GiST 索引存在地图绘制 + 数据库 ST_NPoints 核对
4实时进入事件trigger_dir 含进入时，模拟器车辆外→内穿越产生 GEO_ENTER（event_source='北斗'、confidence=1.00、title 含围栏名）模拟器 + risk_event 查询
5实时离开事件内→外穿越且方向含离开时产生 GEO_EXIT；方向不匹配不产生同上
6首见不补报清空 risk_fence_state 后车辆已在围栏内的首批点不产生事件删状态后推点验证
7冷却生效冷却窗口内反复穿越不重复落事件；窗口后恢复连续推点比对事件时间间隔
8热加载新增/停用围栏后 30 秒内判定行为变化，无需重启 processing-service计时验证
9删除联动删除后 valid_mark=0 且 risk_fence_state 对应行清除，历史 risk_event 保留数据库核对
10自动建单围栏事件存在对应 PENDING 工单与 CREATE 日志，风险页"去处理"可直达risk_work_order 联查
11方向过滤trigger_dir=2 的围栏在车辆进入时不产生事件，仅离开时产生模拟器双向穿越
12停用即时性停用并等过一个 TTL 后，穿越不再产生事件；状态行仍保留risk_fence_state 核对
13同名重建删除围栏后允许用相同名称新建（部分唯一索引仅约束 valid_mark=1）连续两次建同名围栏

17 待核实项

以下条目在 2026-10-05 代码阅读中未找到充分证据或依赖运行环境，按"待核实"标注，不在本文做确定性结论：

  • 圆形围栏判定的大数据量性能：polygon_geom 有 GiST 索引，但圆形判定基于 center_lng/center_lat 标量列与 geography 距离，未见专用空间索引；启用围栏数量很大时全表 ST_DWithin 成本待压测。
  • 多实例并发一致性：状态机 upsert 依赖单实例处理同一车辆的点流；若 processing-service 水平扩展且同一 identity_code 的点分散到多实例并发评估，缺少分布式锁，存在重复翻转事件的理论可能。当前为单实例部署。
  • 状态表增长与清理：risk_fence_state 只在删除围栏时清除对应行，车辆退役或围栏长期停用后的残留状态没有独立的定期清理任务，是否需要归档/清扫策略待确认。
  • 围栏工单 SLA 口径：围栏事件建单复用工单通用 SLA 配置（risk_order_sla 按事件码/等级匹配，未匹配到时的兜底时限以 MOD-009 说明为准）；是否需要为 GEO_ENTER/GEO_EXIT 单独配置 SLA 未见种子数据，属运营配置待核实项。
  • 底图可用性：前端使用在线高德栅格瓦片，目标内网环境的瓦片替代地址与离线部署方案待实施时确认。
