MOD-DBD-008 风控规则引擎

文档编号 MOD-DBD-008|版本 v1.0.0|发布日期 2026-10-05| 状态 已上线|功能编号 F18

事实基准：2026-10-05 源代码（module-risk / module-monitor / processing-service）与 07-risk-tables.sql、03-mon-tables.sql

主要代码锚点：RiskRuleController / RiskRuleService / RiskRule / EngineController / EngineStatsService（Java）；cep_engine.py / db.py / risk_engine.py / routes/analysis.py（Python）；前端 RiskRuleList.vue / risk/RiskEvents.vue

1 功能概述

1.1 模块定位与"边缘触发"口径

风控规则引擎（CEP，Complex Event Processing）把两类输入加工为统一的风险事件（mon.risk_event）：

  • 北斗轨迹点：processing-service 对实时入库的轨迹点做速度/连续驾驶/组合条件评估，产出超速、疲劳、疲劳叠加超速事件；
  • 终端边缘信号：DSM/ADAS 危险动作在北斗终端侧（边缘计算）识别完成，平台只接收信号码并按启用规则分级，产出终端信号类事件。

平台不做全量视频分析。processing-service/app/services/risk_engine.py 模块 docstring 明确"边缘识别+按需调阅，平台不做全量视频分析"。其中的 recognize() 是确定性占位实现（按 task_id 字符和派生事件码、固定置信度），仅用于打通演示链路，不是真实视觉模型。真实 DSM/ADAS 事件以终端上报信号为准。该业务规则已于 2026-10-02 由用户确认。

1.3 配置面与评估面的分工

与电子围栏相同，规则模块也是"Java 配置、Python 评估、共享数据库"：

  • Java（module-risk）：/api/risk/rules 配置管理、/api/risk/engine/summary 概览统计；不做任何事件判定。
  • Python（processing-service）：cep_engine.evaluate_points 与 evaluate_signal 是唯一的事件产生入口；规则以 TTL 缓存从 mon.risk_rule 读取。
  • Java（module-monitor）：/api/monitor/risks 负责事件的查询与人工处置，不产生事件。

编号沿革提示：07-risk-tables.sql 与 Java/Python 注释中"F18"同时涵盖规则与围栏（脚本标题为"F18 风控规则引擎（CEP）：规则配置、电子围栏……"）。现行编号中 F18 仅指规则引擎（本模块），围栏为 F13（MOD-007）。

1.4 术语与概念

术语含义
风险事件 risk_event引擎唯一产出物，落 mon.risk_event；北斗规则事件、终端信号事件、围栏事件与视频占位事件共用该表。
规则 risk_rulemon.risk_rule 一行配置：规则类型 SPEED/FATIGUE/SIGNAL/COMBO、事件码、jsonb 参数阈值、等级与冷却；内置 8 条 + 可自定义。
边缘触发DSM/ADAS 事件在终端侧识别，平台只接收信号码（evaluate_signal），不在平台侧跑视频模型。
事件码 eventCode事件业务编码（SPEED_GENERAL、ADAS_FCW 等）；SIGNAL 规则的 ruleCode 与 eventCode 相同；驾驶评分按 8 个白名单码聚合扣分。
冷却 cooldownSec同车 × 同规则的最小产出间隔；以 mon.risk_event 的 MAX(event_time) 为权威（last_rule_event_times 一条 SQL 查多规则），处理服务重启后去重语义不变。围栏冷却另走状态表时间戳。
每批至多一条 + 冷却SPEED/FATIGUE 在同一轨迹批内每车每规则至多产 1 个候选（SPEED 取批内最大速度点）；跨批能否再产取决于距上一条事件是否已过冷却，而非持续记录"在阈上/阈下"状态。
驾驶中断FATIGUE 评估中相邻轨迹点间隔超过 max_gap_minutes（默认 10 分钟）即认为驾驶中断，连续驾驶计时清零。
组合事件 COMBO30 分钟窗口内已有疲劳事件、且当前批最大速度达到速度阈值时追加的高风险事件。
规则热加载Python 侧 _rules() TTL 缓存（risk_cache_sec，默认 30 秒），配置改后无需重启即生效。

2 典型场景

安全管理员
分级超速阈值管理
保留内置"一般超速 ≥100km/h（中风险、冷却 5 分钟）"与"严重超速 ≥120km/h（高风险、冷却 3 分钟）"，也可按企业制度调整阈值或新增自定义超速规则。
安全管理员
疲劳驾驶制度落地
内置规则按连续驾驶 240 分钟、点间隔超 10 分钟视为中断判定；命中即高风险事件并自动建单，冷却 30 分钟，坐席须按 SLA 15 分钟（高风险）处置。
调度监控员
终端 DSM/ADAS 信号接警
终端识别疲劳、分心、前向碰撞、车道偏离后上报信号码；平台仅对启用中规则对应信号落事件并定级，坐席在风险预警分析页统一接警。
安全管理员
疲劳叠加超速组合预警
内置 COMBO 规则：30 分钟窗口内已发生疲劳事件、且当前批最大速度 ≥100km/h，再产一条高风险组合事件，用于识别最危险的驾驶状态。
平台运维/演示
引擎运行态势一览
风控规则页顶部 4 张卡：启用/全部规则、启用/全部围栏、今日事件（按等级着色）、规则事件 TOP5，用于演示与日常巡检引擎是否在产出事件。

3.1 新建/编辑规则

打开表单抽屉
「新增规则」按钮受 v-perm risk:rule:edit 控制；编码正则 ^[A-Z][A-Z0-9_]{2,39}$。
选择类型
SPEED 速度阈值 / FATIGUE 连续驾驶 / SIGNAL 终端信号 / COMBO 组合事件；表单按类型动态切换参数输入（DEFAULT_PARAMS 与 8 条种子同值）。
SIGNAL 选信号码
SIGNAL 类型编码为下拉四选一：DSM_FATIGUE / DSM_DISTRACTION / ADAS_FCW / ADAS_LDW；创建时 eventCode 自动等于 ruleCode。
设置等级与冷却
riskLevel 1/2/3；cooldownSec 0~86400 秒；可先停用保存（status=0）稍后启用。
保存与热加载
编码/类型/事件码创建后不可变（编辑仅可改名称、等级、params、冷却、状态、备注）；内置规则 built_in=1 禁删，删除为 valid_mark=0 软删；约 30 秒后评估面生效。

3.3 风险预警分析页

菜单路径：实时监控 → 风险预警分析（菜单 id=13，路由 /risk，页面 risk/RiskEvents.vue，权限 risk:view）。

  • 概览：4 张统计卡 + F21 漏斗卡（事件总数 → 工单数 → 干预工单数 → 闭环数，以及干预率/闭环率，口径见 MOD-009）。
  • 筛选：事件来源（DSM/ADAS/national/vendor/北斗）、等级、处置状态、命中规则（下拉来自 /rules/all，含停用项供历史筛选；无权限时静默降级）、车牌、城市钻取 tag（时间窗支持 query 恢复）。
  • 处理：每行"去处理"先调 POST /api/risk/orders/ensure/{eventId} 确保工单存在，再打开 OrderDetailDrawer（见 MOD-009）。
  • 图表：ECharts 事件类型饼图；页面还含视频分析任务表（展示 /api/analysis/video 任务记录）。

3.4 视频分析任务（演示链路）

风险预警分析页的视频分析任务表展示 mon.video_analysis 记录。该链路由 POST /api/analysis/video（服务令牌）驱动：先 upsert RUNNING 任务 → 占位识别 → evaluate_signal → 回写 SUCCESS 结论与事件数。产品上不提供"上传视频做 AI 分析"的用户操作，该接口面向终端/联调方。

5 用户价值

  • 策略可调不改代码：阈值、等级、冷却全部配置化，安全管理员当天即可把新制度推到评估面（≤30 秒热加载）。
  • 一类事件一套出口：北斗点算出的事件与终端边缘信号事件同表同结构，坐席只面对一个风险列表与一套工单流程。
  • 噪声受控：同车同规则冷却窗口去重 + 首见不补报，事件流可被坐席真正消费，而不是被海量重复点淹没。
  • 责任可溯：事件带 rule_id/fence_id 与 title 中文名快照，规则事后改名不影响历史事件语义；误报可在闭环环节标记 FALSE_ALARM 并从评分中剔除（MOD-010）。
  • 边缘架构省带宽：平台不接全量视频流，只接信号与按需调阅片段，符合已确认的视频预警处理规则。

7 核心实现逻辑

7.1 规则模型与校验

RiskRule（@TableName("mon.risk_rule")）字段：ruleCode、ruleName、ruleType、eventCode、riskLevel(1/2/3)、params（jsonb，JacksonTypeHandler 映射 Map<String,Object>）、cooldownSec、status、builtIn、validMark、remark + 审计四字段。

校验点规则（RiskRuleService + RuleSaveRequest）
ruleType 白名单仅 SPEED / FATIGUE / SIGNAL / COMBO 四种
ruleCode 形态正则 ^[A-Z][A-Z0-9_]{2,39}$；有效规则内唯一（部分唯一索引 uk_risk_rule_code WHERE valid_mark=1）
SIGNAL 编码必须 ∈ {DSM_FATIGUE, DSM_DISTRACTION, ADAS_FCW, ADAS_LDW}；创建时 eventCode=ruleCode
不可变字段编码、类型、事件码创建后不可修改（update 仅改名称/等级/params/冷却/状态/备注）
SPEED 参数speedKmh ∈ [1,220]
FATIGUE 参数continuousMin ∈ [1,1440]；gapMin ∈ [1,120]
COMBO 参数windowMin ∈ [1,720]；speedKmh ∈ [1,220]
SIGNAL 参数无阈值参数（params 为空对象即可）
冷却cooldownSec ∈ [0,86400]
删除保护built_in=1 禁删；删除=valid_mark=0 软删

规则保存接口（POST/PUT）请求体字段

字段类型要求备注
ruleCodestring必填；^[A-Z][A-Z0-9_]{2,39}$；有效规则唯一创建后不可改；SIGNAL 时即事件码四选一
ruleNamestring必填写入事件 title 快照
ruleTypeenumSPEED/FATIGUE/SIGNAL/COMBO创建后不可改
eventCodestringSIGNAL 必须等于 ruleCode；其他类型按业务码创建后不可改
riskLevelint1/2/3决定工单 SLA 档位与评分扣分
paramsobject按类型白名单键 + 取值区间校验；SIGNAL 传 {}jsonb 落库
cooldownSecint0~864000 表示不去重（不建议）
statusint0/1停用后最长 30 秒退出评估
remarkstring可空—

COMBO_FATIGUE_SPEED疲劳叠加超速COMBO3 高{"windowMin":30,"speedKmh":100}1800

7.3 北斗点评估：超速/疲劳/组合

evaluate_points(rows) 在轨迹点入库后执行，先按 identity_code（缺省 plate_no）分组、按 gps_time 排序，然后逐车评估：

超速（SPEED）

  • 取本批最大速度点，对每条启用 SPEED 规则判 max_speed >= speedKmh；同批内同规则至多落一条事件，事件点取最大速度点。

疲劳（FATIGUE）

  • 调 db.latest_driving_session：仅取 speed>0 的点，用 SQL LAG 窗口按 gapMin 间隔切分会话；回看 continuousMin+gapMin 分钟；
  • 命中条件：会话时长 ≥ continuousMin 且末点未中断（仍在驾驶）；每车每批每规则至多 1 个候选。

组合（COMBO）

  • 窗口内存在 FATIGUE_DRIVE 事件：库内查 db.has_recent_rule_event(plate, FATIGUE_RULE_ID, since)，或本批内存 batch_events 中已有疲劳事件；
  • 且当前批最大速度 ≥ 规则 speedKmh，两个条件同时满足才产出。

7.4 边缘信号评估：SIGNAL 规则

evaluate_signal(channel, event_code, plate_no, identity_code, lng, lat, speed, media_url, confidence)：

  1. 从启用规则缓存中找 rule_type='SIGNAL' AND event_code = 入参 的规则；找不到返回 None（不落事件）；
  2. 冷却判定通过后落事件：event_source=channel 大写并截断 16 字符（如 DSM/ADAS）；confidence 用传入值，缺省 0.88；media_url 随事件保存（按需调阅的截图/片段地址）；
  3. 事件 title=rule_name 快照，risk_level 取规则等级。

7.5 冷却去重

db.last_rule_event_times(plate, rule_ids) 一条 SQL 查 mon.risk_event 中同车牌各 rule_id 的 MAX(event_time)；_cooled(last_time, point_time, cooldown_sec) 判定是否已出窗口。围栏冷却另走 risk_fence_state 的 last_enter_time/last_exit_time（见 MOD-007）。这保证同车同规则在冷却窗口内无论来多少批点都只产生一条事件。

7.6 事件落库与自动建单

db.insert_risk_events(rows) 是规则事件与围栏事件的共同落库函数，在同一数据库事务内完成：

插入事件
INSERT mon.risk_event（event_source='北斗'、confidence=1.00、title=规则/围栏中文名快照）RETURNING id、risk_level、event_time。
读取 SLA
读 mon.risk_order_sla（进程内 60 秒缓存；缺省高 60 分/中 30 分等待遇由 SLA 种子实际为 15/60/240）。
创建工单
INSERT mon.risk_work_order：order_no=mon.fmt_order_no()、status=PENDING、deadline=event_time+limit_min、creator='cep-engine'。
写流转日志
INSERT risk_order_log：action='CREATE'、operator='CEP'、remark='风险事件自动建单'。

事件与工单在同一事务里提交，不存在"有事件无工单"的中间态；唯一约束 uk_risk_order_event(event_id) 兜底重复建单（Java 侧 ensureOrder 捕获 DuplicateKeyException 返回既有单）。

7.7 视频分析占位识别

routes/analysis.py 的 POST /api/analysis/video（整路由挂 verify_service_token）：

  1. 组装 task（taskId 缺省 VA+uuid 前缀），db.upsert_video_analysis 置 RUNNING；
  2. risk_engine.recognize(task_id, channel, event_code)：若请求显式带 eventCode 则优先采用；否则按 task_id 字符和确定性派生。内置候选 _PROFILES：DSM → DSM_FATIGUE(0.91)/DSM_DISTRACTION(0.84)；ADAS → ADAS_FCW(0.88)/ADAS_LDW(0.82)；
  3. 候选交 evaluate_signal 走与真实终端信号完全相同的匹配/冷却/落事件路径；
  4. 更新任务 SUCCESS：落事件时 summary="检出 X，按规则定级 N 级，已生成风险事件"，event_count=1；否则为"未匹配启用规则或处于冷却窗口"，event_count=0。

/api/ingest/load-sample 还会幂等导入 samples/driver_events.json 的当日事件（等级取 extra.dsm_level，默认 2），同一天只导一次（count_risk_events_on 判重）。

7.8 规则热加载

cep_engine._rules() 与 _fences() 共用 TTL 缓存（settings.risk_cache_sec 默认 30 秒），到期后 db.load_enabled_rules() 重查全部 status=1 且 valid_mark=1 的规则（含 params jsonb）。规则调整无需重启、无刷新接口。

8 数据流程

引擎有两条事件产生路径，在"落 mon.risk_event + 自动建单"处汇合：

路径 A：北斗轨迹点 → 规则事件（已上线主链路）
终端/模拟器 POST /api/ingest/traj → 轨迹分片入库 → evaluate_points 分组排序 → SPEED（批内最大速度）/ FATIGUE（LAG 会话）/ COMBO（窗口疲劳+当前超速）→ 冷却 SQL → insert risk_event + 建 PENDING 单。
路径 B：边缘信号 → SIGNAL 事件（终端为主，视频接口为占位）
终端边缘识别 DSM/ADAS → 平台接收信号（演示由 POST /api/analysis/video 的 recognize 占位产生候选）→ evaluate_signal 匹配启用 SIGNAL 规则 → 冷却 → 同一 insert_risk_events 落事件建单；video_analysis 任务回写 SUCCESS。

汇合之后：风险预警分析页查询（按数据范围过滤）→ 坐席"去处理"ensure 工单 → 工单中心认领/分派/闭环（MOD-009）→ 通知中心推送（MOD-011）；事件同时供评分（MOD-010，FALSE_ALARM 闭环会被排除）与画像统计。

12 技术选型依据

  1. 规则配置与评估引擎分进程：配置面走 Java/MyBatis-Plus 事务与权限体系，评估面在数据接入最近的 Python 服务内执行，两者独立伸缩、独立故障域，靠 mon.risk_rule 表解耦。
  2. params 使用 jsonb：4 类规则参数结构不同且会演进，jsonb + JacksonTypeHandler 避免频繁加列；校验规则放在 Service 白名单内，保证 JSON 不会"配什么算什么"。
  3. 疲劳判定用 SQL LAG 窗口会话切分：连续驾驶本质是会话问题（gap 断档），窗口函数在库内完成排序与分段，比把全部历史点拉进应用层更省内存，也天然覆盖跨批历史。
  4. 冷却以事件表 MAX(event_time) 为权威：不在内存记冷却状态，处理服务重启后去重语义不变；一条 SQL 取多规则最近事件时间，开销低。
  5. 边缘信号与北斗点共用落库/建单函数：insert_risk_events 统一出口保证两类事件的工单、通知、评分行为完全一致。
  6. 视频识别做成可替换的占位：recognize 与 evaluate_signal 之间以 (channel,eventCode,confidence) 三元组为契约，终端真实信号接入后只换来源不改规则与事件结构（risk_engine.py docstring 已声明此演进意图）。

15 边界行为与常见问题

修改规则阈值后多久生效？
最长约 30 秒。Python 侧规则缓存 TTL（risk_cache_sec）到期后重新加载，无需重启；已经落库的历史事件等级/标题不回改。
可以自定义任意参数的规则吗？
不可以。只能在 4 种类型内按白名单键配阈值（speedKmh/continuousMin/gapMin/windowMin），参数键由评估代码硬编码读取；SIGNAL 规则事件码四选一。新规则类型需要开发。
一批点里多次超过 120，为什么只有一条事件？
SPEED 每批每车每规则只取批内最大速度点产 1 个候选，再经冷却去重；这是既定口径，事件次数因此偏保守，风险表 s13 已记录。
导入历史轨迹为什么没有超速/疲劳事件？
/api/ingest/load-sample 只批量 insert 轨迹，不调用 CEP；历史事件通过样例 driver_events.json 幂等导入，或由在线模拟器实时产生。
视频分析接口是真实 AI 识别吗？
不是。risk_engine.recognize 是按 task_id 字符和确定性派生事件码与固定置信度的占位实现，仅打通演示链路；真实 DSM/ADAS 以终端边缘上报信号为准，平台不做全量视频分析。
终端上报了信号为什么没有事件？
evaluate_signal 只在存在 status=1 且 valid_mark=1 的同事件码 SIGNAL 规则时才落事件；规则停用、事件码不在四选一范围内、或处于冷却窗口时均不落事件（视频任务 summary 会写明原因）。
停用或删除规则会影响历史事件吗？
不会。事件的 title、risk_level 是落库时的快照；内置规则 built_in=1 禁止删除（可停用），自定义规则为软删 valid_mark=0。
疲劳驾驶的 240 分钟如何计算？
仅统计 speed>0 的点，用 LAG 窗口按相邻点间隔 gapMin（默认 10 分钟）切分会话；回看 continuousMin+gapMin 分钟，会话连续驾驶 ≥240 分钟且末点仍在驾驶才命中；停车/掉线超 10 分钟视为中断。
COMBO 事件会不会和疲劳事件重复扣分？
驾驶评分按事件码分别计分：FATIGUE_DRIVE 与 COMBO_FATIGUE_SPEED 是两个白名单码，各自按当日 MAX(risk_level) 扣一次，组合事件确实叠加扣分，体现"最危险状态"的设计意图。
规则事件为什么一产生就有工单？
insert_risk_events 在同一数据库事务内插事件、按 risk_order_sla 算 deadline 建工单并写 CREATE 日志；uk_risk_order_event 唯一约束兜底，不会出现重复工单。
事件上的 confidence 有什么用？
北斗规则事件与围栏事件固定 1.00（确定性判定）；SIGNAL/视频占位事件保留终端或占位给出的置信度，仅作信息展示，不参与规则匹配、评分扣分或 SLA 计算。
media_url 存的是视频吗？
是按需调阅的截图/片段地址，随 SIGNAL 事件透传落库；平台不落地全量视频，地址来源依赖终端/对象存储侧（待核实）。
为什么有的事件在评分里找不到？
三种常见原因：事件码不在 8 个评分白名单内（如围栏事件）；工单被以 FALSE_ALARM 闭环（评分 NOT EXISTS 排除）；当天样本点不足 200 或驾驶不足 30 分钟（整天不评分，见 MOD-010）。

17 待核实项

以下条目在 2026-10-05 代码阅读中证据不足或依赖运行环境，按"待核实"标注：

  • 引擎可观测性：processing-service 仅有 GET /health 返回 UP，CEP 评估耗时、候选数、冷却拦截数、失败率均无指标暴露，生产监控方案待补。
  • 多实例下的冷却竞争：冷却以事件表 MAX(event_time) 为权威可跨实例正确去重，但同批并发下的事务隔离与重复候选行为未在多实例部署中验证（当前单实例）。
  • SIGNAL 真实终端协议：evaluate_signal 的入参契约已就绪，但终端边缘信号以何种报文/网关写入该入口、media_url 的对象存储来源，属接入侧待核实内容。
  • 历史重放工具：批量导入不跑 CEP，按时间轴离线重放轨迹补算事件的工具尚未提供，数据回填方案待确认。
  • risk_cache_sec 与 SLA 60 秒缓存的可配置性：两个 TTL 目前为 processing-service 配置/代码常量，未进入 sys_config 后台参数，运营侧是否需要可调待确认。
  • 事件量增长后的保留策略：risk_event 与 video_analysis 未见分区、归档或清理任务，长期在线运行后的表膨胀与查询性能需要容量规划结论。
  • SIGNAL 四码之外的国标码：评分/画像兜底事件名已预留 V_LDW/V_HMW/V_FCW/V_PCW、BEIDOU_SPEED 及国标数字码 1~7，但规则配置 UI 与 SIGNAL 匹配仍只开放四码，终端实际码表待对接确认。
