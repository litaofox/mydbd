MOD-DBD-012 系统配置与数据字典

文档编号 MOD-DBD-012|版本 v1.0.0|发布日期 2026-10-05| 状态 已上线|功能编号 F35（系统部分）

事实基准：2026-10-05 源代码（ConfigController / DictController 等）、09-system-config.sql、11-notify.sql 与前端 views/system/、composables/useDict.ts、constants/dict.ts

主要代码锚点：ConfigController / ConfigService / SysConfig、DictController / DictService / DictType / DictItem；前端 ConfigList.vue / DictList.vue / api/system.ts / useDict.ts

1 功能概述

1.1 模块定位

本模块是平台的基础数据与运行参数中心，由两组相互独立的能力组成，同处系统管理域但分属两个顶级菜单：

  • 数据字典（F35）：维护"类型（dict_type）+ 选项（dict_item）"两级枚举，如车牌颜色、终端状态、风险等级、事件码、工单状态等 11 个内置类型；业务页面的下拉框、标签、颜色统一从字典取，避免枚举散落在代码与 SQL 中。
  • 系统参数（F35）：以 key-value 维护运行期配置（密码策略、登录锁定、通知开关与弹窗级别等），支持 STRING / INT / BOOL / JSON 四种值类型，带内存缓存与类型校验，业务代码通过 ConfigService 按类型安全读取。

此外，"系统参数"页面上半区承载了测试数据与模拟器管理卡片（标准 / 稠密测试集加载、业务数据清空、实时轨迹模拟器开关与状态轮询），该卡片从实时监控页迁入，与参数 CRUD 同页共存（详见 3.3，验收时勿当成多余功能）。

1.3 术语与概念

术语含义
字典类型 DictTypetraj.sys_dict_type 一行：dict_code（唯一编码，如 risk_level）、dict_name（中文名）、status、remark。
字典项 DictItemtraj.sys_dict_item 一行：归属 dict_type_id、item_label（显示名）、item_value（存储值）、sort、status、css_class（标签样式名，如 danger）。
启用 / 停用字典类型与项均用 status=1/0；"删除"按钮执行的是 UPDATE status=0 而非物理删除，历史业务数据仍可按值反查标签。
系统参数 SysConfigtraj.sys_config 一行：config_key 唯一键、config_value 文本值、value_type（STRING/INT/BOOL/JSON）、is_system 是否内置锁定。
内置参数is_system=1 的种子参数（密码 / 登录 / SLA 比例共 5 个），可改值但不可删除；通知类 5 个参数 is_system=0。
内存缓存ConfigService 与 DictService 各持一个 ConcurrentHashMap 做进程内缓存；写操作主动 put / evict，无 TTL、不做定时刷新。
前端字典缓存useDict 的模块级 Map：同一 code 全局只请求一次；无 TTL，靠页面刷新 / 重新登录重新加载。
cssClass字典项上的样式标记（如 success / warning / danger），前端 tag 组件据此着色，而不是每页写死颜色映射。
测试数据卡片ConfigList.vue 上半区的调试功能集合（dataset 加载 / 清空 / simulator），与参数业务无关，生产环境需按角色收敛入口。

1.5 本期边界（不做什么）

  • 不做多级 / 树形字典：字典固定两级（类型 → 项），不支持项挂项；行政区划等树形基础数据不在本模块维护。
  • 不做字典项级权限：字典内容对所有登录用户一致，不按角色返回不同选项集合；数据权限仍由各业务模块自己控制。
  • 不做多节点缓存同步：缓存为各节点本地内存，依赖"写后主动刷新本节点 + 从节点通过各自请求触发 load / 重启"工作；不发缓存失效广播。
  • 不做参数热推送：参数改完更新缓存供后续读取，已持有旧值的长周期任务不会被强制中断或回调通知。
  • 不清理旧硬编码常量：constants/dict.ts 中设备形态等枚举仍被部分页面引用，本期不做全量替换（见第 13 节风险）。
  • 不提供历史版本 / 回滚：字典与参数只有当前值与 @AuditLog 审计记录，没有版本对比与一键回滚。

2 典型场景

系统管理员
新增一种风险事件中文名
设备侧新增了事件码，管理员在数据字典 risk_event_code 类型下新增选项（存储值=事件码、显示名=中文、样式=warning），刷新业务页后风险列表与画像构成直接显示中文标签，无需发版。
安全管理员
收紧登录密码策略
把内置参数 password.min_length 从 8 调到 10、login.max_fail 调到 5；保存即通过类型校验并刷新缓存，后续注册 / 修改密码立即按新策略执行。
值班管理员
调整通知打扰级别
夜间值班只想要高级别弹窗：把 notify.popup.min_level 保持 3；白天改为 1 允许所有级别弹窗。该参数非内置项，可在页面直接修改或停用。
开发 / 测试人员
加载测试集与开启模拟器
演示前在系统参数页上半区加载标准 / 稠密测试集、清空业务数据、打开实时轨迹模拟器；卡片每 2 秒轮询加载状态、每 5 秒刷新模拟器状态。
业务开发
代码里安全读配置
后端用 ConfigService.getInt/getBool/getJson 读取参数，键缺失或值非法时自动回落默认值并对 JSON 解析失败打 warn，业务逻辑不被脏配置击穿。
前端开发
下拉与标签统一来源
新页面用 useDict('order_status') 拿选项渲染下拉与 tag，value↔label 用 toMap 反查；不再为新枚举新增硬编码常量。

3 操作流程

3.1 数据字典双栏维护

入口：侧栏顶级菜单"数据字典"（DictList.vue，/system/dict）。页面为左右双栏布局。

左栏选类型
左栏宽 320px，字典类型表支持按名称 / 编码搜索与新增、编辑、停用；点击某行触发 el-table current-change。
右栏加载字典项
右栏按所选类型的 typeId 调 GET /types/{typeId}/items 加载选项（后端按 sort 升序），未选类型时右栏为空态。
类型弹窗
新增 / 编辑类型：编码（编辑时禁用输入，防止改码导致引用失联）、名称、状态 switch、备注；保存走 POST/PUT /types 并留审计。
字典项弹窗
显示名 itemLabel、存储值 itemValue、排序 el-input-number、状态、样式 cssClass（占位提示"如 danger"）、备注。
停用即删除
列表上的"删除 / 停用"操作把 status 置 0（类型与项相同语义），行从启用集合消失但数据仍在库中。

3.2 系统参数维护

入口：侧栏顶级菜单"系统参数"（ConfigList.vue，/system/config）。页面下半区才是参数 CRUD。

  • 查询：keyword 同时模糊匹配 config_name 与 config_key；列表按 create_date DESC 排列。
  • 新增 / 编辑弹窗：名称、键、值、类型下拉（STRING/INT/BOOL/JSON）、备注。BOOL 类型用 switch（active-value=true / inactive-value=false），JSON 类型用 textarea 多行编辑。
  • 保存时后端按 value_type 做校验（见 7.2）；config_key 重复拒绝（"参数键已存在"）；is_system=1 的内置行不显示删除按钮，后端删除接口也会拒绝（"内置参数不可删除"）。
  • 新增 / 编辑按钮受 system:config:edit（923）控制（v-perm）；role2 只读。

3.3 测试数据与模拟器卡片

ConfigList.vue 页面上半部分是"测试数据与模拟器"卡片，下半部分才是系统参数。两块同页是既有实现（卡片从实时监控页迁入），不是页面放错。

功能调用行为
标准测试集加载@/api/traj datasetLoad（标准集）灌入演示用车辆 / 终端 / 司机 / 绑定等基础数据
稠密测试集加载datasetLoad（稠密集）灌入更大密度数据用于地图 / 性能演示
清空业务数据datasetClear清空演示业务数据（高危操作，按按钮二次确认）
模拟器启停simulatorStart / simulatorStop开关实时轨迹模拟推送
状态轮询datasetStatus / simulatorStatus加载中每 2 秒轮询进度；模拟器状态每 5 秒定时刷新

生产部署应通过菜单 / 按钮权限收敛该卡片可见性；后端数据集接口不属于本模块（在 traj / 监控相关接口中），本页只是承载入口。

3.4 业务侧消费字典与参数

  • 前端字典：业务页调 useDict(code) 得到 {items, toMap}；下拉渲染 items，标签着色用 cssClass，存量数据 value 反查中文名用 toMap。首次请求后缓存于模块级 Map。
  • 前端参数：个别页面可经 getConfigValue(key, default) 读参数（如通知设置由通知模块自己调）；不提供全量参数订阅。
  • 后端参数：ConfigService.getValue/getInt/getBool/getJson 为统一入口，缺省值由调用方给出，解析失败回落默认（JSON 失败额外 log.warn）。
  • 后端字典：需要中文名的服务（如画像 eventName）通过 DictService.getItemsByCode 读取，类型或项被停用则查不到，走调用方兜底。

5 用户价值

11 类
内置字典类型覆盖车 / 终端 / 司机 / 风险 / 工单全链路枚举
4 种
参数值类型 STRING / INT / BOOL / JSON，写入即校验
0 发版
新增枚举选项、调整运行参数不需要重新发布应用
双缓存
后端 ConcurrentHashMap + 前端模块 Map，读路径基本零 SQL
  • 枚举一处维护、处处生效：标签中文名、颜色、排序统一在字典中心，业务页不再各写各的映射。

  • 演示效率：测试数据与模拟器同页管理，交付演示与联调造数无需 SQL 脚本。

6.1 前端实现要点

  • api/system.ts：字典 7 个函数（类型分页 / 增改删、按类型查项、项增改删、按 code 查启用项、全量字典 Map）；参数 5 个函数（分页、增、改、删、按键取值）。

  • cssClass 为纯文本输入（占位"如 danger"），样式名由前端 Element 标签类型白名单解释，不接受任意 CSS / HTML，无样式注入风险。
  • ConfigList BOOL 类型 switch 绑定 active-value="true" / inactive-value="false"，提交字符串与后端 Boolean.parseBoolean 对齐；JSON textarea 不做前端格式化，校验以后端 readTree 为准。
  • 测试数据卡片轮询定时器在组件卸载时清理；模拟器状态与数据集状态分别独立轮询（2s / 5s）。

7 核心实现逻辑

7.1 系统参数读写与缓存

  • 缓存：ConcurrentHashMap<String,String> valueCache，键为 configKey。getValue(key, defaultValue) 使用 computeIfAbsent：未缓存时查库，库里也没有则回退调用方传入的 defaultValue。
  • 写后维护：add（校验唯一 + validate 后 insert 并 put 缓存，isSystem 缺省 0）、update（更新后 put 新值）、delete（仅非内置，删除后 remove）。缓存无 TTL，一致性完全由写操作主动维护。
  • 类型访问器：getInt 用 parseInt，失败回落默认值；getBool 用 Boolean.parseBoolean；getJson 用 ObjectMapper.readValue 反序列化目标类型，失败回落默认并 log.warn，且 getJson 不把失败结果放入缓存（避免缓存坏对象）。
  • 按键开放接口 GET /value/{key}?defaultValue= 注释为"业务读取参数值（登录即可）"，但类级 system:config:view 注解仍然生效——实际门槛是登录 + 拥有 view 权限，不是任意登录用户，调用方鉴权设计需注意（见待核实项）。

7.2 参数值类型与校验

value_typevalidate 规则读取

7.3 字典类型管理

  • 分页 GET /types 的 keyword 同时模糊 dict_name 与 dict_code；新增类型编码唯一（数据库 uk_dict_type_code 兜底），status 默认 1。
  • updateType：若 dictCode 发生变化，同时清旧码与新码两个缓存键，防止旧编码缓存残留。
  • deleteType：不是物理删除，而是 UPDATE status=0；停用后 getItemsByCode 因类型 status≠1 不再返回任何项，等于"整类下线"。
  • 字典项表对类型有外键 FK ON DELETE CASCADE——它为物理删除场景准备级联清理，但当前业务路径只用停用，不会触发级联删项。

7.4 字典项管理与缓存

  • ConcurrentHashMap<String,List<DictItem>> itemCache，键为 dictCode。新增项默认 status=1、sort=0，插入后 evictByType 清缓存。
  • updateItem / deleteItem 同样清该类型缓存；删除项也是 UPDATE status=0，不物理删。
  • 唯一约束 uk_dict_item_type_value UNIQUE(dict_type_id,item_value)：同一类型下存储值不可重复；idx_dict_item_type 支撑按类型取列表。
  • 后台项列表 GET /types/{typeId}/items 按 sort 升序返回全部项（含停用，供右栏管理）；开放接口只返回启用项（见 7.5）。

7.5 对外字典查询

  • GET /items/{dictCode}：开放给业务页面的取项接口，只返回类型启用（status=1）且项启用（status=1）的选项，按 sort 升序。
  • getItemsByCode 走 computeIfAbsent 懒加载：类型停用或不存在时返回空集（空结果也会缓存，避免缓存穿透反复打库）。
  • GET /all：getAllDictMap 先查全部启用类型，再逐个走 getItemsByCode 缓存，返回 Map<code, List<DictItem>>，供前端一次性预热或公共布局渲染多个枚举。

7.6 前端 useDict 缓存

  • composables/useDict.ts 在模块作用域维护 Map<code, items>（dictCache），全局无 TTL；同一 code 第一次被业务页使用时请求 getDictItemsByCode，之后所有页面共享结果。
  • 返回 { items, toMap }：toMap 把 itemValue → itemLabel 建成反查表，供表格里只存值的场景显示中文名。
  • 失败可重试：请求失败时会 delete 占位（不缓存失败态），下次调用重新请求；成功后常驻，直到刷新页面 / 重新登录。
  • 这意味着管理员在字典页改了选项后，已打开的其他标签页不会实时刷新，需要重新进页面；这是无 TTL 设计的已知取舍（见第 13 节）。

7.7 内置参数与受保护数据

  • 删除拦截：ConfigService.delete 先查记录，is_system=1 直接拒绝（"内置参数不可删除"），不执行 DELETE；前端对内置行也不渲染删除按钮，前后端双保险。
  • 内置参数可修改值（例如调整密码长度），修改同样经过类型校验与审计；不可改的是"存在性"而非"取值"。
  • 通知类 5 个参数 is_system=0，属于"种子提供但可运维"的普通参数，允许编辑与删除（删除后通知模块回落到代码默认值）。
  • 字典侧无 is_system 标记，11 个内置字典类型理论上可停用；停用影响面大（所有引用该 code 的页面 / 服务显示受影响），靠编辑权限 system:dict:edit 与审计约束。

8 数据流程

管理写流程：管理员在 DictList / ConfigList 提交 → Controller 校验 view + edit 权限 → Service 做唯一约束与值类型校验 → 写库 → 主动 put / evict 进程内缓存 → @AuditLog 留痕。字典停用更新 status，不物理删。

业务读流程（后端）：ConfigService.getXxx / DictService.getItemsByCode → 先查本地 ConcurrentHashMap（computeIfAbsent）→ 未命中查库并缓存 → 类型 / 键不存在或缺省 / 解析失败时回落调用方默认值。

业务读流程（前端）：useDict(code) → 查模块级 dictCache → 未命中请求 GET /api/system/dict/items/{code} → 缓存 items 并返回 toMap；失败删除占位允许重试。

8.1 异常与降级路径

异常情形系统行为
参数键不存在getValue/getInt/getBool/getJson 全部回落调用方 defaultValue；不抛异常
INT 值被改成非整数写入侧 INT 校验直接拒绝；历史脏值读取时 getInt 回落默认
JSON 值非法写入侧 readTree 拒绝；读取侧 readValue 失败回落默认 + log.warn，不缓存坏对象

8.2 冷启动与缓存预热行为

  • 后端启动不预热：valueCache / itemCache 初始为空，所有键都靠第一次请求 computeIfAbsent 加载；重启后第一批请求略慢（一次主键 / 索引查询），随后回到内存读。
  • 空结果也缓存：字典类型停用、code 不存在时缓存空列表，防止不存在的 code 被高频调用时反复打库（缓存穿透）；写入 / 启用操作会主动 evict 对应键使下次重新加载。
  • /all 不额外建缓存结构：全量查询逐 code 复用 getItemsByCode，结果不单独保存；它的价值是把多个懒加载一次填满。
  • 前端首屏：使用 useDict 的第一个页面触发请求；MainLayout 不做全局预拉，避免登录后一次性请求全部字典；需要预热的公共布局可显式调 /all。
  • 刷新即"手动清缓存"：前端无 TTL 也无推送失效，浏览器刷新 / 重登是当前唯一的重新加载入口；后端重启是服务端缓存清空的唯一时机。

12 技术选型依据

  1. 字典两级模型足够覆盖业务：车 / 终端 / 司机 / 风险 / 工单的枚举全是"一类 + 平级选项"，不引入三级或树形，换取 UI 双栏与 SQL 的极简实现。
  2. 停用代替删除：风险表、工单表大量历史行只存枚举值（字符串 / 数字码），物理删除字典项会导致历史数据无法回显；status=0 既隐藏选项又保留可追溯性。
  3. 数据库唯一约束前置：类型编码、(类型,项值) 在数据库层加 uk，服务端校验只是体验优化；并发新增也不会产生重复枚举。
  4. 参数带类型而非全当字符串：INT / BOOL / JSON 写入即校验，把配置错误拦在保存时；读取侧再用带默认值的访问器兜底，形成双保险。
  5. ConcurrentHashMap 本地缓存：字典与参数都是极热点、极低变更率数据，单节点部署下本地缓存零序列化、零网络开销，写操作主动维护即可接受。
  6. 前端模块级 Map 无 TTL：枚举在一次登录会话内视为不变量，避免每个下拉都发请求；代价是改字典后需刷新页面，在管理后台场景可接受。

必须知晓的双轨枚举现状：09 脚本字典是"统一来源方向"，但 constants/dict.ts 里的旧硬编码枚举（PLATE_COLORS 字符串数组、设备形态数字码、labelOf / tagOf 工具）仍被存量页面使用，且两套取值并不等价（如设备类型：旧为 1/2/4 数字形态，字典为 GNSS/DSM/ADAS/ALL_IN_ONE）。任何"对齐"工作都必须逐页确认存储值含义，不能简单替换。

15 边界行为与常见问题

数据字典菜单为什么在"系统管理"折叠组里找不到？
它本来就不在 900 组内。920 数据字典与 921 系统参数都是 parent=0 的顶级单菜单，直接显示在侧栏；09 脚本注释"parent_id=0 即根菜单"的表述容易误导，以实际菜单层级为准。
字典项点了删除，历史数据还能显示中文吗？
能。删除是停用（status=0），行仍在库；管理列表可见停用项，开放查询不再返回该选项（新数据不可选），历史值反查依赖缓存 / 库内仍存在的行，必要时可重新启用。
为什么修改字典类型编码时输入框是灰的？
编辑态故意禁用 dictCode：编码是缓存键与所有前端 useDict(code) 的引用键，改码会让存量页面取不到字典。确需改码要在代码与种子中同步迁移。
参数保存 INT 报非法怎么办？
该键 value_type=INT 时值必须是整数字符串；小数、带单位文本都会被校验拒绝。若业务需要存"0.2"这类比例，应使用 STRING 并由消费方自行解析（sla.grace_ratio 就是 STRING）。
内置参数为什么删不掉？
is_system=1 的 5 个参数（密码 / 登录策略 / SLA 比例）前端不显示删除、后端拒绝删除；只能改值。这是防止登录与密码策略失效的保护。
改了字典为什么别人页面没变化？
前端 useDict 是无 TTL 的模块级缓存，已打开的会话不会自动刷新；后端缓存会随保存立即更新，新登录 / 刷新页面后看到新值。
设备类型在字典里是英文码，为什么有些页面显示"一体机/分体机"？
那是 constants/dict.ts 旧硬编码枚举（数字形态码）的页面，尚未迁移到字典中心。两套定义暂存，迁移完成前以各页实际代码为准（见第 13 节）。
系统参数页上面的"清空业务数据"是干什么的？
测试 / 演示工具：加载标准或稠密测试集、清空演示数据、开关轨迹模拟器。生产环境应通过权限隐藏，避免误操作。
getJson 读参数时配错会导致启动失败吗？
不会。读取时反序列化失败会回落调用方提供的默认值并打 warn 日志，不缓存坏结果；但写入时坏 JSON 会被直接拒绝保存。
role2 角色能改参数 / 字典吗？
不能。role2 只有 920 / 921 的 view 只读权限；新增 / 编辑 / 停用按钮（922/923、system:*:edit）仅 role1 等管理角色拥有。
字典项的 cssClass 随便写会有样式注入风险吗？
没有。cssClass 只是被 Element 标签类型逻辑选择使用的样式名字符串（白名单解释），不会作为 CSS / HTML 输出执行；未知样式名表现为默认样式。
服务重启后字典 / 参数会丢吗？
不会。内存缓存只是查询加速，真相在 traj.sys_config 与字典表里；重启清空的只是缓存，首次访问重新加载。
11 个内置字典和通知模块的字典是什么关系？
09 脚本先建 11 个基础类型；11-notify.sql 再补 notify_event_type（通知事件 5 项）与 5 个通知参数。它们同在字典 / 参数中心维护，通知页只是消费方。
停用的字典项要重新启用怎么做？
在右栏字典项管理表中找到 status=0 的行（管理接口返回含停用项），编辑把状态切回启用并保存，evict 缓存后开放查询立即恢复该选项。

17 待核实项

下列条目在本期代码 / 脚本中未能闭环确认：

  • sla.grace_ratio 消费方缺失：09 种子备注"工单剩余时限低于该比例视为临期"，但工单代码临期判断使用写死的 ×0.2 字面量，未检索到读取该 config 的代码；需确认是应接线读取参数，还是删除 / 修正参数说明。
  • /value/{key} 鉴权口径：方法注释"业务读取参数值（登录即可）"与类级 system:config:view 冲突；需确认期望是登录可读还是必须有 view，必要时拆分为独立端点。
  • 旧枚举迁移计划：constants/dict.ts 设备形态（1/2/4）、PLATE_COLORS 等与字典种子不等价，迁移批次、存储值映射、历史数据兼容方案未定。
  • 内置字典保护：字典类型 / 项无 is_system 标记，误停用 risk_level 等核心类型只靠权限与审计；是否加内置锁定待定。
  • 多节点缓存：前后端缓存均无失效广播；多实例部署的一致性方案与字典前端刷新机制（版本号 / 手动刷新）待设计。
  • sys_file 预留用途：09 脚本已建文件元数据表但暂无业务读写，归属模块与上传 / 鉴权方案待明确。
