MOD-DBD-009 处置工单与坐席干预

文档编号 MOD-DBD-009|版本 v1.0.0|发布日期 2026-10-05| 状态 已上线|功能编号 F20（工单流转）/ F21（坐席干预）

事实基准：2026-10-05 源代码（module-risk）与 08-work-order.sql、10-risk-intervention.sql

主要代码锚点：RiskOrderController / RiskOrderService / InterventionService / RiskOrderScheduler；实体 RiskWorkOrder / RiskIntervention；前端 risk/RiskOrders.vue / OrderDetailDrawer.vue

1 功能概述

1.1 模块定位

处置工单模块把 MOD-008 产生的每一条风险事件纳入可分派、有时限、可追溯的人工处置流程：风险事件自动建单 → 坐席认领或主管分派 → 电话提醒/安全教育等干预动作留痕 → 按规定闭环结果归档 → 超时自动标记并升级督办。工单与风险事件为 1:1 关系（唯一约束 uk_risk_order_event）。

模块同时提供 F21 坐席干预记录：手动登记电话提醒、安全教育、停运通知、处罚等动作及结果；闭环时系统可按闭环结果自动补一条 SYSTEM 来源干预记录，保证"闭环必有干预"。

1.2 功能清单与状态

1.3 术语与概念

术语含义
三态状态机工单仅 PENDING（待处理）/ PROCESSING（处理中）/ CLOSED（已闭环）三态；认领与分派 PENDING→PROCESSING，闭环 →CLOSED，重开 CLOSED→PROCESSING。
负责人 assigneeId当前持单人。认领取当前登录用户；分派/转派由主管指定；负责人为空的 PENDING 单可被有权坐席抢单。
SLA 时限 / 宽限期deadline = 事件时间 + 处置时限（高 15 / 中 60 / 低 240 分钟）；宽限期在时限之上再加（10/30/60 分钟）。过 deadline 标超时，过宽限才升级督办。
超时 / 升级调度器每 60 秒扫描：now>deadline 置 overdue=1；now>deadline+grace 且未升级过则 escalate=1 并发 ORDER_ESCALATE（level=3）通知负责人与主管。
闭环结果 closeResult代码白名单 VALID_RESULTS 五种：PHONE_REMIND（电话提醒）/ EDUCATION（安全教育）/ REPORT_PENALTY（上报处罚）/ TRAFFIC_VIOLATION（交通违法处置）/ FALSE_ALARM（误报排除）；误报闭环不补干预、且被评分排除。注意 SQL 注释中的 SUSPEND/OTHER 不在白名单。
重开 reopen主管对 CLOSED 单执行 reopen 回到 PROCESSING，写 REOPEN 日志；重开不重建事件关联。
干预记录 intervention5 类动作（电话提醒/安全教育/到场处置/停运通知/行政处罚等）× 4 类结果的留痕；来源 MANUAL（强制当前操作人）或 SYSTEM（闭环自动补录）。
ensureOrder风险事件页"去处理"调用的幂等补单：有单返回既有单、无单补建 PENDING；uk_risk_order_event 与 DuplicateKeyException 兜底。
新单 id 游标调度器记录上次扫描到的最大工单 id，只向通知模块投递增量新单，重启后从库内 MAX(id) 续游标，不重复通知。

2 典型场景

调度监控员
抢单式认领处置
高风险事件自动建单后，持"工单处置"权限的在线坐席收到新单通知，列表点"快捷认领"即成为负责人，在剩余时限内电话提醒司机后闭环。
安全管理员（主管）
分派与超时督办
主管在可分派名单中把单分派给指定坐席；工单超处置时限后自动标超时、超宽限期自动升级，主管与负责人收到 ORDER_ESCALATE 高优先级通知。
车队长
车队内事件闭环
车队长角色可查看与处置本车队工单，执行"安全教育"闭环并登记干预记录；只能看到数据范围内车辆产生的工单。
安全管理员
误报排除
确认事件为设备误报时以"误报排除"闭环并写明依据；该事件会被驾驶评分自动剔除，不影响司机当日分数（MOD-010）。
坐席/主管
闭环不合规被退回
闭环说明不足 10 字或未选闭环结果时前端拦截；闭环后发现处置不实，主管可"重新打开"，工单回到处理中继续走流程。

3.2 认领 / 分派 / 转派

动作入口前置条件结果
认领 claim列表"快捷认领"/详情按钮非 CLOSED；未分派给他人（他人已领须先转派）→ PROCESSING，负责人=当前人，写 CLAIM 日志
分派 assign详情"分派"，负责人下拉（assignable-users）非 CLOSED；目标人在可分派名单内；需 risk:order:assign→ PROCESSING，写 ASSIGN（from/to），向目标人发 ORDER_ASSIGN 通知
转派 transfer详情"转派"非 CLOSED；工单已有负责人→ PROCESSING，写 TRANSFER + ORDER_ASSIGN 通知新负责人

3.3 闭环与重开

选择闭环结果
5 选 1：电话提醒 PHONE_REMIND / 安全教育 EDUCATION / 通报处罚 REPORT_PENALTY / 交通违法 TRAFFIC_VIOLATION / 误报排除 FALSE_ALARM。
填写处置说明
CloseRequest.remark 必填，长度 10~255 字。
权限校验
仅负责人本人或持有 risk:order:assign（主管）可闭环。
重开 reopen
仅 CLOSED 可重开（需 assign 权限）：有负责人→PROCESSING，无负责人→PENDING；清空 close* 字段、reopen_count+1、事件回置未处置。

3.4 干预记录登记

详情抽屉"干预记录"区可手动新增（POST /api/risk/orders/interventions，权限 risk:order:handle，挂 @AuditLog HANDLE INTERVENTION）：

  • 动作 5 项：PHONE_REMIND 电话提醒 / EDUCATION 安全教育 / STOP 停运通知 / PENALTY 处罚 / OTHER 其他；
  • 结果 4 项：SUCCESS 成功 / FAILED 失败 / NO_ANSWER 未接通 / PENDING 待跟进（默认 SUCCESS）；
  • 手动登记的 operator 强制取当前登录人、source=MANUAL。

3.5 SLA 配置

列表页"SLA 配置"弹窗（v-perm risk:order:assign）同时编辑三个等级的处置时限与升级宽限：高 15/10、中 60/30、低 240/60（分钟）。后端 PUT /api/risk/orders/sla 要求三个等级一起提交，limitMin 1~10080、graceMin 0~1440；调整只对之后新建的工单生效，存量单 deadline 不变。

3.6 从风险事件跳工单

风险预警分析页点"去处理"：先 POST /api/risk/orders/ensure/{eventId}（无单则按事件等级查 SLA 当场补建 PENDING 单），再打开详情抽屉。消息中心点击工单消息则跳 /risk/orders?openOrder=<bizId>。

7 核心实现逻辑

7.1 工单三态状态机

RiskOrderService 常量 PENDING / PROCESSING / CLOSED，严格三态、无第四态。允许的迁移与守卫：

迁移触发动作守卫条件副作用
— → PENDING自动建单 / ensure / 存量补单event_id 唯一（uk_risk_order_event 兜底）写 CREATE 日志（operator=CEP/SYSTEM）
PENDING → PROCESSINGclaim 认领未分派给他人；CLOSED 拒绝claim_time、assignee=当前人；CLAIM 日志
PENDING/PROCESSING → PROCESSINGassign 分派非 CLOSED；目标人 ∈ assignable-users；需 assign 权限assign_time；ASSIGN 日志（from/to）；发 ORDER_ASSIGN
PROCESSING → PROCESSINGtransfer 转派非 CLOSED 且已有负责人TRANSFER 日志；向新负责人发 ORDER_ASSIGN
PENDING/PROCESSING → CLOSEDclose 闭环结果 ∈ 5 种白名单；remark 10~255 字；本人负责人或持 assignclose_time/result/remark；回写事件已处置；自动补干预；非本人闭环通知负责人
CLOSED → PROCESSING/PENDINGreopen 重开仅 CLOSED；需 assign 权限清 close*；reopen_count+1；事件回置未处置

旧注释与实际代码不一致（以 RiskOrderService.VALID_RESULTS 为准）：risk_work_order.close_result 的 SQL 列注释与实体注释写的是 "PHONE_REMIND/EDUCATION/SUSPEND/FALSE_ALARM/OTHER"，但实际闭环白名单为 PHONE_REMIND / EDUCATION / REPORT_PENALTY / TRAFFIC_VIOLATION / FALSE_ALARM，没有 SUSPEND/OTHER；前端闭环单选项与代码一致。SUSPEND（停运）语义存在于干预动作 action_type 的 STOP，而不是闭环结果。

7.2 自动建单与 ensure

  • 在线自动建单：Python db.insert_risk_events 插入事件后，读 mon.risk_order_sla（60 秒进程缓存），同事务 INSERT 工单：order_no=mon.fmt_order_no()、status=PENDING、deadline=event_time+limit_min、creator='cep-engine'，并写 CREATE 日志（operator='CEP'，remark='风险事件自动建单'）。
  • 工单号：序列 mon.seq_risk_order_no + 函数 mon.fmt_order_no() = 'WO' + yyyyMMdd + lpad(seq%1000000, 6, '0')。
  • ensure 补建：POST /api/risk/orders/ensure/{eventId} 无单时按事件等级查 SLA 补建；并发下唯一约束抛 DuplicateKeyException 时返回已存在工单，不报错。
  • 存量补单：08 脚本 §8.5 对全部 handle_status=0 的历史事件幂等补单（ON CONFLICT(event_id) DO NOTHING），并补 CREATE 日志（operator_name='SYSTEM'）；已处置历史事件不补。

7.3 SLA 时限口径

mon.risk_order_sla 以 risk_level 为主键，种子值：

风险等级处置时限 limit_min升级宽限 grace_min
3 高15 分钟10 分钟
2 中60 分钟30 分钟
1 低240 分钟60 分钟

列表 SQL 中三档时限标签的实时口径（以当前时间 now 计算，仅针对未闭环单）：

  • due（临期）：deadline 落在 [now, now + sla_limit_min×0.2] 区间，即剩余时限不足总时限的 20%；
  • overdue（超时）：deadline < now；
  • escalated（已升级）：deadline + grace_min < now（同时被调度器置 escalated=1、写 escalate_time）。

7.4 超时扫描与升级通知

RiskOrderScheduler.scan() 每 60 秒（启动后 20 秒首跑）先执行 runTimeoutScan()：

批量置超时/升级
markOverdue / markEscalated 两条批量 UPDATE，按 deadline 与 grace_min 刷新 overdue、escalated、escalate_time。
找新升级单
selectNewlyEscalated：近 2 分钟内升级、且尚无 ESCALATE 日志的工单，limit 200。
补升级日志
insertEscalateLogs：action='ESCALATE'，operator_name='SYSTEM'（日志去重保证重启不重复通知）。
派发升级通知
通知对象 = 工单负责人 + receiversByMenu(916) 主管名单；NotifyEvent 等级 3（ORDER_ESCALATE，见 MOD-011）。

7.5 新单通知与 id 游标

超时扫描后执行 scanNewOrders()：内存维护 lastNotifiedOrderId 游标，@PostConstruct/启动时初始化为当前 MAX(id)，不回放历史；之后每批 50 个新单，向全部持菜单 915 权限的在线坐席派发 ORDER_CREATE 通知。增量推送用 id 游标而非时间窗口，调度抖动既不丢也不重。

7.6 闭环校验与事件回写

  1. 校验：状态非 CLOSED；closeResult ∈ {PHONE_REMIND, EDUCATION, REPORT_PENALTY, TRAFFIC_VIOLATION, FALSE_ALARM}；remark 10~255 字；操作人是负责人本人或持 risk:order:assign；
  2. 更新工单：status=CLOSED、close_time=now、close_result、close_remark（事件快照字段不动）；
  3. 回写 mon.risk_event：handle_status=1、handle_remark="闭环结果中文名：remark"（截断 255）；
  4. InterventionService.autoFromClose 自动补一条 SYSTEM 干预：FALSE_ALARM 不生成；PHONE_REMIND→PHONE_REMIND、EDUCATION→EDUCATION、REPORT_PENALTY/TRAFFIC_VIOLATION→PENALTY；
  5. 若非负责人本人闭环，向原负责人发 ORDER_CLOSE 通知。

7.7 干预动作与自动补录

mon.risk_intervention：action_type ∈ PHONE_REMIND / EDUCATION / STOP / PENALTY / OTHER；action_result ∈ SUCCESS / FAILED / NO_ANSWER / PENDING（默认 SUCCESS）；source ∈ MANUAL / SYSTEM。手动新增经 InterventionService.add：operator_id/name 强制取 UserContext 当前人，source=MANUAL。干预与工单多对一（一单可多条干预），order_id/event_id/plate_no/identity_code 冗余便于统计。

7.8 可分派名单与权限

selectAssignableUsers = 启用用户 ∩ 启用角色 ∩（role id=1 超级管理员 或 角色拥有菜单 915）。端点 GET /api/risk/orders/assignable-users 供分派下拉。角色授权种子：role1 全量；role2 安全管理员 view+handle+assign；role3 调度监控员、role4 车队长 view+handle（无分派/重开/SLA 权限）。列表查询还会按当前人数据范围（deptScope → 可见车牌集）过滤，越权访问他人工单详情返回 40401（fail-closed）。

7.9 统计卡与漏斗口径

OrderStatsVO：pendingCount、processingCount、overdueCount、escalatedCount、closedTodayCount、avgCloseSeconds、avgCloseMinutes。selectStats 全部实时按 deadline 计算；平均闭环时长仅统计今日 CLOSED 单的 EXTRACT(EPOCH FROM close_time - create_date)。

OrderFunnelVO（RiskOrderService.funnel，区间 [start,end)）：

  • eventTotal = risk_event 按 create_date 落区间计数；
  • orderTotal = 工单按 create_date 落区间；closedTotal 同样按工单 create_date（CLOSED 状态）；
  • interventionTotal = InterventionService.countIntervenedOrders：区间内创建且存在干预记录的 distinct order_id；
  • 率 = ×1000 / orderTotal / 10.0 保留 1 位小数；orderTotal=0 时率为 0。

口径差异（风险提示）：本漏斗 closedTotal 按工单 create_date 统计；MOD-010 画像对象卡 ProfileOrderMapper.closedTotal 按 close_time 落在区间统计。同一时间窗两个页面的"闭环数"可能不同，比较数据时须先对齐口径。

11 定时任务

任务调度方式行为
RiskOrderScheduler.scan@Scheduled(fixedDelay=60_000, initialDelay=20_000)（每 60 秒，启动后 20 秒首跑；fixedDelay 非 cron）runTimeoutScan（置超时/升级、补 ESCALATE 日志、通知负责人+916 主管）→ scanNewOrders（id 游标每批 50 新单，通知 915 在线坐席）

12 技术选型依据

  1. 事件与工单 1:1 且同事务创建：风险处置不允许"无主事件"，uk_risk_order_event 从数据库层杜绝重复单；ensure 接口用 DuplicateKeyException 兜底并发点击。
  2. 三态极简状态机：PENDING/PROCESSING/CLOSED 覆盖运输安全处置实际流程，迁移规则全部集中在 Service 常量与守卫方法中，避免状态膨胀。
  3. SLA 快照入单：sla_limit_min/grace_min/deadline 在建单时写入工单行，后续 SLA 调整不改历史单，考核口径可重现。
  4. 扫描器只做幂等批量更新：超时标记用 SQL 集合更新，通知通过"近 2 分钟新升级 + 无 ESCALATE 日志"去重，单实例重启/漏跑后下一节拍自动补齐且不重复通知。
  5. 新单用 id 游标而非时间窗：lastNotifiedOrderId 初始化为 MAX(id)，重启不回放历史，调度抖动不丢不重（项目既有避坑经验）。
  6. 通知异步且失败隔离：调度器只负责"找人+发事件"，NotifyService 异步派发全程吞异常，通知故障不影响工单状态正确性（见 MOD-011）。

15 边界行为与常见问题

谁可以认领、谁可以闭环？
持有 risk:order:handle 的角色（role1 全部、role2 三项权限、role3/role4 view+handle）可认领；闭环限负责人本人或有 assign 权限者；数据范围外车辆的单不可见，详情直调返回 40401。
"超时"和"升级"是一回事吗？
不是。now>deadline 仅置 overdue=1（列表标红）；now>deadline+grace_min 且未升级过才置 escalate=1 并向负责人与主管发一次 ORDER_ESCALATE 高优先级通知。
调整 SLA 后，存量工单时限会变吗？
不会。limit_min/grace_min/deadline 在建单时快照写入工单行；SLA 配置页也注明"仅对新单生效"。
闭环时为什么要求填写说明？
必须选择闭环结果且说明长度 10~255 字，前端与后端双重校验；目的是保证每条闭环可审计、可回溯教育/提醒内容。
"误报排除"闭环与其他结果有何不同？
FALSE_ALARM 闭环：回写事件已处置但不自动补录 SYSTEM 干预记录；且次日驾驶评分 NOT EXISTS 排除该事件，不扣分。
闭环后发现处置不实怎么办？
有 risk:order:assign 权限的主管可"重新打开"，工单回到 PROCESSING 并写 REOPEN 日志；事件关联不变，之后可再次闭环。
事件页点"去处理"为什么有时直接打开了已有工单？
ensure/{eventId} 是幂等的：工单已存在直接返回既有单（含并发点击被唯一约束拒绝后回查）；不存在才补建 PENDING 单。
工单可以删除吗？
不提供删除接口。工单是处置审计对象，只能沿状态机流转；三态之外没有作废/物理删除路径。
新单铃铛为什么没收到通知？
ORDER_CREATE 只投给拥有 915 处置权限的启用用户；WebSocket 不在线时站内信仍落库（铃铛未读数可见），但弹窗需要在线会话；外部短信/语音/App 通道本期为预留，不会真实外发（MOD-011）。
手动登记干预能代他人登记吗？
不能。MANUAL 来源的 operatorId/operatorName 强制取当前登录用户，请求体传他人 id 无效；只有 SYSTEM 自动补录的来源是系统。
工单漏斗和画像页闭环数为什么对不上？
时基不同：工单漏斗闭环按 create_date 区间（建单时间在窗口内），画像对象卡 closedTotal 按 close_time 区间（闭环动作发生在窗口内）。跨页对账需先统一时基。
分派后还能改派吗？
可以。持单坐席或主管可转派（transfer），写 TRANSFER 日志并向新负责人发 ORDER_ASSIGN；转派不改变 deadline 与超时状态。
