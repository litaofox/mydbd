MOD-DBD-011 通知中心与多渠道预警

文档编号 MOD-DBD-011|版本 v1.0.0|发布日期 2026-10-05| 状态 站内信 / WebSocket 已上线 短信 / 语音 / App 推送仅预留|功能编号 F19 / F35

事实基准：2026-10-05 源代码（module-notify + module-monitor 推送实现）与 11-notify.sql、09-system-config.sql

主要代码锚点：NotifyController / NotifyService / NotifyMessage / NotifySendLog / NotifyEvent / NotifyAsyncConfig / SmsChannel / VoiceChannel / PushChannel；前端 views/system/MessageCenter.vue、composables/useNotify.ts、api/notify.ts

1 功能概述

1.1 模块定位

通知中心把风险工单域的关键业务动作（工单生成、分派、超时升级、闭环）转化为面向具体坐席 / 管理员的个人消息，并负责消息的在线实时提醒。后端包 com.mydbd.notify（NotifyController 基址 /api/notify），包含两个真实通道：

  • 站内信：逐接收人写入 traj.sys_message（msgType='INBOX'），在消息中心页面持久化展示，支持未读筛选、单条已读、全部已读、删除。
  • WebSocket 实时弹窗：在线用户立即收到推送，浏览器右下角弹出 ElNotification、可发声、可调系统通知，点击直达工单。

短信、语音外呼、App 推送三个外部通道本期只有接口、开关与"发送意图"日志，任何情况下都不会真实外发（详见 7.6），请勿在交付材料中描述为"已支持短信预警"。

安全模型一句话：NotifyController 没有类级权限码，登录即可调用；但每个接口都强制用当前登录人 currentUserId 过滤 / 校验，A 永远读不到、改不了、删不掉 B 的消息（越权访问他人消息统一返回 404"消息不存在"，不暴露消息是否存在）。

1.3 术语与概念

术语含义
通知事件 NotifyEventrecord 形式的内部消息载体：eventType、bizType、bizId、title、content、level、orderNo、plateNo；由工单域构造后交给 NotifyService。
事件类型 eventTypeORDER_CREATE（工单生成）/ ORDER_ASSIGN（工单分派）/ ORDER_ESCALATE（超时升级）/ ORDER_CLOSE（工单闭环）/ SYSTEM（系统通知），字典 notify_event_type 同步维护中文名。
业务类型 bizType本期固定 BIZ_WORK_ORDER；前端据此决定点击跳转目标（工单中心）。
接收人菜单口径能接收某类工单消息 = 启用状态用户 ∩ 启用角色 ∩（role1 超管角色 或 角色被授予对应菜单 915 处置 / 916 督办）。
站内信 INBOXsys_message.msg_type='INBOX'、is_read=0、creator='system' 的个人消息行。
WEBSOCKET 通道对在线会话的实时投递记录；不落消息正文，只在 notify_send_log 记 SENT/SKIPPED 与在线会话数。
通知级别 levelsmallint 1 / 2 / 3：3 高、2 中、1 低；前端弹窗门槛 popupMinLevel 表示"≥ 该级别才弹窗"（默认 3 = 仅高级弹窗）。
发送意图日志notify_send_log：每个事件 × 接收人 × 通道一行，状态 SENT / SKIPPED / FAILED，detail 记会话数或失败原因（截断 500 字符）。
独立 WebSocketuseNotify 使用 /ws/realtime?token=JWT 单独建连，与实时监控页 useRealtime 的连接互不影响；一个用户多个标签页 = 多个 sessionId 同时收。
ObjectProvider 解耦notify 模块通过 ObjectProvider<RealtimePusher> 可选注入推送 bean，真正实现位于 module-monitor，避免 notify → monitor 的编译期反向依赖。

1.4 五类通道现状一览

通道（channel）是否真实送达默认开关打开开关后记账状态
INBOX 站内信是 写 traj.sys_message始终启用—落库即成功（消息行本身）
WEBSOCKET是 仅在线会话始终启用在线 SENT"在线会话 n"；不在线 SKIPPED"接收人不在线"逐接收人逐次记账
SMS 短信否notify.sms.enabled=falsesend 抛 UnsupportedOperationException → FAILED"短信渠道未对接厂商，暂不可用"未启用 SKIPPED"渠道未启用"
VOICE 语音外呼否notify.voice.enabled=falseFAILED"语音外呼渠道未对接网关"同上
PUSH App 推送否notify.push.enabled=falseFAILED"App 推送渠道未对接推送服务"同上

旧说法纠正（重要）：部分早期材料把"多渠道预警"表述为短信 / 电话通知能力。代码事实是：NotifyChannel 接口 javadoc 明确写"本期仅接口 + 开关 + 发送意图日志"，三个外部渠道实现的 send 方法无条件抛 UnsupportedOperationException。默认配置时全部 SKIPPED；即使运维把开关改成 true，也只会记 FAILED，任何部署配置下都不会真实外发短信 / 语音 / 推送。真实通知只有站内信 + WebSocket。

1.5 本期边界（不做什么）

  • 不做消息编辑 / 群发运营位：消息只能由业务事件（system 身份）产生，不提供管理员手工群发、公告编辑、消息模板管理页面。
  • 不做通知偏好自助页：popupMinLevel / soundEnabled 只有后端 GET /settings 读取，前端弹窗行为遵循参数；用户个人暂不可自行改阈值（参数在系统参数中心维护）。
  • 不对接真实外部厂商：不连短信厂商、语音网关、APNs / 各厂商推送，开关开启也不外发。
  • 不做多实例广播：WebSocket 会话注册表 SessionRegistry 是单机内存 ConcurrentHashMap，不做 Redis / MQ 跨节点路由（多节点部署见第 13 节风险）。
  • 不做消息撤回 / 已读回执同步给发送方：全部已读只影响本人收件箱状态。
  • 不持久化 WS 报文：WebSocket 报文本身不落库，不在线期间错过的实时弹窗靠站内信补看。

2 典型场景

值班监控员
新工单实时弹窗提醒
凌晨系统自动生成高风险工单，所有有处置菜单（915）权限的在线坐席右下角立即弹出通知并响一声提示音；点击弹窗直接打开该工单。
当班坐席
被分派 / 转派工单
班长把工单分派给某人时，当事人收到 ORDER_ASSIGN 消息；即使当时不在线，下次登录顶栏铃铛也显示未读数，消息中心可回看。
安全督办
超时升级督办
工单 SLA 超时升级（lv3），通知发给当前负责人和全部有督办菜单（916）的人员，级别为高，确保升级动作有人接。
坐席本人
闭环回执与清理
别人代为闭环自己负责的工单时收到 ORDER_CLOSE 消息；在消息中心一键全部已读，或删除不再需要的消息，未读数实时变化。
多标签页办公的坐席
每个标签都在线、只弹一次窗
同一账号开多个浏览器标签，每个标签是独立 sessionId 都能收到推送；前端单例保证未读数与最新列表在标签内一致维护。
网络抖动的远程坐席
断线自动重连不丢消息
网络抖动导致 WS 断开时指数退避重连（上限 30 秒）；断线期间的事件仍有站内信兜底，重连后刷新未读数与最新 10 条。

3 操作流程

消息中心是侧栏顶级单菜单：sys_menu id=924，parent=0（不在"系统管理"折叠目录 900 内），路由 /system/messages，图标 ChatDotRound，权限码 system:message:view，授予 role1~role4；同时顶栏铃铛在 MainLayout 全局常驻，无需进入菜单即可收弹窗。

3.1 顶栏铃铛与实时弹窗

登录即订阅
MainLayout 挂载时调用 useNotify（模块级单例，全局只挂一次），并行拉取未读数与最新 10 条，同时建立 /ws/realtime?token=JWT 长连接。
收到推送
只消费 type='NOTIFY' 的报文；level ≥ popupMinLevel（系统参数 notify.popup.min_level，默认 3）时右下角 ElNotification 弹 5 秒。
声音 / 系统通知
soundEnabled（默认 true）时用 Web Audio 合成 880Hz beep，无任何音频文件；level=2 且浏览器 Notification 已授权时额外发系统通知。
点击处理
点击弹窗（或系统通知）对 WORK_ORDER 消息直接跳转 /risk/orders?openOrder=<bizId>。

3.2 消息中心列表

  • 入口：顶级菜单"消息中心"（MessageCenter.vue）。顶部 el-radio-group 切换全部 / 未读，右侧显示未读条数与"全部已读"按钮。
  • 表格列：级别 tag（高 / 中 / 低配色）、类型（eventTypeName 映射：ORDER_CREATE 新建工单 / ORDER_ASSIGN 工单分派 / ORDER_ESCALATE 升级督办 / ORDER_CLOSE 工单闭环，未知类型显示原值）、标题、内容（超长 tooltip 悬浮看全文）、时间、状态（已读 / 未读）、删除操作。
  • 分页：固定 size=15，layout 为 total/prev/pager/next；服务端对入参 size 做 Math.min(size,100) 钳制，防止恶意大页。

3.3 已读、全部已读与删除

点行自动已读
点击列表行时若消息未读，先调 POST /messages/{id}/read，成功后本地未读数 −1 并更新行状态；非本人消息后端返回 404。
全部已读
点"全部已读"调 POST /messages/read-all，后端按 currentUserId 批量置 is_read=1 / read_date=now，返回 {updated}；前端未读数清零。
删除
DELETE /messages/{id} 仅删除本人消息；若删掉的是未读消息，前端刷新未读数。删除为物理删除（消息行从 sys_message 移除，发送日志 notify_send_log 保留）。

3.4 一键跳转到工单

列表行点击在"自动已读"之后判断 bizType === 'WORK_ORDER'，携带 bizId 跳转 /risk/orders?openOrder=<bizId>，工单中心据此自动打开对应工单详情（与画像 Top5 工单同一深链约定）。bizId 在后端为 Long、在前端 NotifyMessage 类型中为 string（与 id 一样字符串化，避免 JS 精度问题）。

3.5 事件与界面对照

eventType列表"类型"列典型标题来源点击去向
ORDER_CREATE新建工单"新工单：<事件名 / 等级>"，正文带车牌工单详情 openOrder

5 用户价值

0 配置
登录即自动订阅，无需坐席做任何设置
5 类事件
生成 / 分派 / 升级 / 闭环 / 系统，覆盖工单全生命周期
11 字段
推送报文自带工单号、车牌等跳转与展示信息
≤100
列表 size 服务端钳制，最新 10 条供铃铛、分页 15 条
  • 处置不遗漏：新单、升级按菜单权限精准推送给"有权处理的人"，而不是全员轰炸；在线弹窗 + 不在线站内信双通道兜底。
  • 零点击直达现场：报文携带 orderNo / plateNo / bizId，弹窗或列表点一下就打开工单，减少跨页查找。

  • 可审计可排障：每次投递（含跳过与失败原因）在 notify_send_log 留痕，"为什么我没收到"可以直接按事件 + 接收人查日志。
  • 外部渠道演进不返工：渠道接口、开关、日志、接收人圈定已就位，将来对接短信厂商只需替换 send 实现，不影响业务触发点。

6.1 前端实现要点

  • api/notify.ts 共 8 个函数：listMessages、latestMessages、unreadCount、markRead、readAll、deleteMessage、getNotifySettings（类型定义中 NotifyMessage.id / bizId 均为 string）。
  • useNotify.ts 状态在模块作用域（单例）：MainLayout 只调用一次注册，任何页面均可读其 unread / latest(10)；refresh() 并行请求未读数与最新列表。
  • WS 与实时监控页的 useRealtime 各自建连、互不影响：监控页断开不影响通知弹窗，反之亦然。
  • 重连退避：失败后等待时间指数增长，封顶 30 秒；重连成功立即 refresh 补拉断线期间的未读变化。
  • 提示音用 Web Audio API 现场合成 880Hz 短音，不依赖任何 mp3 / wav 资源（全站无外部资源约束）。
  • 系统通知需浏览器 Notification 授权，仅 level=2 走该路径且做能力检测；未授权静默降级为页面内弹窗。
  • MessageCenter 点行顺序：未读先 markRead（本地减未读）→ 再按 bizType 决定跳工单；删除未读消息后重新拉未读数。

7 核心实现逻辑

7.1 接收人圈定

  • 常量：MENU_OPERATOR=915L（处置工单菜单 / 按钮）、MENU_SUPERVISOR=916L（督办分派菜单）。
  • receiversByMenu(menuId) 调 NotifyMessageMapper.selectUserIdsByMenu，交集条件：用户启用 ∩ 角色启用 ∩（角色为 role1 超管 或 角色被授予该 menu）。
  • 各事件接收人：ORDER_CREATE → 菜单 915 全员；ORDER_ESCALATE → 工单当前负责人 + 菜单 916 全员（level=3 高）；ORDER_ASSIGN / ORDER_CLOSE → 被分派 / 负责该工单的具体人。
  • 接收人集合用 LinkedHashSet 去重（同一人不会因多角色重复收信）。

7.2 异步派发主流程

入口 dispatchAsync
业务方调用后立即返回；方法标注 @Async("notifyExecutor")，整个方法体外层 try/catch 吞掉所有异常——通知失败绝不允许反向打断工单主流程（如分派事务）。
圈定接收人
按事件类型算出接收人集合；为空则直接结束（无受众不产生任何日志噪声）。
逐接收人 dispatch
每人：①insert 一条 sys_message 站内信；②pushWebsocket 在线实时推送并按送达数记账；③dispatchExternalChannels 遍历短信 / 语音 / 推送三个预留渠道。

异步化的意义：RiskOrderService 的分派 / 闭环是同步业务事务，通知若同步发 WS、查接收人、写多行日志会拉长接口 RT 且可能被外部 IO 拖累；@Async + CallerRunsPolicy（队列满时由调用线程兜底执行）兼顾了隔离与不丢任务。

7.3 站内信落库

  • 实体 NotifyMessage @TableName("traj.sys_message")：id、userId、title、content、msgType、isRead、bizType、bizId(Long)、level、eventType、creator、createDate、readDate。
  • 派发写入固定值：msgType='INBOX'、is_read=0、creator='system'，create_date 走默认时间；biz_id 存工单 ID，level / event_type 随事件带入。
  • 已读：单条更新校验 user_id = currentUserId，写入 read_date；全部已读按 user_id 批量更新。
  • 查询：列表索引 (user_id,is_read,id DESC) 支撑"未读 + 最新在前"；(biz_type,biz_id) 支撑按业务对象反查消息。

7.4 WebSocket 实时推送

  • 解耦方式：NotifyService 注入 ObjectProvider<RealtimePusher>。RealtimePusher 的实现 bean 由 module-monitor 提供（SessionRegistry）；监控模块不在部署中时 ObjectProvider 取不到 bean，推送安全跳过，通知模块照常发站内信，无启动依赖失败。
  • 会话模型：SessionRegistry 为单机内存 ConcurrentHashMap，键为 uid，值为该用户的多个 sessionId——同一账号多标签页、多设备同时在线时每个会话都送。
  • 报文：sendToUsers(uid, "NOTIFY", payload)，type 固定 NOTIFY，payload 11 个字段：id（字符串）、title、content、level、eventType、bizType、bizId（字符串）、orderNo、plateNo、createDate——即前端弹窗与跳转所需的全部信息，无需收到后再回查接口。
  • 送达记账：按返回的在线会话数记 WEBSOCKET 通道日志：在线 SENT 且 detail="在线会话 n"；该用户当前无会话则 SKIPPED"接收人不在线"（不算失败）。
  • 鉴权：连接 URL /ws/realtime?token=JWT，握手期校验令牌并绑定 uid，不靠查询参数传用户身份之外的任何内容。

7.5 发送日志记账

实体 NotifySendLog @TableName("traj.notify_send_log")：eventType、bizType、bizId、channel、receiverId、title、level、status、detail、createDate。

channelstatus 取值与 detail
WEBSOCKET在线：SENT，detail="在线会话 n"（n=会话数）；不在线：SKIPPED，detail="接收人不在线"
SMS / VOICE / PUSH开关关：SKIPPED，detail="渠道未启用"；开关开但发送抛异常：FAILED，detail=异常信息（截断 500 字符）
（INBOX）站内信以 sys_message 行本身为凭证，不另外写发送日志

索引 (biz_id,event_type) 支撑按业务事件回溯"发给了谁、各通道结果"；(create_date DESC) 支撑按时间排障。日志只增不改，删除消息不影响日志。

7.6 外部渠道预留实现

三个渠道均实现统一 NotifyChannel 接口（javadoc："本期仅接口 + 开关 + 发送意图日志"），结构完全对称：

渠道开关配置（默认）send 实现
SmsChannelnotify.sms.enabled = falsethrow new UnsupportedOperationException("短信渠道未对接厂商，暂不可用")
VoiceChannelnotify.voice.enabled = falsethrow new UnsupportedOperationException("语音外呼渠道未对接网关")
PushChannelnotify.push.enabled = falsethrow new UnsupportedOperationException("App 推送渠道未对接推送服务")
  • dispatchExternalChannels 对每个渠道：未启用 → SKIPPED"渠道未启用"；启用且 send 正常 → SENT（当前实现不可达）；send 抛异常 → FAILED（detail 截 500）。
  • 因此在任何配置组合下都不会产生真实外部通讯；配置项存在的意义是固化参数键、让未来对接时无需改表结构，并提前打通"开关→日志"链路。

7.7 通知设置读取

  • GET /api/notify/settings 返回 NotifySettingsVO：popupMinLevel（int）与 soundEnabled（boolean）。
  • popupMinLevel 读系统参数 notify.popup.min_level，默认 3；值不在 1~3 范围内时回落 3，防止参数配错导致全部弹或全不弹。
  • soundEnabled 读 notify.sound.enabled，默认 true；经 ConfigService.getBool 解析（Boolean.parseBoolean，非法值按 false 处理）。
  • 本模块不提供设置写入接口；两个参数在"系统参数"中心维护（见 MOD-DBD-012），且 11 脚本种子中这 5 个通知参数 is_system=0（非内置锁定项，可在页面编辑 / 删除）。

7.9 前端实时单例 useNotify

  • 模块级单例：状态与连接定义在 composable 模块作用域，MainLayout 初始化一次；铃铛、消息中心共用同一份 unread / latest。
  • 独立连接：直连 /ws/realtime?token=JWT，与监控页 useRealtime 的连接相互独立；只处理 type='NOTIFY' 报文，其他类型忽略。
  • 指数退避重连：断线后等待 1s、2s、4s… 重试，封顶 30 秒；页面可见性恢复时也会触发检查，减少长时间挂起。
  • 三道提醒：①满足级别门槛 → ElNotification 右下角弹 5 秒；②soundEnabled → 880Hz Web Audio beep（无音频资源文件）；③level=2 且 Notification 已授权 → 浏览器系统通知。
  • 点击动作：弹窗 / 系统通知点击后关闭并对 WORK_ORDER 执行工单深链跳转。
  • 状态维护：unread 计数与 latest(10) 随推送增量更新；refresh() 并行调 unread-count 与 latest 两接口做对账，重连后必刷。

7.10 派发时序与一致性边界

  • 提交后派发：业务侧在工单落库事务成功路径上调用 dispatchAsync；@Async 使写消息发生在独立线程 / 独立事务，不存在"消息发了但工单回滚"的回滚连带问题，但也意味着极端情况下"工单提交成功、派发线程执行前进程被杀"会丢这一条通知（站内信也没有），靠工单调度 / 列表查询兜底被发现。
  • 先落库后推送：每人 dispatch 内先 insert sys_message 再 pushWebsocket，保证在线弹窗点出的 bizId 一定查得到工单消息；推送失败不回滚已落库消息。
  • 失败隔离粒度：逐接收人处理，某人某通道异常不影响其他人；异常被 catch 后记 FAILED 或仅服务端日志，循环继续。
  • 顺序保证：同一工单的生成 → 分派 → 升级 → 闭环在不同业务时刻产生，经同一线程池最多 2 线程并发，不保证严格按事件时间顺序送达；消息带 createDate，列表按 id DESC 展示，排障以时间为准。
  • 无重试：站内信 insert 失败、WS 发送失败均不做自动重试（WS 本就是在线即时语义；失败已记账），需要补偿时按业务重放（如再次分派）。
  • 权限快照：接收人集合在派发当下计算一次并固化为逐人消息；事后回收某人菜单权限不会删除已入库消息，只会让后续事件不再发给他。

7.11 安全与隐私设计要点

  • 无水平越权面：接口不接收 userId / receiverId 入参，收件人恒等于登录态 currentUserId，从参数层面消除改 ID 看他人数据的可能。
  • 存在性不泄露：访问他人消息一律 404"消息不存在"，而不是 403，攻击者无法据此分辨消息 ID 是否存在。
  • 写操作只来自后端：sys_message 没有面向前端的创建接口，标题 / 内容 / 级别全部由服务端事件对象决定，用户不能伪造"系统通知"钓鱼。
  • WS 令牌鉴权：握手期校验 JWT 绑定 uid，会话注册表不接受自报身份；登出 / 令牌失效后旧连接无法继续收信（结合网关心跳清理）。
  • 最小内容原则：消息正文只带处置必需信息（工单号、车牌、事件名），不带司机身份证号 / 电话等敏感字段。
  • 大页防护：size 钳 100、latest.limit 钳 50，防止用大结果量做拖库式探测。
  • 日志最小化：send_log 记 title / level / 接收人用于排障，不记录 WebSocket 报文头或 token。

12 技术选型依据

  1. 通知与业务事务解耦：@Async 专用线程池让派发改动、WS IO、日志写入都不进工单事务，通知子系统故障不外溢为处置流程故障。
  2. ObjectProvider 可选注入消除反向依赖：WS 实现属于监控模块，通知模块若直接 @Autowired 会造成 notify→monitor 硬依赖与潜在循环；ObjectProvider 让 bean 缺失成为可运行的降级路径。
  3. 单机内存会话表满足当前部署：平台为单节点 / 主备部署，ConcurrentHashMap 比引入 STOMP / Redis Pub/Sub 简单且零外部依赖；多标签页按多 sessionId 支持；横向扩展时再升级（见风险）。
  4. 站内信作为唯一持久真相：实时推送是"锦上添花"，可丢可跳；消息必须落 sys_message，在线 / 离线、弹窗 / 不弹窗都不影响信息可追溯。
  5. 外部渠道先立契约再接厂商：统一 NotifyChannel 接口 + 配置开关 + send_log 记账，使运营侧先在日志里看到"本该发给谁"，厂商对接只是替换三个 send，调用方零改动。
  6. 前端单例 + 独立 WS：通知是全局能力，单例避免多页面重复建连；与监控 WS 分连接避免高频轨迹报文挤占通知消息、也避免生命周期互相牵连。

15 边界行为与常见问题

为什么开了 notify.sms.enabled=true 还是收不到短信？
这是预留开关。SmsChannel.send 无条件抛 UnsupportedOperationException，系统只记一条 FAILED 日志，任何情况下都不真实外发；需要短信能力必须先对接厂商实现。
为什么收不到新工单弹窗？
依次排查：①账号是否启用且角色拥有菜单 915（role1 默认有）；②WS 是否在线（顶栏连接态 / 重连日志）；③消息级别是否达到 popupMinLevel（默认 3，只有高级弹窗）；④浏览器是否屏蔽了页面内通知。站内信列表可作为消息是否生成的最终依据。
不在线期间的消息会丢吗？
不会。实时推送只对在线会话发送（不在线记 SKIPPED），但站内信在派发时已落库；下次登录 / 重连 refresh 后未读数与最新列表都会补出来。
多个标签页会收到多条吗？
后端会向每个 sessionId 都投递（多标签都在线），但 useNotify 是模块级单例，同一标签内只维护一份状态；不同标签各自弹一次属于预期（每个窗口都是独立页面环境）。
点别人转发的消息链接会怎样？
已读 / 删除接口都校验消息 user_id = 当前登录人，不匹配返回 404"消息不存在"，看不到标题内容，也无法替别人已读。
删除消息后发送日志还在吗？
在。删除只物理移除 sys_message 行；notify_send_log 只增不改，仍可按 biz_id + event_type 审计当时各通道结果。
全部已读返回的 updated 为什么有时是 0？
当前没有未读消息时更新 0 行；前端无论返回数字是几都会把本地未读数清零对齐。
提示音可以关吗？
可以，把系统参数 notify.sound.enabled 置为 false（GET /settings 生效）；本模块不提供个人偏好页，参数为全局口径。
分派工单为什么当事人没收到 ORDER_ASSIGN？
只有"分派 / 转派导致负责人变更"才发；若账号停用、角色停用，或接收人查询时该用户不在启用集内则不会入库。可用 notify_send_log 按工单 biz_id 反查。
消息中心菜单在哪？
侧栏顶级单菜单"消息中心"（id=924，ChatDotRound 图标），不在"系统管理"折叠目录里；role1~role4 默认可见。
通知为什么没有把司机电话 / 身份证号推给我？
消息正文按最小内容原则只带工单号、车牌与事件信息；司机明细请点进工单详情按权限查看，通知渠道不承载敏感个人信息。
怎么确认一条通知到底有没有"尝试发送"？
查 traj.notify_send_log：按 biz_id（工单 ID）+ event_type 可看到每个接收人在 WEBSOCKET / SMS / VOICE / PUSH 各通道的 SENT、SKIPPED 或 FAILED 与 detail；INBOX 以 sys_message 行本身为准。

17 待核实项

下列条目在本期代码 / 脚本中未能闭环确认：

  • 多节点部署路线：SessionRegistry 单机内存，横向扩容时实时消息如何路由（Redis Pub/Sub、MQ 还是网关粘性会话）未定方案。
  • 站内信保留策略：sys_message / notify_send_log 无清理 / 归档任务与保留周期配置，数据增长后的容量与清理责任方待明确。
  • 个人通知偏好：popupMinLevel / soundEnabled 当前是全局参数；是否需要用户级覆盖（免打扰时间段、按事件类型订阅）待产品确认。
  • SYSTEM 事件使用方：NotifyEvent.SYSTEM 常量与字典项已备，但当前没有任何业务代码构造系统通知，触发场景待定义。
  • 外部渠道排期：短信 / 语音 / 推送三家厂商选型、签名 / 模板报备、频控与退订合规均未启动；对接时还需明确 send_log 与厂商回执的对账方式。
  • WS 心跳与令牌续签：指数退避重连已实现，但长连接心跳间隔、JWT 有效期内续签是否会强制断连，需结合统一认证配置复核。
