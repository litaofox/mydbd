MOD-DBD-003 主数据管理

文档编号 MOD-DBD-003|版本 v1.0.0|发布日期 2026-10-05| 状态 已上线|功能编号 F28 / F29 / F30 / F31 / F32

事实基准：2026-10-05 源代码（backend-java module-mdm）与初始化 SQL（02-traj-tables.sql、04-mdm-tables.sql、06-iam-tables.sql、16-province-test-data.sql）

主要代码锚点：VehicleController / TerminalController / DriverController / OrgController / BindingController；VehicleService / TerminalService / DriverService / OrgService / BindingService（module-mdm）；前端 views/mdm/VehicleList.vue、OrgTree.vue、TerminalList.vue、DriverList.vue、api/mdm.ts

1 功能概述

1.1 模块定位与边界

主数据管理（MDM）维护平台一切业务数据的锚点档案：多级组织树、车辆、车载终端、驾驶员，以及"车-终端""车-司机"两类绑定关系。轨迹点、报警、风险事件等动态数据都通过车牌 / 终端编号 / 车辆归属组织回挂到本模块的档案上，因此它是数据权限（归属锚点 traj_vehicle.dept_id）与监控、回放、分析等所有下游模块的共同地基。

  • 组织架构（F32）：运输企业 / 车队两级语义的多级树（traj.traj_dept，parent_id=0 为根），支持无限层级；树节点带有效车辆数；是 IAM 五级数据范围的作用对象。
  • 车辆档案（F28）：车牌 + 车牌颜色为业务唯一键，另存 VIN、车型、运营类型、行业、道路运输证、归属组织、车主等台账字段。
  • 终端档案（F29）：终端编号（identity_code，对接 JT/T 808 终端手机号口径）唯一，另存型号、SIM、协议类型、设备类型、视频通道数、状态。
  • 驾驶员档案（F30）：驾驶证号唯一，另存准驾车型、联系方式、状态。
  • 绑定关系（F31）：车-终端一对一（同车换终端走"换绑"，同事务先解后绑）；车-司机一车一主班、多副班；一名司机同一时刻仅一条有效绑定。互斥由 Service 校验 + 数据库部分唯一索引双重保障。

一句话边界：本模块只回答"这辆车/这台终端/这名司机是谁、挂在哪个组织、当前和谁绑在一起"。轨迹怎么进来（MOD-DBD-004）、车辆实时位置怎么展示（MOD-DBD-005）、报警怎么处置（MOD-DBD-006）都不在这里；但它们的查询与权限过滤全部回读本模块档案。

1.3 术语与概念

术语含义
归属锚点 dept_idtraj_vehicle.dept_id 是车辆类数据（轨迹/报警/统计）的唯一权限锚点；数据可见性一律以车辆归属组织为准，不按车牌省份过滤。
deptType组织类型：1=运输企业，2=车队/部门；仅作展示与语义区分，不参与权限计算。
identity_code终端编号，轨迹点（traj_gps_point.identity_code）与报警（traj_warn_info.identity_code）经它回挂终端与车辆。
有效绑定绑定记录 status=1 AND valid_mark=1；解绑只置 status=0 并写 unbind_time，行保留作历史。
换绑车辆已绑终端时再绑新终端：旧关系同事务置失效并追加备注"换绑：旧终端卸除"，再插入新关系。
主班 / 副班车-司机绑定的 driver_type：1=主班（一车仅一名，部分唯一索引兜底），2=副班（数量不限）。
运营类型 operationType1=货运 2=客运 3=危化品 9=其他（实体注释口径）。
祖先补全自定义数据范围只勾了若干下级部门时，组织树自动把它们的祖先节点补为可见（仅作树形容器），避免树断成孤点。
软删 valid_mark四类档案与组织均软删（置 0）；业务唯一键均为"valid_mark=1 部分唯一"，删除后同名可再建。

2 典型场景

企业车队长
新车投入运营
登记车辆（车牌+颜色+VIN+归属车队）→ 登记终端（编号/SIM/协议）→ 绑定管理中把终端绑到车上 → 绑定主班司机。完成后该车立即可被监控页检索，轨迹点经终端编号回挂档案。
企业车队长
终端故障更换
车辆终端损坏换新：在绑定管理直接绑定新终端，系统自动执行换绑——旧关系置失效写解绑时间，新关系生效；历史时间线完整保留两次绑定。
调度监控员
按组织核查车辆
在车辆档案用"所属组织（含下级）"树选车队，一次列出该车队及全部下级车队的车辆；只能看到自己数据范围内的组织与车辆，范围外车辆连下拉都不出现。
平台管理员
企业入驻建组织
在组织架构页"新增根单位"建运输企业，再在其下"新增下级"建车队；随后把车辆归属到车队，IAM 角色按该组织配置数据范围即完成租户隔离。
安全管理员
创建用户时选归属部门
占位
组织树接口同时授权给 mdm:org:view 与 iam:user:edit（OR），因此安全管理员（只有用户维护权、没有主数据菜单全量权）也能在用户管理里挑选归属部门。
数据治理
司机跨车调班
司机从 A 车调到 B 车：先在 A 车解绑，再到 B 车绑定。系统强制"一司机同时仅一条有效绑定"，杜绝一名司机同时挂在两台车上导致驾驶行为归属混乱。

3 操作流程

菜单路径：主数据管理一级目录（sys_menu id=100），下挂四个菜单：组织架构（id=101，/mdm/org，权限点 mdm:org:view）、车辆档案（id=102，/mdm/vehicles，mdm:vehicle:view）、终端档案（id=103，/mdm/terminals，mdm:terminal:view）、驾驶员档案（id=104，/mdm/drivers，mdm:driver:view）。维护按钮 id=201~204，权限点 mdm:org:edit / mdm:vehicle:edit / mdm:terminal:edit / mdm:driver:edit。内置角色中：调度监控员四个菜单只读；企业车队长四个菜单可见且有车辆/终端/驾驶员维护（组织仅查看）；安全管理员仅见目录与组织架构。

3.1 组织架构维护

打开组织页
主数据管理 → 组织架构，左侧为组织树（企业/车队标签区分），右侧为选中节点详情。
新增根单位 / 下级
树上方"新增根单位"（parentId 置 0）；或节点行内"新增下级"。表单含名称、编码、类型、联系人、地址、排序号。
编辑 / 删除
节点行内"编辑"改资料或换上级（不能选自己或自己的下级）；"删除"要求该组织下无下级、无有效车辆。
查看辖区车辆
选中节点后右侧展示详情（含"有效车辆数"标签）与"该单位下车辆"表（车牌/颜色/车型/品牌/主班司机）。

3.2 车辆档案登记与查询

组合筛选
顶部工具栏：关键字（车牌号 / VIN）、所属组织（树选，自动含全部下级）、车牌颜色、运营类型；查询 / 重置。
浏览列表
列：车牌、颜色、所属组织、车型/品牌、运营类型、车主、当前终端（未绑定显示"未绑定"）、主班司机、操作列。
登记 / 编辑车辆
"登记车辆"打开 460px 抽屉：归属组织（树选）、车牌、颜色、VIN（17 位字母数字，可空）、车型、运营类型、行业、道路运输证、车主及电话等；车牌+颜色重复时提示冲突。
删除车辆
存在有效终端或司机绑定时被拒绝（"该车辆存在有效终端或司机绑定，请先解绑"）；否则软删。

3.3 绑定管理（车-终端 / 车-司机）

打开绑定管理
车辆列表操作列"绑定管理"（需 mdm:vehicle:edit），弹出 780px 绑定视图。
查看当前状态
三张卡片：当前终端（编号/型号/SIM/安装人/安装时间）、在班司机（姓名/班别/电话/准驾）、绑定历史时间线（终端与司机两段，含解绑时点）。
绑定 / 换绑终端
"换绑/绑定"选终端（下拉仅列状态正常的终端）、绑定类型、安装人；车辆已绑其他终端时自动换绑。终端已绑他车会被拒绝并提示那台车的车牌。
绑定 / 解绑司机
"绑定司机"选驾驶员（下拉仅列在岗司机）、班别（主班/副班）；主班已存在时再绑主班会被拒绝。解绑在卡片行内点"解绑"。

3.4 终端档案维护

  • 筛选：关键字（终端编号 / SIM 卡号）、状态、协议类型（如 JT808）、设备类型。
  • 列表聚合"当前绑定车牌"（boundVehicleNo，取自有效车-终端绑定）。
  • 新增/编辑字段：编号（唯一）、MAC、厂商编码、型号、SIM、协议类型、设备类型、视频通道数、状态、备注。
  • 删除约束：存在有效车辆绑定的终端禁删，先解绑。

3.5 驾驶员档案维护

  • 筛选：关键字（姓名 / 手机号 / 驾驶证号）、状态（在岗/停用）。
  • 列表聚合"当前绑定车牌"。
  • 新增/编辑字段：姓名、性别、身份证（可空）、联系电话（手机号格式校验）、驾驶证号（唯一）、准驾车型、照片地址、状态、备注。
  • 删除约束：存在有效车辆绑定的司机禁删。

5 用户价值

5 类档案
组织/车辆/终端/司机/绑定统一管理，一处维护处处引用
3 道互斥
一车一终端、一终端一车、一车一主班，数据库部分唯一索引兜底
1 个锚点
车辆 dept_id 是全平台数据权限的唯一归属锚点
0 误删
有绑定禁删车/终端/司机，有下级或有车辆禁删组织
  • 台账一致：车牌+颜色、终端编号、驾驶证号三项业务唯一键，从源头杜绝重复建档。
  • 换绑不断史：换绑、解绑全部保留历史行与时间线，事故追溯时能还原"当时是谁的车、装的哪台终端、谁在开车"。
  • 权限天然生效：受限角色打开任何档案页只能看到本范围组织与车辆；组织树自动补祖先，树形体验不塌。
  • 操作防呆：重复绑定、主班冲突、终端占用的报错文案直接给出对方车牌（如"该终端已绑定车辆 鲁Axxxxx，请先解绑"），不用猜原因。
技术篇

6 模块架构与组件

主数据是单模块（module-mdm）内聚实现：5 个 Controller 暴露 REST，5 个 Service 承载全部业务规则，6 个 Mapper（MyBatis-Plus）访问 traj schema 的 6 张表；前端 4 个页面 + 1 个 api 封装。

7 核心实现逻辑

7.1 数据范围裁剪与组织树祖先补全

车辆与组织是数据权限的直接作用对象，裁剪全部在服务层完成，准则为 fail-closed：

取范围
UserContext.get().deptScope()：null=不限（超管/数据范围=全部），空集合=任何部门数据都不可见，非空集合=可见部门 ID 集。
车辆分页裁剪
scope 为空集直接返回空页；deptId 筛选先 expandDeptTree(deptId) 展开自身+全部下级，再与 scope 求交，交集为空返回空页；最终 dept_id IN (交集)。
车辆详情裁剪
detail 查出车辆后判断 deptId 是否 ∈ scope，不在则抛 40401"车辆不存在或无权查看"——不暴露"存在但无权"的信息。
组织树裁剪
全量有效组织查出后，visibleIds = scope + appendAncestors(scope)（沿 parent 链补全祖先）；根判定 = parent_id=0 或父节点不在可见集内（裁剪后的"伪根"）。

可见性以归属组织为准，与车牌省份无关：公司名下可挂任意外省车牌，只要 dept_id 在范围内即全部可见；province_code/车牌首字仅作档案展示，不作为权限条件（SYS-DBD-001 §8.2 条款）。车辆过户改 dept_id 后，历史数据随新归属可见。

7.2 车辆档案 CRUD 与占用校验

动作校验顺序失败响应
新增① 车牌+颜色在 valid_mark=1 内查重 → ② deptId 非空时校验组织存在 → ③ 置 valid_mark=1 插入40901"车牌号+车牌颜色已存在：{车牌}"；40401"所属组织不存在"
编辑① requireVehicle（不存在或已删 → 40401）→ ② 同新增①②（排除自身）同上
删除① requireVehicle → ② 统计有效终端绑定数与有效司机绑定数 → ③ 任一 >0 拒绝 → ④ 置 valid_mark=040901"该车辆存在有效终端或司机绑定，请先解绑"
分页valid_mark=1 + 关键字（车牌/VIN 模糊）+ 颜色 + 运营类型 + 范围裁剪，按 id 倒序；enrich 聚合三字段—

enrich 的三次批量查询（避免 N+1）：按 deptIds 批量取组织名；按 vehicleIds 取有效车-终端绑定后批量取终端编号；按 vehicleIds 取有效且 driver_type=1 的车-司机绑定后批量取司机姓名。

7.3 绑定关系状态机（换绑 / 主副班）

车-终端（一对一）：

绑定前置校验
终端须存在且 valid_mark=1；status=1（正常）才可绑；该终端已有效绑定到他车 → 40901 并给出对方车牌。
重复 / 换绑分支
本车当前有效终端 = 目标终端 → 40901"无需重复绑定"；= 其他终端 → 同事务内旧关系置 status=0、写 unbind_time、备注追加"换绑：旧终端卸除"。
插入新关系
bind_type 默认 1，bind_time 与 install_time 同取 now，installer 透传，status=1、valid_mark=1。
解绑
须存在当前有效绑定（否则 40901"当前车辆没有绑定终端"）；置 status=0 + unbind_time + 备注追加（旧备注与新备注以"、"连接）。

车-司机（一主多副）：司机须存在且在岗（status=1）；司机已有效绑定他车 → 40901 给车牌；已绑本车 → 40901 重复；绑主班（driver_type=1）时统计本车有效主班数，>0 → 40901"本车已有主班司机，一车仅一名主班"；副班（driver_type=2）无人数限制。解绑按 vehicle_id+driver_id 定位当前有效绑定。

绑定视图 getBinding：一次返回当前终端（有效绑定第一条）、在班司机列表、终端历史、司机历史；两个历史 SQL 分别 LEFT JOIN 车辆/终端与车辆/司机，把车牌、终端编号/型号/SIM、司机姓名/电话/准驾一并带出，前端时间线直接用。

7.4 部分唯一索引：互斥的最终防线

Service 校验存在并发窗口（两个请求同时通过"未绑定"检查），04-mdm-tables.sql 用三条 PostgreSQL 部分唯一索引在数据库层兜底：

索引定义保证
uk_traj_vt_vehicle_activeUNIQUE (vehicle_id) WHERE status=1 AND valid_mark=1一辆车同一时刻仅一台有效终端
uk_traj_vt_terminal_activeUNIQUE (terminal_id) WHERE status=1 AND valid_mark=1一台终端同一时刻仅绑定一辆车
uk_traj_vd_vehicle_mainUNIQUE (vehicle_id) WHERE status=1 AND valid_mark=1 AND driver_type=1一辆车同一时刻仅一名有效主班司机

并发撞索引时由 GlobalExceptionHandler 把 DuplicateKeyException 统一翻译为 40901"数据已存在或绑定冲突，请检查唯一性规则"（见 MOD-DBD-001）。档案类唯一键同样是部分唯一：uk_traj_vehicle_no_color（车牌+颜色）、uk_traj_terminal_identity、uk_traj_driver_license、uk_traj_dept_code，均带 WHERE valid_mark=1，软删后同名可再建。

7.5 前端页面实现

  • 筛选与权限：四个页面筛选区与 api/mdm.ts 参数一一对应；维护按钮统一 v-perm="'mdm:*:edit'"，只读角色（调度监控员）看不到按钮，直输 URL 调写接口也会被后端 40301 拒绝。
  • 组织树选择：车辆页用 el-tree-select（check-strictly）选组织，占位文案"所属组织（含下级）"提示服务端子树展开语义。
  • 绑定弹层：打开时 @open=loadBinding 拉取绑定视图；终端/司机下拉分别用 options 接口（只列状态正常/在岗）；解绑有确认框；操作后刷新视图。
  • 组织页：树节点行内按钮 @click.stop 防止误触发选中；右侧车辆表复用车辆分页接口（deptId=选中节点，天然含下级）。

8 数据流程

以"车队长登记一辆车并绑定终端司机"为例的端到端链路：

建档
POST /api/mdm/vehicles → 查重/组织校验 → insert traj_vehicle（审计字段自动填充）。
绑终端

绑司机

变更留痕

12 技术选型依据

  1. 邻接表组织树 + 内存组装，而非闭包表/物化路径：组织规模在千级以内，一次 selectList 全量取出后内存建树、补祖先、展开子树都是 O(n)；换来的是模型简单、迁移成本低，且无递归 SQL（PostgreSQL 递归 CTE 在此规模无必要）。
  2. 部分唯一索引而非全表唯一约束：软删（valid_mark）与"活跃绑定"语义下，唯一性只在有效行上成立；PostgreSQL 部分索引精确表达该语义，且让"同名再建""历史行留存"天然可行。
  3. 换绑同事务先解后绑，而非直接改外键：绑定是带生命周期的关系记录（bind/unbind_time、installer、备注），不是车辆上的一个字段；事务保证"旧解新立"原子生效，历史线完整。
  4. Service 校验 + DB 索引双保险：Service 给出可读文案（含对方车牌），索引兜住并发窗口；翻译器把撞库错误统一成 40901，不泄 SQL。
  5. 列表聚合用批量查询手工 enrich，而非视图/JPA 关联：MyBatis-Plus 下单表实体更轻；deptName/terminalIdentity/mainDriverName 三次 in 批量查询避免 N+1，也避免维护数据库视图。
  6. 组织树接口对 iam:user:edit 做 OR 授权：用户管理表单需要选归属部门，但该角色未必有主数据菜单；一个接口双权限点 OR 免去再开一条专用接口。

13 技术风险与对策

风险现状证据影响对策/演进
同车同司机解绑后无法再次绑定 解绑仅置 status=0，valid_mark 保持 1；uk_traj_vd_vehicle_driver 对 (vehicle_id, driver_id) 在 valid_mark=1 上唯一 司机调班再调回原车时，重复绑定会撞索引返回 40901（约束翻译文案，不指名原因） 已在 15/17 节明示；如需支持复绑，应把该索引改为含 status=1 条件或解绑时置 valid_mark=0，改动需评审
终端/司机档案无归属组织字段 traj_terminal / traj_driver 无 dept_id；分页不做数据范围裁剪（司机经绑定的车辆间接归属） 受限角色可见全平台终端/司机台账（不含轨迹等业务数据） 现行口径：档案级共享、业务数据按车辆归属过滤；如需台账级隔离，应为终端补归属或经绑定车辆 EXISTS 过滤
组织树全量查出后内存裁剪 OrgService.tree() selectList 全表 组织规模到万级时单次查询与内存组装成本上升 当前企业级规模无压力；规模化后改按 scope 递归查询或闭包表
换绑期间轨迹归属瞬时双写窗口 轨迹点按 identity_code 关联，换绑事务提交前的在途点仍挂旧关系口径 秒级窗口内"车辆当前终端"与最新点可能不一致 事务内先解后绑已把窗口压到最小；监控展示以最新点为准，影响可忽略
无档案批量导入 仅单条 CRUD；演示数据走数据集生成器 企业初次入驻数百台车需逐条录入或脚本化 建设规划中的批量导入可复用现有 Service 校验逐行执行

15 边界行为与常见问题

车牌相同但颜色不同能建两台车吗？
能。唯一键是"车牌号+车牌颜色"组合（uk_traj_vehicle_no_color），同色同号才冲突。
为什么受限角色能看到别的企业的终端/司机？
终端与司机表没有归属组织字段，档案级全平台共享；车辆、组织及全部业务数据仍严格按 dept_id 过滤。司机的业务数据经其绑定车辆间接归属。
车辆删除失败提示"存在有效终端或司机绑定"？
删除前统计有效（status=1 且 valid_mark=1）绑定，任一大于 0 即 40901 拒绝，须先在绑定管理中解绑。终端、司机同理。
换绑和"先解绑再绑定"有什么区别？
结果相同，但换绑是一个事务内的原子的"旧解新立"，中途失败整体回滚，不会出现车辆短暂无终端的中间态；备注自动追加"换绑：旧终端卸除"。
一台车能绑几个司机？
一名主班 + 不限量副班。主班唯一由 Service 计数与 uk_traj_vd_vehicle_main 索引双重保证。
司机从 A 车解绑后，能立刻绑回 A 车吗？
现状不能。uk_traj_vd_vehicle_driver 对（车,司机）在 valid_mark=1 上唯一，而解绑不置 valid_mark=0，重复绑同一组合会撞索引报 40901；换绑他车不受影响。该行为是否需调整为"可复绑"待评审（见 17 节）。
组织删除的两个前置条件是什么？
无有效下级组织、无有效车辆（均按 valid_mark=1 统计），报错文案会带具体数量。
把组织的上级改成它的下级会怎样？
被拒绝（40901"上级组织不能选择自己的下级"）；同时禁止选自己。collectDescendantIds 遍历全部后代判定，防止成环。
自定义数据范围只勾了下级部门，组织树为什么是完整的？
appendAncestors 自动把可见部门的祖先补进可见集（仅作树形容器），树根不断裂；祖先节点本身不代表有该部门业务数据权限。
VIN 和手机号校验规则是什么？
VIN 允许空或 17 位字母数字；车主电话/联系电话允许空或大陆手机号 ^1[3-9]\d{9}$；校验失败返回 40001 并带字段名。

17 待核实项

以下条目在 2026-10-05 代码阅读中表现为现状但产品口径未定，按"待核实"标注，不在本文做确定性结论：

  • 车-司机解绑后复绑：uk_traj_vd_vehicle_driver 的现状导致"同车同司机解绑后不能再绑"（见 13/15 节）；这是索引设计的有意约束还是遗漏（应加 status=1 条件），需产品确认。
  • 终端/司机台账的数据范围：档案级共享是否符合多租户预期；若需隔离，方案（补归属字段 vs 经绑定过滤）待评审。
  • 车辆 dept_id 为空：档案允许不选组织（deptId 可空）；此类车辆对受限角色不可见、对超管可见，过户/补录流程是否要求强制归属待确认。
  • 演示企业 id 10/20/30/40 的创建时点：16 号种子只做改挂，企业本体由数据集生成器创建；全新空库未跑生成器时改挂 UPDATE 不生效（无副作用），该初始化顺序依赖已在部署手册登记。
