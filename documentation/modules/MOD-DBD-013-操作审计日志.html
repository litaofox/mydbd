MOD-DBD-013 操作审计日志

编号：MOD-DBD-013｜版本：v1.0.0｜日期：2026-10-05｜ 状态：已上线｜覆盖功能项：F34｜ 代码锚点：module-audit、platform-common/audit、05-audit-tables.sql、AuditLog.vue、api/audit.ts
产品篇

1. 模块用途

操作审计日志模块对平台用户的关键操作进行自动、完整、不可由业务侧修改的留痕，回答四个问题：谁（userName / clientIp / userAgent）、在什么时间（createTime）、对什么对象做了什么（module / action / objectType / objectId）、结果如何（成功失败 / 业务码 / 错误信息 / 耗时）。

模块覆盖 F34「操作审计日志」的上线范围：登录（含失败登录）、退出登录、全部增删改写操作、业务处置动作的留痕，以及面向安全管理员的多维检索、区间统计与详情查看。检索页面本身只读，且默认不审计自身查询，避免审计噪声自循环。

使用角色
超级管理员、安全管理员（权限码 audit:view，类级注解强制）
菜单入口
系统管理 → 操作审计（前端 views/system/AuditLog.vue）
数据保留
只追加表 traj.sys_audit_log，应用层不提供修改、删除接口；保留策略与归档周期见 第 23 节
性能取向
业务请求只做"包装 + 发事件"，落库在独立单线程异步执行，审计故障不影响业务响应
基准说明
本文全部"已实现"表述以 2026-10-05 仓库源代码为事实基准；无代码证据的能力不做上线声明

2. 术语与概念

术语本文中的含义
审计事件（AuditEvent）一次 HTTP 请求处理完毕后，由过滤器组装的 18 字段不可变记录（Java record），是采集端与落库端之间唯一的数据载体。
审计动作（action）操作语义的大写英文编码，如 LOGIN、CREATE、HANDLE；同时落库中文动作名快照 action_name，避免字典变更影响历史可读性。
模块（module）操作所属业务域编码，如 IAM、RISK、MDM、MONITOR；显式取注解值，兜底取 URI 第三段大写。
对象类型 / 对象 ID被操作资源的类型（VEHICLE、USER、RISK_EVENT 等）与其主键字符串；对象 ID 有"SpEL → 响应体 → 路径末段"三级解析。
内容指纹（content_hash）对关键字段规范化串计算的 SHA-256 十六进制摘要，用于逐行内容核对；不是哈希链。
追踪 ID（trace_id）过滤器为每个请求生成的 32 位无横线 UUID，用于关联同一次请求的相关记录。
只追加（append-only）应用层只有 INSERT 语义、无任何修改/删除入口的工程约束；当前不包含数据库账号级 REVOKE。
语义切面AuditAspect 对 @AuditLog 做环绕，仅负责把 SpEL 解析出的对象 ID 经 request 属性转交给过滤器。
背压（CallerRunsPolicy）审计队列满时由当前业务线程亲自执行落库任务，以拖慢请求为代价换取"审计不丢"。

3. 典型场景

安全管理员 · 事后追责
排查"谁改了这条风控规则"
按对象 ID 或 URI 关键字检索，可定位到具体操作人、来源 IP、请求体（已脱敏）与操作结果，时间精确到毫秒。
安全管理员 · 登录安全
暴力破解与异常登录发现
概览卡直接展示区间登录失败次数；即使登录请求未通过鉴权过滤器，也会以请求体中的用户名留下失败记录。
运维 / 审计岗 · 合规检查
导出周期内操作清单
按时间区间（默认近 7 天，单次最大 90 天）、模块、动作、结果组合筛选，逐页核查处置、授权、配置变更是否合规。
平台运营 · 操作态势
操作量与成功率概览
区间操作总量、成功率、今日操作数、动作分布 Top5、高频操作人 Top10，辅助发现异常高频行为。
业务坐席 · 处置留痕
报警确认、工单流转可回溯
报警确认/解除、工单认领/分派/闭环、干预记录等 HANDLE 动作均带中文动作名与对象 ID 自动入库。
系统管理员 · 配置变更审计
字典、参数、权限变更追踪
用户/角色/字典/系统配置/电子围栏/风控规则的新增、修改、删除逐条可查，失败操作同样留痕。

4. 操作流程

4.1 一次被审计操作的端到端流程

① 发起请求
用户在前端执行登录、保存、删除、确认报警、分派工单等操作，HTTP 请求经 nginx 进入 platform-app。
② 审计过滤器包装
AuditFilter（order=0）用 ContentCaching 包装器包住请求/响应，生成 traceId，执行业务链。
③ 切面补语义
命中 @AuditLog 注解时，AuditAspect 用 SpEL 从方法入参提取对象 ID，暂存 request 属性。
④ 组装事件
请求返回后解析状态码与业务 code、脱敏请求体、解析操作人与对象，构造 AuditEvent 并发布。
⑤ 异步落库
AuditLogListener 在 auditExecutor 单线程池中调用 Service，计算 SHA-256 行指纹后插入审计表。
⑥ 检索核查
安全管理员在审计页组合筛选、查看统计与详情抽屉，含追踪 ID、脱敏报文与内容指纹。

4.2 审计员检索操作流程

进入菜单
系统管理 → 操作审计；页面挂载即带"近 7 天"默认区间加载明细与概览。
设置筛选
日期范围、操作人、模块、动作、结果、关键字（URI / 对象 ID / 错误信息）。
浏览列表
按时间倒序分页；失败行红色底纹；列表只给请求体前 200 字预览。
查看详情
抽屉中分基本信息、请求信息、结果信息、终端信息四组展示全字段。

4.3 登录失败的留痕分支

登录成功：HTTP 200 且 code=0 → action=LOGIN、status=1，userName 取请求体 username，objectType=USER。
登录失败：密码错误 / 账号停用 / 验证码失败等 → action=LOGIN_FAIL、status=0、errorMsg 落业务消息。该请求在 JwtAuthFilter 之前短路也没关系——AuditFilter 包在最外层，登录路径强制记录不依赖鉴权上下文。

5. 业务价值

  • 无侵入留痕：业务 Controller 只需在需要细化语义的方法上加 @AuditLog，所有写操作默认已被过滤器覆盖，新增模块零额外埋点即自动纳入审计。
  • 失败也可查：鉴权短路、业务异常、参数校验失败的请求同样记录，登录失败可追溯尝试账号与来源 IP。
  • 敏感信息不泄露：密码、令牌、密钥、身份证、动态口令类字段在落库前统一打码；手机号前 3 后 4 脱敏，审计表自身不成为泄密源。
  • 业务零影响：异步单线程落库 + 调用方运行兜底策略，审计组件任何异常只输出错误日志，不改变业务响应。
  • 可核对指纹：每行携带规范化内容的 SHA-256 指纹，为后续哈希链、外部存证等增强预留核对锚点。
  • 查询不干扰：审计模块自身路径默认排除，安全管理员高频翻页检索不会制造审计噪声、不污染统计。

技术篇

8. 总体机制

审计能力分两部分部署：采集端位于公共模块 platform-common（对所有业务模块生效，不依赖 module-audit），落库与查询端位于 module-audit。两端通过 Spring 的 ApplicationEvent 解耦——common 只发布不可变事件对象，不引用任何业务/审计模块的类。

采集层
common
AuditRegistrar 注册过滤器 order=0 AuditFilter 包装请求/响应、判定切点、脱敏、发事件 AuditAspect SpEL 提取对象 ID @AuditLog 方法注解 AuditEvent 不可变事件载体
解耦机制
ApplicationEventPublisher 进程内事件（非 MQ） @EventListener + @Async("auditExecutor")
落库层
module-audit
AuditLogListener 异步消费 AuditAsyncConfig 单线程池/队列 2000/CALLER_RUNS AuditLogService 组装实体、SHA-256 指纹、检索、统计 SysAuditLogMapper 只追加 Mapper
存储/展示
PostgreSQL traj.sys_audit_log（4 索引） AuditLogController /api/audit/**（audit:view） AuditLog.vue 检索/统计/详情

关键注册事实（代码确证）：

  • AuditRegistrar 与 AuditAspect 均带 @ConditionalOnProperty(prefix="audit", name="enabled", havingValue="true", matchIfMissing=true)：配置 audit.enabled=false 可整体关闭，默认开启。
  • 过滤器 URL 模式 /api/*，order=0，位于 JwtAuthFilter（order=1）外层。因此即使鉴权过滤器短路（无 Token / Token 失效），审计过滤器仍能在链路返回后记录匿名/失败访问。
  • 排除路径来自 AuditProperties.excludePaths，默认仅 /api/audit/**（Ant 模式），审计查询自身不再产生审计记录。

11. 审计切点：哪些操作会被留痕

是否记录由 AuditFilter.shouldNotFilter() 与 record() 两级决定，全部以代码为准：

请求类型是否记录判定依据
HTTP 方法非 GET/POST/PUT/DELETE不记录RECORD_METHODS 白名单（HEAD/OPTIONS/PATCH 等直接跳过）
命中 excludePaths（默认 /api/audit/**）不记录AntPathMatcher 匹配
POST /api/auth/login始终记录登录特判；成功记 LOGIN，失败记 LOGIN_FAIL；用户名从请求体取（失败也记）
GET 请求仅当方法标注 @AuditLog 时记录设计用途：敏感查询 / 导出 / 视频调阅（EXPORT/QUERY/VIDEO_VIEW）
POST / PUT / DELETE全部记录含成功与失败；无语义注解时走 HTTP 方法与 URI 兜底映射

11.2 无注解写操作的兜底语义

主数据模块（module-mdm 的车辆、终端、驾驶员、组织、绑定关系）的写方法未挂注解，但因 POST/PUT/DELETE 全记录规则仍被留痕，语义按以下兜底逻辑生成：

  • module：URI 第三段大写。如 /api/mdm/vehicles → MDM。
  • action：按 HTTP 方法映射 POST→CREATE、PUT→UPDATE、DELETE→DELETE。
  • objectType：路径资源段查固定映射表（vehicles→VEHICLE、terminals→TERMINAL、drivers→DRIVER、orgs/depts→DEPT、bindings→BINDING、users→USER、roles→ROLE、rules→RULE、events→RISK_EVENT、orders→WORK_ORDER）；末段为数字 ID 时取倒数第二段。
  • actionName：取动作字典缺省中文名（新增/修改/删除）。

设计取舍：显式注解优先（细化模块/动作/对象/中文名/SpEL 提取 ID），兜底映射保证"忘了加注解也不丢审计"，二者互补而非二选一。

11.3 登录与登出的两个细节

  • 登出 POST /api/auth/logout 显式标注 @AuditLog(module="AUTH", action="LOGOUT", actionName="退出登录")。注意 AuditAction 常量类中没有 LOGOUT 常量，LOGOUT 是以字面量直接使用的；过滤器动作名表也无 LOGOUT 项，其动作名完全依赖注解显式传入。前端 AUDIT_ACTIONS 字典含 LOGOUT 文案。
  • JWT 无状态，服务端不做令牌拉黑；登出仅有审计留痕意义（AuthController 注释明确）。

12. 采集与脱敏细节

12.1 请求/响应包装

AuditFilter.doFilterInternal() 使用 Spring 的 ContentCachingRequestWrapper / ContentCachingResponseWrapper 包裹原始请求响应，在 finally 中执行 record()，并始终调用 resp.copyBodyToResponse() 保证响应体回写。审计组装自身的任何异常被 catch 后仅输出 error 日志。

12.2 成功/失败判定

  • 解析响应 JSON：读取 code（业务码）与 message；非 JSON 响应时 bizCode 为 null。
  • success = HTTP 状态码 < 400 且（bizCode 为空 或 bizCode == 0）；status 落库 1=成功 / 0=失败，失败时 errorMsg 取 message（截断 500 字符）。

12.3 对象 ID 三级解析

① AOP SpEL 结果
AuditAspect 解析 @AuditLog.objectId（如 "#id"），写入 request 属性 ATTR_SEMANTIC；过滤器优先采用。
② 新增响应体
POST 请求且响应 Result.data 为数字/文本或含 id 字段时，从响应取新对象主键。
③ 路径末段数字
URI 末段匹配 1~19 位数字时直接作为对象 ID（覆盖雪花 ID 长度）。

12.4 操作人解析

  • 登录请求：从请求体 JSON 的 username 字段取（登录失败也要知道在试谁的账号）。
  • 其他请求：取 request 属性 ATTR_USER（JwtAuthFilter 鉴权成功后写入的 UserInfo）的 username；未认证访问为 null，前端展示为"匿名"。

13. 异步落库机制

事件发布与落库通过 Spring 容器内事件机制衔接（非消息队列）：

  1. AuditFilter 构造 18 字段的 AuditEvent record，调用 ApplicationEventPublisher.publishEvent()；
  2. AuditLogListener.onAuditEvent() 以 @EventListener 订阅、@Async("auditExecutor") 异步执行；
  3. AuditLogService.saveEvent() 逐字段拷贝为 SysAuditLog，计算 contentHash 后 auditLogMapper.insert()。
线程模型
auditExecutor 核心线程=最大线程=1：单实例内事件严格按发布顺序落库（同实例时间有序）
缓冲队列
有界队列容量 2000；突增流量先排队
拒绝策略
CallerRunsPolicy：队列满时由业务线程自己执行落库，退化为同步、牺牲响应时间但优先不丢审计
关停行为
waitForTasksToCompleteOnShutdown=true，awaitTerminationSeconds=10，优雅停机尽量排空队列
失败处理
Listener 内 catch 全部异常，仅 log.error（带 uri/action），不重试、不抛出；业务无感知

17. 检索与统计实现

17.1 分页检索

使用 MyBatis-Plus LambdaQueryWrapper 动态拼装：between 时间区间；userName/module/action 为精确匹配（eq，空串不拼）；status 精确匹配；keyword 为 AND 嵌套 OR 的三字段 like；orderByDesc(createTime).orderByDesc(id)。AuditLogVO.from() 映射时将 requestBody 截为 200 字符 bodyPreview。

17.2 区间统计

  • total：区间总量；success：status=1 数量；successRate：四舍五入保留 1 位小数（总量为 0 时返回 100.0）。
  • loginFailCount：action=LOGIN_FAIL 计数。
  • todayCount：当日 00:00 至当前时刻计数（不受传入区间影响）。
  • actionDist：Mapper 注解 SQL GROUP BY action ORDER BY count DESC。
  • topUsers：GROUP BY user_name WHERE user_name IS NOT NULL ORDER BY count DESC LIMIT 10。

17.3 统计 SQL 口径（Mapper 注解实现）

-- 动作分布
SELECT action AS name, COUNT(*) AS count
FROM traj.sys_audit_log
WHERE create_time BETWEEN #{start} AND #{end}
GROUP BY action
ORDER BY count DESC;

-- 高频操作人 Top10（排除匿名）
SELECT user_name AS name, COUNT(*) AS count
FROM traj.sys_audit_log
WHERE create_time BETWEEN #{start} AND #{end}
  AND user_name IS NOT NULL
GROUP BY user_name
ORDER BY count DESC
LIMIT 10;

其余统计项（total/success/loginFail/todayCount）由 Service 用 LambdaQueryWrapper 的 count 拼条件得到，成功率在 Java 侧计算并统一保留 1 位小数，避免 SQL 方言差异。

18. 前端实现要点

  • 默认区间：页面初始化即取"今天 00:00 ~ 此刻"为结束、前推 7 天为开始，自动拉取明细与统计，与后端 resolveRange 默认值双保险。
  • 字典渲染：模块/动作/结果均通过 dict.ts 的 labelOf 映射中文；无匹配时原样显示编码（保证新模块上线后页面不空白）。
  • 失败行高亮：表格行依据 status=0 加红色底纹 class。

19. 定时任务

无。审计为纯事件驱动链路：请求到达即采集、异步即落库；统计为查询时实时聚合，不做物化汇总；模块内没有任何 @Scheduled 任务，也不依赖 Redis/MQ。

留存与归档（如按月分区、历史转冷存、到期清理）当前在代码与脚本中均未实现，属后续合规增强项，不在 F34 上线范围内。

20. 防篡改设计现状（只陈述代码确证事实）

20.1 已具备

  • 只追加写入：AuditLogController 只有 GET 端点；module-audit 代码中不存在 update/delete 的业务调用；SysAuditLog 不继承公共实体、无软删字段；Mapper 注释明确"只追加，无 update/delete 方法"（指自定义方法；BaseMapper 框架能力仍在，但无业务入口）。
  • 行级内容指纹：落库前对规范化字符串计算 SHA-256（JDK 内置 MessageDigest，HexFormat 转十六进制），规范串以 "|" 连接 11 个字段：traceId | userName | module | action | objectType | objectId | requestMethod | requestUri | status | resultCode | createTime(yyyy-MM-ddHH:mm:ss.SSS)，null 统一转空串。
  • 失败也留痕：业务失败、鉴权失败均入库，无法通过"制造报错"绕过操作记录。

20.2 明确未做（不得在合规表述中夸大）

  • 没有哈希链：05-audit-tables.sql 对 content_hash 的注释原文为"行级防篡改指纹（本期不做哈希链）"。行间不首尾相接，单行被改后无法通过链校验自动发现，只能事后用相同算法重算比对。
  • 指纹覆盖范围有限：规范串不含 queryString、requestBody、errorMsg、clientIp、userAgent、costMs、actionName；修改这些未入 hash 的列不会导致指纹变化。content_hash 的定位是"关键字段快照核对"，不是全行完整性证明。
  • 没有数据库账号级隔离脚本：初始化脚本中未见对审计表 REVOKE UPDATE/DELETE 的 GRANT 设计；拥有库写权限的账户技术上可直接改表，防护依赖运维侧 DB 权限管控（待核实：生产环境是否已配置 INSERT-only 账号）。
  • 没有 WORM 存储、没有外部存证/上链、没有异地副本校验；create_time 取应用时钟，无防回拨措施。
  • Listener 落库失败仅记日志、不重试：极端情况下（DB 长时间不可用且队列溢出/进程重启）会丢失审计事件，没有 outbox 或本地落盘补偿。

21. 边界行为与常见问题

情形实际行为（代码确证）
不传时间参数后端强制补为近 7 天，不允许全表扫描式查询

GET 请求未加注解不记录（绝大多数查询由此豁免，避免查询风暴）
POST 响应体不是统一 Result按 HTTP 状态码判定成功，result_code 落 NULL

审计落库数据库短暂不可用Listener 报错记日志；队列积压；持续高压时 CALLER_RUNS 反压到业务线程
同一秒内多条事件排序列表按 create_time DESC, id DESC 双键排序，同毫秒内以雪花 id 决定先后
processing-service（FastAPI）的接入请求使用 X-Service-Token 的服务间调用若经 platform-app 的 /api/** 同样被过滤器记录；直发 FastAPI 的 /api/ingest/** 不经过本过滤器（规划在 F38 统一网关纳管）
Actuator 端点（/actuator/health）路径不以 /api 开头，不匹配 /api/*，天然不记录；容器健康探针不产生噪声
分页 size 传超大值沿用平台分页参数的统一上限约束；审计查询本身不做额外特殊处理
对象 ID 是 UUID/业务编号三级解析的"路径末段"只认 1~19 位数字；非数字 ID 依赖注解 SpEL 或响应体提取，否则 object_id 留空但其余字段照常记录
批量操作（一次请求影响多行）当前审计粒度为"一次请求一条"，批量删除/启停只落一条记录，对象 ID 取路径或响应，不逐行展开；需要逐对象留痕时须在业务侧改造为多次调用或在 request_body 中留存 ID 集合（截断内）
查询结果为空正常返回空页 / 零值统计（成功率在无数据时给 100.0），不报错
动作/模块出现字典外的新值后端不校验枚举字典，任意字符串可入库；前端回显原编码，统计接口照常 GROUP BY——保证审计记录不被字典演进阻塞

22. 选型依据

选择理由备选与取舍
Servlet Filter 作为主采集点能包住整个请求链（含鉴权短路），可靠拿到响应状态与耗时；与业务代码完全解耦纯 AOP 拿不到未进入 Controller 的请求、拿不到响应结果；纯拦截器对非 MVC 链路覆盖弱
AOP 切面补 SpEL 语义过滤器层无法访问 Controller 方法入参，SpEL 可精确提取 #id、#req.vehicleId 等业务主键在 Filter 用反射取参脆弱且随参数顺序失效；切面 + request attribute 传价是两层能力互补
Spring ApplicationEvent 解耦零中间件依赖，common 不反向依赖业务模块；同步发布/异步监听切换只在注解Kafka 可跨进程、可回放，但当前单体部署无必要；代价是应用崩溃丢失在途事件
单线程顺序消费实现简单、同实例天然时间有序、无并发写竞争多线程吞吐高但乱序；审计写量远低于业务峰值，单线程 + 2000 队列 + CALLER_RUNS 已够
CALLER_RUNS 拒绝策略审计场景"不丢"优先于"快"：队列满时让业务线程同步落库，形成背压DISCARD 会静默丢审计；AbortPolicy 会向业务抛异常，均不符合审计目标
SHA-256 行指纹JDK 内置、无外部依赖、碰撞概率可忽略；为逐行核对与未来哈希链预留国密 SM3 是等保/国密方向的可选替换（F37 规划），算法集中在单一私有方法，替换成本低

24. 上线验收清单

  1. 无权限账号访问 /api/audit/logs 返回 403；有权限账号可正常分页。
  2. 任意 POST/PUT/DELETE 业务请求后，审计表新增一条记录，字段与请求实际一致（含耗时、IP、UA）。
  3. 错误密码登录产生 LOGIN_FAIL 记录，user_name 为请求中用户名，status=0，error_msg 有值。
  4. GET 请求在无 @AuditLog 时不产生记录；/api/audit/** 自身查询不产生记录。
  5. 请求体含 password/newPassword/token/idCard 等键时，落库值为 ***；手机号形如 138****0001。
  6. 每条新记录 content_hash 为 64 位十六进制；用相同规范化算法离线重算结果一致。
  7. 检索默认区间为近 7 天；跨度 >90 天、起止倒置均被后端拒绝。
  8. 统计接口返回总量、成功数、成功率、登录失败数、今日数、动作分布、Top10 用户，数值与 SQL 直查一致。
  9. 停止数据库后执行业务写操作：业务在队列未溢出时不受影响；恢复后队列排空（或高压期观察到 CALLER_RUNS 延迟）。
  10. 设置 audit.enabled=false 重启后不再产生任何审计记录；恢复默认（删除配置）后自动生效。
  11. 对象 ID 提取三路径分别验证：注解 SpEL 命中、POST 响应 data.id 命中、PUT/DELETE 路径末段命中，详情中对象类型与 ID 正确。
  12. X-Forwarded-For 多级代理链场景下，client_ip 取首个地址；无该头时回退 X-Real-IP / remoteAddr。
