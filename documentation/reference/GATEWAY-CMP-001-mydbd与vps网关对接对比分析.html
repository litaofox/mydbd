mydbd 平台与 vps 车载网关对接对比分析

文档编号：GATEWAY-CMP-001 ｜ 平台侧：D:\ProgramData\mytraeprojects\mydbd ｜ 网关侧：D:\ProgramData\mytraeprojects\vps ｜ 用途：对接决策 ｜ 配套文档：GATEWAY-REF-001 网关功能接口与标准协议分析

迁移说明：本报告原编制于 2026-10-05，同日自 docs/html 归档迁入正式文档库 reference 分区（编号 GATEWAY-CMP-001）。迁移仅更换文档库统一顶栏/样式入口、补充本说明与页脚，正文、结论卡片、矩阵表及原有内嵌排版均保持原貌；文末对 GATEWAY-REF-001 的同目录相对链接保持有效。

0. 结论摘要（TL;DR）

总体判断：协议语义“对得上”，传输范式“对不上”——不能直接对接，需要增加一个适配层（中等工作量，无需改造终端）

① 传输范式不匹配（根因）：vps 网关对平台的输出是 Kafka 事件总线（8 个 Topic）+ 少量同步 HTTP 指令接口；mydbd 目前只有同步 HTTP JSON 批量推送（POST /api/ingest/traj），没有任何 MQ。

② 定位字段语义基本可对接，但必须做单位换算（速度 m/h→km/h、里程 m→km）、标识映射（手机号↔identity_code、truckId↔车辆）、报警位图扩容（32 位 Long vs smallint），且会丢失车辆状态/附加项等字段。

③ 报警/主动安全：编码体系不同（网关 101001/102001 数字码 vs 平台 DSM_FATIGUE/ADAS_FCW 字符串码），需要字典映射 + 开始/结束状态机 + warnId 附件关联。

④ 图片：traj_gps_photo 表结构已按网关同构预留，但无任何写入入口、无文件存储/服务能力；苏标附件有 Kafka 出口可订阅，立即拍照的照片元数据无 Kafka 出口（需网关侧小改或跨库读取）。

⑤ 视频：mydbd 完全没有 JT/T 1078 能力（无收流/信令/流媒体）；不需要自己收流——直接复用独立部署的 vps-video，平台只调 18001 信令拿 ws-flv 地址、前端 flv.js 播放即可，契合 F06/F07“边缘触发、按需调阅”。

⑥ 文本：网关只有“平台→终端”的 TTS 下行（0x8300），无终端上行文本；平台需在通知中心新增一个 JT808-TTS 通道。

推荐：方案 A —— 引入 Kafka，新增轻量“接入适配服务”（或 processing-service 内置 consumer）订阅网关 Topic，完成映射后复用现有入库与 CEP 链路；视频/拍照/文本经 platform-app 调用网关 18001 REST。

3. 逐类信息对比

3.1 定位信息

网关侧契约

  • Topic jt808_gps_topic，key=truckId，载荷 PositionInfo{GpsHead, GpsInfo}，0x0200/0x0704/0x0801 均汇入；
  • 经纬度已为“度”；speed 单位 m/h（=1/100 km/h 数值×100）；mileage 单位米；时间 GMT+8；
  • 携带 alarmFlag（32 位位图 Long）、status（车辆状态位图）、recordSpeed、delay 补报、gpsType(10/11/12)、trackId、附加项数组等。

mydbd 现状

  • 唯一入口 POST /api/ingest/traj（X-Service-Token）：{identityCode, plateNo, points:[{gpsTime,lng,lat,speed,direction,altitude,alarmFlag,mileage}]}，批量写 traj.traj_gps_point（5000/批），旁路 CEP（异常不阻断）；
  • 表列：speed integer（业务口径 km/h）、mileage numeric(12,2)（km）、alarm_flag smallint（实际当 0/1 用）、location geometry(Point,4326)；无 status、recordSpeed、卫星数、信号、补报、gpsType、trackId、附加项列。

差距

  1. 传输方式：Kafka vs HTTP，需消费者；
  2. 单位：speed、mileage 必须换算（否则速度放大 100 倍、里程放大 1000 倍）；
  3. 报警：alarmFlag 32 位位图塞入 smallint 会溢出/丢语义，且平台目前仅 0/1；
  4. 标识：网关 truckId(Integer 内部主键)/手机号 vs 平台 identity_code/plate_no，需绑定换算（见第 4 章）；
  5. 信息损失：ACC/转向/制动等 status 位、附加项（里程/油耗/信号/苏标报警原始块）无处落。

建议 适配层消费 Topic 后转换并调用现有入库逻辑（复用 db.insert_gps_points 与 cep_engine.evaluate_points）；工作量 M。alarm_flag 列建议升级为 bigint（或新增 status/alarm_raw 列保留位图，alarm_flag 保留 0/1 供旧逻辑）；是否补 status/附加项扩展列见第 9 章决策项。

3.2 报警 / 主动安全预警

网关侧契约

  • Topic jt808_warn_topic 载荷 WarnInfo：warnId(32UUID)、typeId(101001 等数字码)、rawType(如 0x64_0x01)、alarmLevel(1一级/2二级)、开始/结束位置与状态、warnIdentity(16B hex)、附件数量/已收/已传、标志状态（开始 1/结束 2）；
  • 附件完成另有 jt808_warn_media_topic（MediaInfoDto，含 warnId、fileType、url、fileStatus）。

mydbd 现状

  • mon.risk_event：event_code(字符串如 DSM_FATIGUE/ADAS_FCW)、event_source(ADAS/DSM/北斗/vendor)、risk_level(1低2中3高)、media_url 单字段、confidence、fence_id/rule_id 等；由 POST /api/analysis/video 占位接口（信号事件，无真实媒体）与样例导入写入；
  • traj.traj_warn_info：source_id、type_id(integer)、起止时间/位置/速度、warn_continue_mark、rule_id、handle_status；目前无生产代码写入（仅表与字典 base_warn_type 1–5）；
  • 无报警开始/结束状态机、无 warnId、无一事件多附件模型。

差距

  1. 事件码字典不同：101001↔ADAS_FCW、102001↔DSM_FATIGUE 等需建映射表；rawType(外设字节) 建议原样保留；
  2. 级别方向相反：苏标 1 级为高（强制报警）、2 级为低；平台 1低/2中/3高——不能直接拷贝；
  3. 状态机缺失：网关有开始/持续/结束，平台为单点事件，需用 warnId 做开闭环合并（写 traj_warn_info 起止）；
  4. 附件关联缺失：risk_event.media_url 只有一个 URL，苏标一警多附件需新增子表或以 warnId 关联媒体表；
  5. 平台 CEP 自产事件（SPEED/FATIGUE/围栏）与网关上报事件需用 event_source 区分（如 vendor/jt808），避免重复告警与重复扣分。

建议 适配层按 warnId 落 traj_warn_info（source_id=warnId、type_id 存网关数字码），同时按映射字典生成 mon.risk_event 进入既有分级/通知/工单链；附件单独建 mon.risk_event_media 或复用照片表加 source/ warn_id 列。工作量 M（字典+状态机是主要工作）。

3.3 图片

网关存在两条互不相通的图片路径：

路径网关行为平台可见性
① 平台主动拍照 0x8801→0x0805→0x0801照片落网关本地盘 + MySQL vps_gps_photo；gps_topic 发 gpsType=11 关联点（不含 URL/文件名）无 Kafka 出口，平台拿不到照片元数据
② 苏标报警附件 9208→1210/1211/码流/1212文件服务落盘，完成发 jt808_warn_media_topic（含 url、fileType、fileSize、warnId）可直接订阅，URL 指向 18009/static

mydbd 现状

  • traj.traj_gps_photo 字段（photo_id、truck_id、identity_code、channel_id、file_name、url、photo_size、track_id、task_id、req_source、cmd/gps/receive/create_time）几乎照搬 vps_gps_photo，已预留；
  • 但无任何写入接口/代码、无对象存储、无静态文件服务；/api/analysis/video 的 clipUrl 只是字符串占位，无真实上传能力。

差距与建议

  1. 苏标附件：适配层订阅 warn_media → 下载/转存文件（见下）→ 写照片/媒体表并以 warnId 回连 risk_event；M
  2. 主动拍照：需在网关侧做小改造（拍照入库后向 gps 或新增 media Topic 补发含 URL 的事件），或由平台适配层以只读账号轮询 vps_gps_photo（不推荐跨库耦合）；S–M
  3. 存储三选一：(a) 平台与网关共享挂载卷；(b) 适配层把文件转存 MinIO/OSS 并改写 url（推荐，解耦且利于备份/鉴权）；(c) 反代 18009/static 并加访问控制（最快）；
  4. URL 可达性、时效与数据权限（按车辆归属校验后才能取图）必须同步设计。

3.4 视频

项网关（vps-video + 18001）mydbd
终端收流RTP over TCP 10780/10781/10782，H264/H265+多音频无
信令9101/9102、9201/9202、9205/1205（经 REST 触发）无
浏览器播放ws-flv 20780/20781/20782无播放器集成
建设规划已实现并可用SYS-DBD-001：F06（1078 接入，v0.3）、F07（截图片段按需调阅）“待建设”，原设想含 ZLMediaKit

结论与建议：平台无需自建收流/转码（避免重复造轮子与 FFmpeg 运维成本）：

  1. 独立部署 vps-video（与终端网络可达）；platform-app 新增“视频调阅服务”封装 18001 的 5 个视频 REST（实时/停止/回放/停止回放/资源列表），把返回的 ws 地址经平台反代 + 时效签名给前端（vps-video 的 ws 本身无鉴权，不可裸放）；
  2. 前端集成 flv.js（H265 需支持网关私有增强 FLV 的播放器版本）；对讲页面走 20782（PCM 640B/帧）；
  3. 与 F07 对齐：报警事件详情页提供“调阅实时/回放/拍照”按钮（边缘触发 + 按需调阅，终端不传全量视频，与既定业务规则一致）；调阅审批、水印（F25）在平台侧实现；
  4. 若决策替换 vps 改用 ZLMediaKit，则需在 mydbd 侧自建 808/1078 信令（等同 F01+F06 全量建设，L），不建议在已有可用网关时选择。

推荐路径工作量 M–L（主要在前端播放器、反代鉴权、调阅审批）。

3.5 文本

  • 网关：仅“平台→终端”方向：POST /api/command/{phone}/tts → 0x8300 文本信息下发（type 1 通知/2 服务、sign 标志位、content 文本）。终端→平台无独立文本通道（0x0900 透传仅编解码，业务未消费）。
  • mydbd：无任何文本下发功能；通知模块（module-notify）已有 SMS/Voice/Push 通道。

建议 在通知中心新增 JT808-TTS 通道：通知规则命中后经 platform-app 调网关 /tts；通道参数为终端手机号、文本、类型。工作量 S。终端上行文本本期不支持（如确有需求，再评估 0x0900/0x0301）。

3.6 心跳与在线/离线态

  • 网关：jt808_heartbeat_topic（0x0002）、jt808_offline_topic（断链 type=1，无上线消息）；
  • mydbd：大屏以“最近 5 分钟有定位点”判定在线（refTime 口径），无接入侧连接事件。

建议 适配层维护终端会话状态：消费 command_topic 的 0102（鉴权成功）视为上线、offline 立即置离线、心跳刷新存活；写终端在线状态供大屏精确展示，“最近有点”保留为兜底口径。S。

3.7 原始报文（审计留痕）

网关 jt808_raw_hex_topic 提供白名单车辆的原始 hex 报文（心跳除外，按 monitor 配置）。mydbd 有操作审计模块但无报文留痕。建议二期按需订阅落冷存储，供协议排障与争议追溯；S，非首期必需。

4.4 标识体系映射

网关以 手机号（phoneNumber=鉴权码）+ truckId（网关库自增整数）标识；mydbd 以 identity_code（终端唯一）+ 车辆/终端绑定标识。现状种子数据中 identity_code 为 TERM_001 一类编码，手机号在 traj_terminal.sim_account。

对接前必须统一（二选一）：① 将网关注册手机号写入/同步为 traj_terminal.identity_code（推荐，天然全局唯一、协议可见）；② 适配层以 sim_account 反查终端，再经 traj_vehicle_terminal 定位车辆与归属组织。同时需把网关 vps_base_truck 白名单与平台车辆档案做一次性同步，未登记车辆网关侧直接拒绝注册。

4.5 时间、坐标系与其他口径

  • 时间：网关全部 GMT+8、格式 yyyy-MM-dd HH:mm:ss/BCD；平台 timestamp，入库时统一带 +08:00 处理；
  • 坐标：终端上报为原始卫星坐标（通常 WGS-84/北斗）。平台底图/逆地理用高德（GCJ-02，geocode 组件已配高德 key）。网关参考 StarRocks 表同时保留原始与高德(lon_g/lat_g)、百度(lon_b/lat_b)三列，说明纠偏责任在下游。建议平台入库保留原始坐标（4326 语义按 WGS-84 标注），出图时统一转 GCJ-02，避免重复转换（见决策项）；
  • 速度精度：0x0200 原始速度为 1/10 km/h，网关 JSON 已乘 100 得 m/h；平台 integer km/h 会损失小数，如驾驶评分需要更高精度，可新增 numeric 列；
  • 鉴权：适配层→processing-service 带 X-Service-Token；platform-app→网关 18001 目前无鉴权，走内网/网关白名单，建议要求网关侧加服务令牌校验。

8. 风险、合规与数据权限

  1. 数据权限锚点不变：所有车辆数据可见范围以车辆归属组织（traj_vehicle.dept_id，经 traj_vehicle_terminal→traj_terminal 到 identity_code）为锚点；网关传入的车牌/归属不得改变这一口径，严禁按车牌省份（province_code）做数据过滤；
  2. 媒体越权：网关 /static 与 ws-flv 均无鉴权，禁止把其裸地址直接给浏览器；必须经平台反代 + 登录态/归属校验 + 时效签名；
  3. 指令安全：18001 无应用鉴权，视频/拍照/TTS 为可影响行车设备的指令，需内网隔离 + 服务令牌 + 操作审计（复用 IAM/审计模块），调阅审批走 F25；
  4. 敏感配置：网关配置文件含明文数据库口令（详见配套文档第 5 章），对接时以最小权限只读账号访问、口令经密钥管理注入，不得复制到本项目仓库或文档；
  5. 重复告警/重复评分：网关报警与平台 CEP 可能对同一行为双重计分，需以 event_source/rawType 去重或制定优先级；
  6. 可靠性语义：网关校验失败不丢包（可能有脏数据）、附件进度仅内存（文件服务重启需终端重传）、无上线消息——适配层均需容错；
  7. 坐标合规：对外展示用 GCJ-02；入库保留原始坐标时需在元数据注明坐标系，避免混用造成位置偏移。
