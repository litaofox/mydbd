SYS-DBD-001 项目总体设计

文档编号 SYS-DBD-001|版本 v1.0.0|发布日期 2026-10-05|事实基准 2026-10-05 源代码

关联文档：ARC-DBD-001 系统架构设计　DDL-DBD-001 数据库设计　DEP-DBD-001 部署与运维手册　FUNC-DBD-001 功能清单与建设规划

1 项目背景

道路货运车辆正规模化换装"单北斗视频智能终端"。该类终端集成 GNSS 定位、CAN 总线读取、ADAS（高级驾驶辅助）与 DSM（驾驶员状态监控）能力，在行驶过程中持续产生定位轨迹与驾驶行为事件。行业主管部门、运输企业与保险机构需要基于这些数据掌握车辆运行状态、干预高风险驾驶行为，并以风险减量为目标开展安全管理与费率浮动。上述业务背景与数据量级的完整论述，见业务蓝图BLUEPRINT-001 导航系统数据采集与应用平台设计。

mydbd（北斗导航数据业务平台）是这一蓝图的数据底座在当前阶段的工程实现，承担三类职责：

  • 接得住：接收终端上报的北斗定位点与 DSM/ADAS 预警信号，落入 PostgreSQL/PostGIS 持久化；
  • 看得见：在地图上实时呈现车辆位置与报警态势，支持历史轨迹回放与监控大屏；
  • 管得闭：预警信号经规则引擎定级形成风险事件，驱动处置工单、坐席干预、通知与驾驶评分，形成"感知—预警—干预"闭环。

口径说明：蓝图规划接入规模为试点 1 万辆 → 区域 10 万辆 → 百万级。当前版本（代码版本 0.1.0）为单节点内网演示/试点基线，终端接入以 HTTP 推送与内置模拟器为主，JT/T 808/1078 协议网关属于后续规划（见 MOD-DBD-014）。本文件严格区分"现状"与"规划"。

2 项目定位与目标

2.1 项目定位

mydbd 是专注于北斗导航数据核心业务的独立平台，不依赖公司其他业务系统即可独立部署运行。平台对上服务于安全监控坐席、企业车队长与平台管理员；对下面向北斗车载终端与等价格式的数据推送方。平台本身不生产视频、不替代终端侧识别，也不是面向公众的互联网服务。

4 系统边界

4.1 做什么（系统职责内）

  • 北斗定位数据的接入、解析与持久化：现状支持样例 CSV 批量导入、终端/第三方系统 HTTP 批量推送（POST /api/ingest/traj，服务令牌鉴权）与进程内模拟器；
  • 轨迹查询、历史回放、最新位置与在线状态统计；
  • 终端报警接入与报警中心：报警列表、808 报警位解析展示、确认/解除闭环；
  • DSM/ADAS 预警信号接入：终端/处理服务上报"信号码 + 置信度 + 抓拍/片段引用"，平台按可配置规则完成定级、冷却去重并落风险事件；
  • 电子围栏（圆形/多边形）的绘制、进出判定与告警；
  • 风险事件 → 处置工单 → 坐席干预的流程管理，含 SLA 时限与超时升级；
  • 站内消息与 WebSocket 实时推送，短信/语音/App 推送的通道接口预留；
  • 驾驶安全分（T+1 全量计算 + 手动重算）、风险趋势与画像；
  • 用户/角色/菜单/按钮权限与五级数据范围、操作审计、系统配置与数据字典。

4.2 不做什么（明确排除）

  • 不做终端侧视觉识别：疲劳、分心、前向碰撞等 DSM/ADAS 识别发生在终端边缘侧；平台 risk_engine 只对上报的信号候选做规则分级，当前为占位实现；
  • 不做全量视频汇聚与全量视频分析：平台不接收、不存储全天候视频流，CEP 引擎不消费视频流；
  • 不做公网地图与导航消费服务：地图瓦片依赖高德/Leaflet 展示能力，平台不提供 C 端导航；
  • 现状不做 JT/T 808/1078 协议接入：不做终端 TCP 长连接、注册鉴权、心跳、指令下行与 1078 实时拉流（规划见 MOD-DBD-014、MOD-DBD-016）；
  • 不做轨迹深度加工：现状不做地图匹配、坐标转换、在线压缩、异常点剔除（规划见 MOD-DBD-015）；
  • 不替代企业既有 OA/财务/保险核心系统，工单与评分数据仅通过接口/报表对外提供。

4.3 边缘触发 + 按需调阅规则

视频与图像数据遵循"边缘触发 + 按需调阅"（该原则在 processing-service/app/services/risk_engine.py 模块说明中明文确立），具体口径：

边缘侧（车载终端）
  • 持续运行 DSM/ADAS 识别，事件触发才上报，而非持续上报视频；
  • 每条预警信号携带事件码、时间、位置、置信度与抓拍截图（蓝图要求 1~3 张）；
  • 预警时刻前后约 10 秒的短视频片段仅在平台调阅/事件取证时上传（samples/dashcam_clips.zip 为该形态的演示素材）。
平台侧（mydbd）
  • 只接收信号、抓拍图与经授权调阅的短视频片段；
  • 规则引擎（CEP）对结构化信号做分级与去重，不对视频做全量 AI 分析；
  • 坐席按需调阅片段，调阅动作进入操作审计。

待核实：业务蓝图对"事件触发自动上传片段"的规划口径为前后各 15~30 秒（720P 起步），当前演示素材与界面按约 10 秒片段组织。正式接入真实终端时，片段时长以终端招标技术要求与 JT/T 1078 对接方案为准，本文不将演示口径等同于最终规格。

5 约束条件

类别约束性质
行业协议JT/T 808-2019《道路运输车辆卫星定位系统 终端通讯协议及数据格式》：定位/报警/指令方向；ADAS/DSM 扩展遵循地方补充协议（苏标、川标、粤标等）规划合规方向 现状为 HTTP 接入
视频协议JT/T 1078-2016《道路运输车辆卫星定位系统 视频通信协议》：实时视频调阅与事件片段上传；设备标准另涉 JT/T 794、GB/T 19056规划合规方向
空间数据PostgreSQL 16 + PostGIS 3.4，轨迹点使用 geometry 与 GIST 空间索引；围栏判定依赖 PostGIS 空间函数现状已落地
部署形态内网单机部署：数据库与后端端口仅绑定 127.0.0.1，仅门户 8090 对用户网段开放；无公网依赖（地图瓦片除外）现状已落地
浏览器面向 Chromium 内核现代浏览器（含现场内嵌 Electron/工控浏览器）；前端为 Vue3 SPA，不兼容 IE工程约束
安全合规等保三级、《数据安全法》《个人信息保护法》方向：现状已具备 JWT、MFA(TOTP)、密码哈希、操作审计与登录失败锁定；分级防护、密评等为规划项现状部分具备
运行资源四容器内存上限合计约 2.2GB（pg 1G / app 768M / py 384M / nginx 64M），宿主机建议 4GB 以上内存工程约束 详见 DEP-DBD-001
弱网与补传蓝图要求终端本地缓存 ≥72 小时、断网恢复断点续传；平台侧现状按入库即受理设计，补传识别为规划能力规划

6 总体业务流程

主链路：终端采集 → 接入入库 → 规则定级 → 范围推送 → 坐席处置 → 闭环回写。

终端采集
1Hz 北斗定位点；DSM/ADAS 边缘识别命中时产生预警信号，带时间/位置/置信度/抓拍
接入与入库
现状：HTTP ingest / 模拟器写入 PostGIS；规划：JT/T 808 网关解码接入
CEP 规则定级
处理服务旁路评估启用规则与围栏，冷却去重后写风险事件；异常不阻断入库
按范围推送
WebSocket 每秒推位置、id 游标增量推风险/报警，按会话用户 deptScope 过滤
坐席接单
风险事件生成工单，调度器向在线坐席派发建单通知；SLA 时限起算
干预处置
电话提醒、安全教育、停运等动作留痕；必要时按需调阅事件片段取证
闭环与评分
工单闭环回写；每日 01:00 T+1 全量计算驾驶安全分，沉淀趋势与画像
统计与运营
大屏/报表按数据范围聚合，支撑企业安全管理与风险减量运营

7 术语表

术语含义
风险事件预警信号经规则引擎定级后落库的记录（mon.risk_event），含事件码、车牌、时间、位置、风险等级、规则来源；是工单生成的输入
预警信号（信号）终端侧 DSM/ADAS 识别产出的原始事件候选（信号码 + 置信度），在平台侧是否落事件由启用规则与冷却窗口决定
终端报警终端按 808 报警标志位上报的报警（traj_warn_info），报警中心对其确认/解除；与风险事件是两类数据
处置工单风险事件达到建单条件后生成的派工记录（risk_work_order），有待处理/处理中/已闭环等状态与 SLA 时限
deptScope（数据范围）登录用户可见数据的部门 ID 集合：null=全部，空集合=不可见任何数据，非空集合=范围内可见；随 UserInfo 在鉴权时装载
CEPComplex Event Processing，复杂事件处理。本项目指处理服务中的风控规则引擎（cep_engine），对定位点/信号做规则匹配、分级与去重
电子围栏在地图上划定的圆形或多边形区域，车辆进出区域触发判定与告警；基于 PostGIS 空间查询实现
在线率在最近一个可配置时间窗口（缺省 5 分钟）内有定位点上报的车辆占比；窗口参数实时读 sys_config
归属锚点判定一条业务数据归属组织所用的唯一外键，本项目为 traj_vehicle.dept_id；所有车辆类数据经车牌关联车辆表取锚点过滤
fail-closed无法确定用户身份或数据归属时按"不可见"处理的默认策略，与 fail-open（放行）相对
identityCode（身份码）终端/设备身份标识，定位点以身份码关联终端与车辆；HTTP 接入的必填字段
DSMDriver Status Monitoring，驾驶员状态监控：疲劳、分心、抽烟、接打电话等
ADASAdvanced Driver Assistance Systems，高级驾驶辅助：前向碰撞 FCW、车道偏离 LDW、车距过近 HMW 等
JT/T 808-2019道路运输车辆卫星定位系统终端通讯协议及数据格式，行业标准；平台协议网关的规划合规目标
JT/T 1078-2016道路运输车辆卫星定位系统视频通信协议；实时视频调阅与事件片段上传的规划合规目标
PostGISPostgreSQL 的空间数据库扩展，提供 geometry 类型、GIST 空间索引与空间关系函数
雪花 ID19 位长整型全局 ID。前端 JavaScript number 无法保真，后端 VO 统一用 ToStringSerializer 序列化为字符串
冷却窗口同一规则同一车辆在设定秒数内重复命中只落一次事件的去重机制，避免信号风暴
SLAService Level Agreement，工单处置时限；超时由调度器每分钟扫描并物化超时/升级标记
服务令牌内部服务调用密钥（X-Service-Token / SERVICE_TOKEN），用于 ingest、视频分析等机器对机器接口
T+1 评分每日 01:00 对前一天数据全量重算驾驶安全分；与手动重算共用互斥锁
MFA / TOTP多因子认证 / 基于时间的一次性密码。已开通账号登录需二次验证（中间令牌 5 分钟有效）

8 数据权限强制规则（总体规则）

本节为总体强制规则，效力覆盖全部模块与后续全部功能开发：查询、分析、报表、导出、实时推送、异步任务均适用。任何功能设计文档必须写明数据范围口径；任何代码评审必须核对数据权限是否落实。例外须在设计文档显式说明并经审批。

8.1 默认强制，无一例外（fail-closed）

  1. 全部业务数据访问默认受登录用户 UserInfo.deptScope 约束：
    • null = 全部数据（超级管理员，或角色数据范围=全部），不加部门条件；
    • 空集合 = 不可见任何数据（返回空列表、空页或计数 0）；
    • 非空集合 = 按部门/车牌集合过滤。
  2. 只有超级管理员与数据范围=全部的角色不受限；不存在"某个接口特殊、先不过滤"的默认许可。
  3. fail-closed：无法确定用户（如 WebSocket 握手未写入 uid）或归属缺失时，按"不可见"处理，而非放行。
  4. 功能权限（@RequiresPerm，能不能点这个按钮）与数据范围（deptScope，能看到谁的数据）是两道独立闸门，任一不通过即拒绝；功能权限通过不代表数据可见。

8.2 归属锚点与过滤口径

  1. 车辆类数据唯一锚点：轨迹、位置、里程、行驶/停车/怠速、油耗、报警、风险、统计、服务费等一切车辆类数据，以 traj_vehicle.dept_id 为唯一归属锚点；明细数据经车牌（或车辆绑定关系）以 JOIN / EXISTS 关联车辆表后按锚点过滤。
  2. 司机数据经绑定映射：司机表不设 dept_id，统一经车-司机绑定关系（traj_vehicle_driver）映射车辆归属，不新增司机归属字段。
  3. 组织聚合先裁剪后聚合：企业/组织维度的统计必须先按范围裁剪组织行、再在裁剪后的集合上聚合；禁止"全量聚合后过滤"，防止总指标越权。
  4. 越权表现统一为"不存在"：越权访问详情一律表现为 404 或空结果，不提示"无权查看"，不泄露资源是否存在。
  5. 禁止按车牌省份过滤：可见性一律以车辆归属组织为准，账号不与车牌的省份属性绑定。一个部门名下可以挂任意外省车牌的车辆——只要该车辆 dept_id 在用户数据范围内，其全部数据（轨迹、报警、风险、统计、推送等）即可见；反之，同省车牌但归属其他组织的车辆不可见。province_code、车牌首字仅作档案/展示信息，不得作为权限条件。

    实现注意：种子数据中 province_code/city_code 列实际写入的是中文省/市名（如"山东省""济南市"）而非行政区划码，更不能将其用于权限判断。

  6. 过户口径：车辆过户（dept_id 变更）后，其历史数据随新归属可见，即"现状归属"口径。如需"历史按发生时归属隔离"，须另行设计时点归属表，并在设计文档显式说明后再实施。

8.3 实时推送与异步任务

  1. 实时通道按会话过滤：WebSocket/SSE 必须按会话所属用户的范围过滤后推送。握手时确定用户身份并写入会话属性；新连接首帧位置快照同样受限。禁止对所有会话无差别广播业务数据。
  2. 游标只决定增量，不决定可见性：风险事件与终端报警以 id 游标增量扫描（不用时间窗口，避免漏推/重推），游标是全局的，但每条消息仍逐会话按范围过滤后才发送。
  3. 异步任务固化范围快照：异步导出/异步计算在任务创建时固化执行人及其数据范围；任务与结果文件按人隔离；事后范围变更不回溯历史任务。现状定时任务（工单超时扫描、T+1 评分）为系统级维护任务，不面向个人数据交付；未来新增面向人的异步任务时适用本条。
  4. 服务令牌不扩大读权限：ingest 等服务令牌调用只允许写入其被授权的数据，不借服务令牌绕过读取范围；处理服务直接读库属容器网络内的系统进程行为，不等同于终端拥有读权限。

8.4 一致性与准入

  1. 同一数据在"屏幕显示、HTTP 接口、导出文件、实时推送"中的范围必须一致。
  2. 新功能准入清单：
    • 设计：列出功能涉及的数据实体、归属锚点、过滤口径与越权表现；
    • 开发：接入本规则，不新增绕过路径（不新写无范围条件的业务查询）；
    • 评审/测试：以受限角色（四省测试账号）实际验证"本范围可见、范围外不可见"，并验证空集合账号看到空数据而非全量。
  3. 字段级脱敏、跨部门写校验等更细粒度要求随功能迭代另行补充，但其设计不得放宽本规则。

8.5 规则在当前代码中的实现映射

规则要点现状实现位置
登录主体与范围装载JwtAuthFilter 解析 JWT → DbAuthRealm.loadByUserId → UserInfo(perms, deptScope) 写入 UserContext（ThreadLocal）
