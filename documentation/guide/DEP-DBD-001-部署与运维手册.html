DEP-DBD-001 部署与运维手册

文档编号 DEP-DBD-001|版本 v1.3.0|发布日期 2026-10-06|事实基准 2026-10-06 源代码

关联文档：ARC-DBD-001 系统架构设计　DDL-DBD-001 数据库设计　SYS-DBD-001 项目总体设计

运行环境约定：本文命令以 Windows + Docker Desktop（PowerShell 7）为基准；docker compose 为 v2 子命令语法。如使用 Linux/macOS，将 PowerShell 写法替换为等价 shell 命令即可，容器内操作完全相同。

3 配置项说明

3.1 .env 变量（以 .env.example 为模板）

变量示例 / 缺省说明
POSTGRES_DBmydbd数据库名；同时注入 postgres 初始化、Java JDBC 与 Python DSN
DB_USERmydbd数据库用户名（POSTGRES_USER）
DB_PASSWORDchange_me_in_prod数据库密码；生产环境必须修改。也是 DBeaver 等工具直连 5432 的密码
JWT_HMAC_SECRETchange_me_to_32_bytes_min_length_secret_value_hereJWT HMAC 签名密钥（Java 与 processing 共用）；生产用 openssl rand -hex 32 生成。签发算法固定 HS256（密钥长度不影响算法选择；processing 验签兼容 HS384/HS512 存量令牌）。修改后所有已签发令牌立即失效，用户需重新登录
SERVICE_TOKENchange_me_service_token_for_internal_api_calls内部服务令牌：调 /api/ingest/traj、/api/analysis/video 时以 X-Service-Token 头携带；Java 与 Python 两侧必须一致
JAVA_OPTS-Xmx640m -XX:+UseG1GC.env.example 提供该变量，但 docker-compose.yml 中 platform-app 的 JAVA_OPTS 当前为同值硬编码（未引用该变量）；调整 JVM 参数需改 compose 文件或使用 override 文件
AMAP_KEY空高德开放平台 Web 服务 Key（控制台申请）。用于服务端代理的逆地理编码与地点检索（/api/terminal/geocode/reverse、/search），Key 不下发前端；留空时这两个接口返回业务码 50301，不影响地图瓦片与其余功能
GATEWAY_MODEsimulatorvps 网关对接运行模式（GATEWAY-PLAN-001）：simulator=既有进程内模拟器，不启动 Kafka 消费（默认）；mock=内置 mock_producer 向 Kafka 投递 500 车仿真报文并走真实消费链路（开发/演示，需同时配 KAFKA_BOOTSTRAP_SERVERS 并以 --profile dev-infra 启动 kafka）；gateway=对接真实 vps 网关。切换后需重启 processing-app 生效
KAFKA_BOOTSTRAP_SERVERS空（mock 填 kafka:9092）Kafka broker 列表，逗号分隔；mock 模式指本地 dev-infra kafka 服务，gateway 模式填网关集群地址。为空时即使 GATEWAY_MODE=mock/gateway 也不启动消费（gateway_enabled 双重判定）
KAFKA_GROUP_IDmydbd-ingest网关消息消费组 ID；对接共享集群时须使用独立消费组与只读 ACL
GATEWAY_FILE_BASE_URL空网关附件服务地址（18009），用于转存图片/音视频；留空则不转存（mock 模式生成占位文件）
GATEWAY_MEDIA_STRATEGYlocal附件策略：local=流式下载转存到 mydbd-data 卷（/data/media，单文件上限 50MB，鉴权取件）；proxy=仅记录原始 URL 不转存

4 首次部署步骤

在项目根目录 mydbd/ 下按顺序执行（PowerShell）：

第 1 步：准备环境配置。

Copy-Item .env.example .env
# 编辑 .env：至少修改 DB_PASSWORD、JWT_HMAC_SECRET、SERVICE_TOKEN；需要逆地理时填 AMAP_KEY
notepad .env

第 2 步：构建前端静态资源。（nginx 只挂载 dist，不构建）

cd frontend
npm install
npm run build
cd ..
# 成功标志：生成 frontend/dist 目录（含 index.html 与 assets/）

第 3 步：构建镜像并启动全部容器。

docker compose up -d --build
# 首次会拉取 postgis:16-3.4、nginx:1.27-alpine 并本地构建两个应用镜像

# 如需 GATEWAY_MODE=mock 网关仿真链路，追加 dev-infra profile 同时拉起 Kafka：
docker compose --profile dev-infra up -d --build
# （.env 中 GATEWAY_MODE=mock、KAFKA_BOOTSTRAP_SERVERS=kafka:9092）

Kafka 是 compose 条件服务（profiles: ["dev-infra"]）：不带 profile 的常规 docker compose up 不启动它，既有 simulator 模式部署不受影响。注意启动顺序：kafka 晚于 processing-app 启动时，mock_producer 初始引导失败不自动重连，需 docker compose restart processing-app（消费侧本身带 5s 退避重连）。

第 4 步：健康检查。

docker compose ps
# 常规四个容器 STATUS 最终均应为 healthy：
# postgres(约10~30s) → processing-app/platform-app(约20~60s) → portal-nginx
# mock 模式另有 kafka 容器（dev-infra profile，无 healthcheck，State=running 即可）

# 应用直连健康端点（宿主）
curl.exe http://127.0.0.1:8000/health
curl.exe http://127.0.0.1:8080/actuator/health
curl.exe http://127.0.0.1:8090/

第 5 步：访问与登录。

  1. 浏览器打开 http://localhost:8090；
  2. 用 admin / admin123 登录（登录页可点击测试账号快捷填充）；
  3. 进入"实时导航监控"页，点击「加载样例数据」，处理服务把 samples/ 中的轨迹 CSV 与当日司机事件导入 PostGIS，地图随即出现车辆与风险事件。

需要更大体量数据时，可调用处理服务的标准数据集接口（standard / dense 两档，后台异步生成，可用 status 查询进度）：见 API-DBD-001 中 /api/ingest/dataset/*。

5 数据库初始化

infra/postgres/init/ 以只读方式挂到 postgres 容器的 /docker-entrypoint-initdb.d。官方镜像行为：仅当数据卷为空（首次初始化）时按文件名字典序执行一次；之后重启、升级镜像都不会再次执行。需要重跑必须清空 pg-data 卷（见 §10/FAQ）。

脚本内容（按文件命名与头部注释）
01-create-schemas.sql创建 traj / mon schema 与 PostGIS 扩展等基础对象
02-traj-tables.sql轨迹域：gps_point、vehicle、terminal、driver、绑定关系、warn_info、photo、报警类型等
03-mon-tables.sql监控域：risk_event、video_analysis

6 日常运维

6.1 启停与状态

docker compose ps                 # 查看容器状态与健康状况
docker compose stop               # 停止（保留容器与卷）
docker compose start              # 再次启动
docker compose restart platform-app   # 只重启 Java 服务（IP 不变，无需动 nginx）
docker compose down               # 停止并删除容器/网络（卷保留，数据不丢）
docker compose up -d              # down 后重新拉起

6.2 查看日志

docker compose logs -f platform-app      # Java 日志（含 WS 推送游标、工单扫描记录）
docker compose logs -f processing-app    # Python 日志（CEP 异常只打印不阻断）
docker compose logs -f portal-nginx      # nginx access/error，502 排查首选
docker compose logs --tail=200 postgres  # 数据库最近日志

6.3 健康检查端点

端点返回说明

6.4 vps 网关模式运维（GATEWAY-PLAN-001）

网关消费链路在 processing-app 内，模式由 .env 的 GATEWAY_MODE 控制，切换后重启 processing-app 生效：

# 模式切换示例：simulator（默认）→ mock 仿真
# 1) .env 设置：GATEWAY_MODE=mock、KAFKA_BOOTSTRAP_SERVERS=kafka:9092
# 2) 拉起 kafka（条件服务）并重启处理服务
docker compose --profile dev-infra up -d kafka
docker compose restart processing-app
# 3) 验证消费状态（容器内/宿主带服务令牌直连 processing）
curl.exe -H "X-Service-Token: %SERVICE_TOKEN%" http://127.0.0.1:8000/api/gateway/status
事项说明
三种模式simulator=进程内模拟器（/api/simulator/* 控制），不启动 Kafka；mock=mock_producer 500 车仿真报文（5s GPS/30s 心跳/29 类报警限频 ≤2 起/分、每起带 2 附件/上下线循环；测试模式下可在运行模式页运行时启停）灌入 Kafka，消费/CEP/工单/附件全链路真实运行；gateway=对接真实 vps 网关（上线前需落实 broker、只读 ACL、独立消费组并小批量真车灰度）
运行状态查看平台页面「系统管理 → 运行模式」（菜单 925，/system/gateway，权限码 system:gateway:view，2026-10-06 由「网关接入状态」更名）：模式、运行态、分 topic 收发计数、DLQ 数、未登记终端数与隔离区清单；测试模式下可启停 mock 仿真投递（开关持久化、重启后保持）并一键「清除模拟数据」（清运行数据保留基础数据）；接口见 API-DBD-001 §2.27/§3.2/§3.4/§3.6
未登记终端双标识（手机号 / gateway truckId）均解析不到的终端进入 traj.gateway_unknown_terminal 隔离区，报文仍落轨迹/报警不丢弃；补档后自动恢复关联，隔离区可在状态页核查
死信解析/入库失败消息写 traj.gateway_dlq，状态页可见计数；正常运行应为 0
附件存储local 策略转存 mydbd-data 卷 /data/media/日期/warnId/，单文件上限 50MB；前端经 /api/monitor/alarm/media/{id} 鉴权中转查看；备份 mydbd-data 卷即同时备份附件（见 §10）
Kafka 日志docker compose logs -f kafka；消费侧引导失败有 5s 退避自动重连；mock_producer 引导期失败不重连，需重启 processing-app（已知遗留，二期加固）

7 后端发版标准流程

热替换流程（不重建容器、IP 不变、nginx 无需操作）：

第 1 步：全量离线构建。在 backend-java/ 目录执行：

mvn -o -B -ntp clean install -DskipTests

第 2 步：核对 fat jar 时间戳。

# 检查 platform-boot/target/platform-app.jar 已刷新
Get-Item backend-java\platform-boot\target\platform-app.jar | Select-Object FullName, Length, LastWriteTime

必须做全量 clean install。只在某个业务模块目录执行 mvn package 可能只刷新该模块 jar，不会重新 repackage platform-app.jar，导致"代码改了、容器里没生效"。fat jar 内嵌的各业务模块 jar 时间戳应与本次构建一致。

第 3 步：拷入运行中容器。

docker cp backend-java/platform-boot/target/platform-app.jar mydbd-platform-app-1:/app/platform-app.jar

第 4 步：重启并轮询就绪。

docker restart mydbd-platform-app-1

# PowerShell 轮询登录接口：返回 HTTP 200 即视为就绪（一般 20~60 秒）
$body = '{"username":"admin","password":"admin123"}'
while ($true) {
  try {
    $r = Invoke-WebRequest -Uri http://127.0.0.1:8080/api/auth/login -Method Post `
      -ContentType 'application/json' -Body $body -UseBasicParsing -TimeoutSec 3
    if ($r.StatusCode -eq 200) { Write-Host "platform-app ready"; break }
  } catch { Start-Sleep -Seconds 2 }
}

该方式只 restart 同一容器，容器 IP 不变，portal-nginx 无需任何操作；验证门户：http://localhost:8090。

8 前端发版与缓存

发版：

cd frontend
npm run build
cd ..
# dist 是直接挂载进 nginx 容器的宿主目录，覆盖即生效，无需重启容器
# 浏览器侧刷新页面即可；若浏览器缓存顽固，Ctrl+F5 强刷

缓存策略（portal.conf 已固化）：

  • location = /index.html 显式加 Cache-Control: no-cache, no-store, must-revalidate，保证发版后浏览器立刻拿到引用最新 hash chunk 的 index.html；
  • assets/ 文件名带内容 hash，可长期缓存；发版后旧 chunk 自然淘汰；
  • nginx 对未知路径 try_files ... /index.html 回退 SPA。

现场内嵌 Electron/工控浏览器可能缓存更顽固：旧 chunk 白屏/404 时用 Ctrl+Shift+R 强制刷新，或在该壳的清缓存菜单中清理站点数据后重开。

9 容器重建注意（重要）

现象：执行 docker compose up -d --build 或 docker compose up -d --force-recreate 重建后端容器后，http://localhost:8090 返回 502，但直连 http://127.0.0.1:8080 一切正常。

原因：容器重建会获得新的内部 IP；nginx 在启动时把 upstream 主机名（platform-app / processing-app）解析为固定 IP 并缓存，旧 nginx 进程仍在连旧 IP。docker logs mydbd-portal-nginx-1 可见 connect() failed (111: Connection refused) 类报错。

处理：重建后端/处理容器后，必须重启门户容器刷新 upstream 解析：

docker compose restart portal-nginx
# 或：docker restart mydbd-portal-nginx-1

对比：§7 的"docker cp + restart 同一容器"不换 IP，因此不需要重启 nginx——两种发版路径的区别就在于容器是否被重建。

10 备份与恢复

10.1 pg-data 卷（核心数据）

全部业务数据、IAM、审计都在 pg-data 卷（物理路径用 docker volume inspect mydbd_pg-data 查看，卷名以 compose 项目目录名为前缀，可用 docker volume ls 核对）。推荐用 pg_dump 做逻辑备份：

# 备份（自定义压缩格式，PowerShell 重定向）
docker compose exec -T postgres pg_dump -U mydbd -d mydbd -Fc -v > backup-20261005.dump

# 恢复（--clean 先清后建；建议在停服窗口执行）
docker compose exec -T postgres pg_restore -U mydbd -d mydbd --clean --if-exists -v < backup-20261005.dump

纯 SQL 格式备份可用 pg_dump -U mydbd -d mydbd -Fp > backup.sql，恢复用 psql -v ON_ERROR_STOP=1 -f backup.sql。备份文件中不含卷内但库外的内容；恢复后如改过密码，注意 .env 与备份内角色口令的一致性问题（逻辑备份不含角色定义时不影响）。

10.2 mydbd-data 卷与 samples

  • mydbd-data 挂在处理容器 /data，存放处理服务运行期工作数据（当前主要是数据集生成过程产物）；按需直接用 docker cp 拷贝目录备份；
  • samples/ 是仓库内宿主目录（只读挂载），随代码仓库版本管理，无需随卷备份；
  • 清空业务数据重来可调用 /api/ingest/dataset/clear（保留 IAM/菜单/字典/配置/审计）；要连库结构完全重建，先 docker compose down 再 docker volume rm mydbd_pg-data，然后 docker compose up -d 让 17 个初始化脚本重新执行（危险操作，先备份）。

11 常见问题 FAQ

Q1 浏览器报 502/AxiosError，怎么判断是后端挂了还是前端路径错了？

现象前端反馈"接口 502"，但后端进程看着在运行。

原因必须以 docker compose logs portal-nginx 的 access log 为准，不能只看浏览器报错文案。nginx combined 日志中状态码后面紧跟的第二列是响应体字节数（body_bytes_sent）：

  • 200 40401：HTTP 状态其实是 200、返回了约 40 KB 的 JSON 业务数据——这不是 502。曾出现该 4 万字节 JSON 响应被前端误报为 "AxiosError 502" 的案例，应排查前端处理逻辑而非网络；
  • 200 加约 500 字节 text/html：返回体是 index.html（SPA 回退页），说明请求漏了 /api 前缀，被 try_files 回退到前端页面；应检查请求 URL 与 baseURL；
  • 502 157 一类且 error.log 有 connect() failed：才是 nginx 到上游真不通，按 Q2 排查。

处理先读日志两列数字定性，再决定查前端路径还是查容器/网络。

Q2 门户 :8090 间歇性/重建后 502，:8080 直连正常？

现象重建后端容器后 :8090 返回 502，:8080 直连与登录正常。

原因nginx 启动时把 upstream 解析成固定容器 IP；后端容器重建换了 IP，旧 nginx 仍连旧地址。

处理docker compose restart portal-nginx。热替换发版（docker cp + restart 同容器，见 §7）不换 IP，可避免此问题。

Q3 列表正常、点开详情 404，或详情 id 与列表对不上？

现象列表数据正常，点详情报"不存在/404"；新数据尤其明显。

原因主键是 19 位长整型雪花 ID，超过 JS Number.MAX_SAFE_INTEGER（2^53-1，16 位）。后端若漏加 @JsonSerialize(using = ToStringSerializer.class)，Long 以 JSON number 返回，前端 JSON.parse 丢精度，拿错误 id 去查详情必然 404。

处理所有面向前端的 VO/DO 中的 Long id 一律加 ToStringSerializer 序列化为字符串（集合 id 用 contentUsing）；前端按字符串持有 id，不做数值运算。代码中 AuditLogVO、UserListVO、UserDetailVO 等均已按此处理，新增 VO 照做。

Q4 接口偶发 InvalidDefinitionException: Java 8 date/time type LocalDateTime not supported by default？

现象新增接口序列化含 LocalDateTime 的对象时抛 InvalidDefinitionException。

原因代码里 new ObjectMapper() 新建的裸 Mapper 不带 jsr310 模块，不认 JDK8 时间类型；Spring 容器中经 Boot 自动配置的 ObjectMapper 才注册了时间模块并套用全局格式/时区。

处理凡是要序列化业务对象（尤其含 LocalDateTime）的 ObjectMapper，必须注入 Spring 容器实例（如 AuditRegistrar 通过构造参数注入给 AuditFilter）。仅序列化简单固定结构（无时间类型，如 JwtAuthFilter 输出错误 Result）才可自行 new。

Q5 定时任务突然全部不执行（推送/工单扫描/每日评分）？

现象WS 不推送、工单超时不升级、T+1 评分不产出。

原因@EnableScheduling 只允许标注在启动类 PlatformApplication 一处；重构包名/移动启动类或误删该注解后，全部 @Scheduled 方法静默停摆（不报任何错）。

处理确认 PlatformApplication 上三个注解完整：@SpringBootApplication(scanBasePackages="com.mydbd")、@MapperScan("com.mydbd.**.mapper")、@EnableScheduling。各调度类只写 @Scheduled，不重复加 @EnableScheduling。

Q6 为什么实时推送只推新事件、且重启后不会把历史事件重推一遍？

现象重启服务后客户端收不到库里已有的历史风险/报警；偶发疑问"为什么不用时间窗口增量"。

原因这是刻意设计：RealtimePushScheduler 在 @PostConstruct 把风险/报警游标初始化为当前最大 id，之后每 tick 用 id > 游标 增量扫描（每批 50 条）。用 id 游标而非时间窗口，可避免同秒/乱序数据漏推、重复推，也避免时钟回拨问题。

处理历史数据走 HTTP 分页查询接口，不要指望 WS 回放；新连接首帧只补发一帧当前位置快照。

Q7 按城市/省份码筛选车辆数据查不到，或分组统计串了？

现象以为 city_code 存行政区划码（如 370100），按码查询为空。

原因traj_vehicle.city_code（以及 traj_dept 的 province_code/city_code 等列）在标准测试数据生成器中实际写入的是中文名称（"山东省""济南市"这类值），列名虽叫 code，内容不是数字码。

处理按中文名称匹配，或改用 dept_id 组织口径统计；再次强调这些列只能用于展示/分组，绝不能作为数据权限条件（见 SYS §8.2）。

Q8 报警中心/大屏 KPI 显示"今日报警 0"，但库里明明有报警数据？

现象报警列表为空或今日统计为 0，数据库里能查到 traj_warn_info 记录。

原因默认查询窗口是服务器墙钟"今日"：后端 /api/alarm/stats 缺省 today 00:00~当前；报警中心前端打开即默认今日时间范围。样例 CSV 与标准数据集的时基是历史日期（如 2026-09-01/02），模拟器不跑时没有"今日"新报警，自然查 0。

处理在页面时间选择器改选数据实际发生日期（大屏钻取会自动带 beginTime/endTime 跳转）；接口调用显式传 beginTime/endTime（ISO LocalDateTime，如 2026-09-01T00:00:00）；要看实时数据则启动模拟器或推送实时点。

Q9 用 DBeaver/Navicat 直连数据库的参数是什么？

现象想在宿主上直接查表。

处理PostgreSQL 连接参数：主机 127.0.0.1、端口 5432、数据库 mydbd、用户名 mydbd、密码 change_me_in_prod（若 .env 改过则用新密码）。端口仅绑回环地址，远程主机连不上是正常的，需走 SSH 隧道或临时调整映射。

Q10 PowerShell 调接口做中文断言，响应里中文变成乱码？

现象Invoke-RestMethod 拿到的中文字段乱码，断言中文消息失败。

原因Windows PowerShell 默认按响应头/系统编码解码，对无 charset 头的 UTF-8 JSON 可能误判。

处理用 Invoke-WebRequest -UseBasicParsing 取原始字节，再显式 UTF-8 解码后断言：

$r = Invoke-WebRequest -Uri http://127.0.0.1:8080/api/alarm/types -UseBasicParsing
[System.Text.Encoding]::UTF8.GetString($r.RawContentStream.ToArray())

发 JSON 请求体含中文时同样先把 body 按 UTF-8 字节发送，避免服务端按 ISO 误读。

Q11 修改了 init 目录里的 SQL，重启容器后为什么不生效？

现象改了 infra/postgres/init 下脚本并重启，库里没有变化。

原因/docker-entrypoint-initdb.d 只在数据卷首次初始化（空卷）时执行一次。

处理已有环境走增量迁移 SQL（手工 psql 执行，写成幂等）；只有开发库允许 down + 删 pg-data 卷 + up 全量重建（§10.2，先备份）。

Q12 逆地理/地点检索接口报 50301"高德地图 Key 未配置"？

现象车辆详情取地址、监控页地点搜索返回业务码 50301。

原因AMAP_KEY 为空时 GeocodeController 直接拒绝（这是预期行为，不是故障）；Key 由服务端代理使用，不下发前端。

处理在高德开放平台申请 Web 服务 Key 填入 .env 的 AMAP_KEY，docker compose up -d 重建/重启 platform-app 生效（仅 restart 同容器也可读到新环境变量需重建容器，建议改后 docker compose up -d platform-app，随后按 Q2 重启 nginx）。无外网/无 Key 环境下地图瓦片与核心业务不受影响。

Q13 改完 Java 代码重新发版，行为完全没变？

现象mvn package、docker cp、restart 全套做了，旧逻辑依旧。

原因常见两个：① 只在子模块执行 package，fat jar 没重新 repackage（内嵌业务模块 jar 仍是旧时间戳）；② docker cp 的源路径不是 platform-boot/target/platform-app.jar。

处理严格按 §7 在 backend-java 根做 mvn -o -B -ntp clean install -DskipTests，先核对 fat jar 与内嵌模块 jar 时间戳再 cp；重启后看启动日志确认启动时间已刷新。

Q14 改了 JWT 密钥或服务令牌后出现大面积 401 / ingest 401？

现象用户登录态集体失效；终端/第三方推轨迹返回 401"服务令牌无效"。

原因JWT_HMAC_SECRET 变更后旧令牌签名验不过（预期，重新登录即可）；SERVICE_TOKEN 必须 Java 与 Python 两侧（及所有调用方）同步，不一致则处理服务鉴权拒绝。

处理密钥轮换选低峰期并通知用户重登；SERVICE_TOKEN 改后 docker compose up -d 让两个应用同时拿到新值。

Q15 打开「运行模式」菜单立刻被踢回登录页（其他菜单正常）？

现象admin 登录后，一点「运行模式」（/system/gateway）就提示"登录已失效，请重新登录"并跳转 /login；其他菜单正常。

原因该页是唯一在打开时让浏览器直接带 JWT 请求 processing-service 的页面（/api/simulator/status、/api/simulator/mock/status、/api/ingest/dataset/status）。2026-10-06 前 Java 侧 signWith(key) 未指定算法，JJWT 按密钥长度自选——JWT_HMAC_SECRET 为 50 字节（≥48 字节）时签发的是 HS384，而 processing 的 PyJWT 验签白名单只有 HS256，判 InvalidAlgorithmError 回 401；前端拦截器收到 401 即清令牌硬跳 /login。

处理已于 2026-10-06 修复（v1.3.0）：Java JwtUtil 显式 signWith(key, Jwts.SIG.HS256) 固定 HS256；processing app/security.py 验签白名单放宽为 HS256/HS384/HS512 兼容存量令牌（修复后无需重登）。应急排查命令：先解 JWT 头部看 alg（token.split('.')[0] base64 解码），再 docker exec mydbd-processing-app-1 python -c "import jwt; ..." 复现验签异常；改后按 §7 发版（Python 改文件可先 docker cp + restart 止血，再 docker compose build 固化镜像）。方案存档：plans/20261006-01-jwt-alg-401-fix.md。
