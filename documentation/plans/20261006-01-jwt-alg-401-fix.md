## 1. 目标与范围

admin 登录后点击「运行模式」菜单（菜单 925，路由 /system/gateway），页面立即提示"登录已失效，请重新登录"并硬跳 /login，其他菜单均正常。需定位根因并修复，保证浏览器→processing-service 的 JWT 鉴权链路与 Java 平台签发侧长期一致。

范围内：JWT 签名/验签算法两侧对齐；代码注释与正式文档库同步。
范围外：前端 401 拦截策略改造（辅助轮询接口 401 是否一律踢登录）本次不动，作为后续可选韧性优化。

## 2. 现状分析（根因证据链）

1. Java 签发：`JwtUtil.build()` 使用 `.signWith(key)` 未显式指定算法，`key = Keys.hmacShaKeyFor(JWT_HMAC_SECRET.getBytes(UTF_8))`。JJWT 0.12.6 在只传 Key 时按密钥长度自选算法：≥64 字节→HS512、≥48 字节→HS384、≥32 字节→HS256。
2. 运行环境实测：两容器 `JWT_HMAC_SECRET` 明文一致（均 50 字符、等值，排除密钥不一致）；50 字节 = 400 bit ≥ 384 bit，实际签发 token 头部经 base64 解码为 `{"alg":"HS384"}`。
3. processing 验签：`processing-service/app/security.py` 的 `_bearer_uid` 调 PyJWT 2.15.1 `jwt.decode(token, secret, algorithms=["HS256"])`，白名单仅 HS256 → 抛 `InvalidAlgorithmError: The specified alg value is not allowed`，被统一 `except` 兜底成 HTTP 401（detail：登录已过期，请重新登录）。
4. 前端 `frontend/src/api/http.ts` 响应拦截器对任何 401 执行 `localStorage.removeItem('mydbd-token')` + `window.location.href='/login'`。
5. 只有「运行模式」页（`views/system/GatewayStatus.vue`）在 onMounted 阶段让浏览器直接带 JWT 请求 processing：`GET /api/simulator/status`、`GET /api/simulator/mock/status`、`GET /api/ingest/dataset/status`（经 nginx /api/simulator/、/api/ingest/ 反代）。其他页面只调 Java（同钥验 HS384 正常）；Java→processing 走 X-Service-Token，不经 JWT。该浏览器侧 JWT 校验是 2026-10-06 测试模式治理（require_access）新引入链路，首次被真实走通即暴露。

实测复现（admin 登录后带 token 逐个请求）：

| 接口 | 走向 | 修复前 |
|---|---|---|
| /api/simulator/status | 浏览器→nginx→processing（PyJWT） | 401 |
| /api/simulator/mock/status | 同上 | 401 |
| /api/ingest/dataset/status | 同上 | 401 |
| /api/monitor/gateway/* | 浏览器→Java（X-Service-Token 中转） | 200 |
| /api/system/config | Java | 200 |

## 3. 实施方案（已确认：A+B 一起做）

- **A｜processing 止血与兼容**：`app/security.py` 的 jwt.decode 白名单由 `["HS256"]` 改为 `["HS256","HS384","HS512"]`；模块 docstring 补算法口径说明。同一把 HMAC 密钥下接受同族算法不降低安全性（不接受 `none`），且让切换前签发的 HS384 存量令牌继续有效，用户无需重新登录。
- **B｜Java 根治契约漂移**：`JwtUtil.build()` 改为 `.signWith(key, Jwts.SIG.HS256)` 显式钉死 HS256，新签发令牌算法不再随密钥长度变化；解析侧 `verifyWith(key)` 保持原样（JJWT 对 400-bit 密钥天然接受 HS256/HS384/HS512），保证存量令牌平滑过渡。类注释写明踩坑原因。

部署：
- processing：`docker cp security.py` 进容器 → restart 止血；`docker compose build processing-app` 重建镜像固化（运行容器不重建，IP 不变，nginx 无需重启）。
- platform：`mvn -o -B -ntp clean install -DskipTests` 全量打包 → 核对 fat jar 与内嵌 platform-common jar 时间戳 → docker cp platform-app.jar → restart → 轮询登录接口 200（restart 不换 IP，nginx 无需重启）。

## 4. 影响面

- 新登录令牌 alg 由 HS384 变为 HS256；8 小时内存量 HS384 令牌在 Java 与 processing 两侧仍被接受，过期后自然全量切换为 HS256。
- 不涉及数据库、接口出入参、前端逻辑与 nginx 配置变更。
- 文档：MOD-DBD-001、API-DBD-001、ARC-DBD-001、DEP-DBD-001、MOD-DBD-014、GATEWAY-PLAN-001、index.html 同步；本文件为方案归档。

## 5. 风险与回滚

- 风险低：改动仅 2 行生产代码 + 注释；HS 同族验签为标准用法。
- 回滚：两处改动均可独立还原（Python 还原白名单并重启 processing；Java 还原 signWith 重新发版）。注意若只回滚 B 不回滚 A，系统仍正常（processing 继续接受 HS384）；若只回滚 A 不回滚 B，HS256 新令牌在 processing 验签同样通过。两侧解耦，无强绑定窗口。

## 6. 验证方式与结论（已执行）

1. processing 重启后、Java 发版前，用当时仍为 HS384 的登录令牌请求三个 processing 接口：全部 200（证明 A 生效且存量令牌兼容）。
2. Java 发版后重新登录，解码新令牌头部：`{"alg":"HS256"}`。
3. 新令牌全链路：/api/simulator/status、/api/simulator/mock/status、/api/ingest/dataset/status、/api/monitor/gateway/status、/api/monitor/gateway/unknown-terminals、/api/system/config?keyword=gateway、/api/auth/profile 均 200。
4. 用共享密钥手工签发一枚 HS384 令牌：Java /api/auth/profile 与 processing /api/simulator/status 均 200（平滑过渡实证）。
5. 浏览器实测（admin/admin123）：登录 → 打开「运行模式」→ 停留 /system/gateway，三张卡片正常渲染；等待 12 秒跨过 10 秒自动刷新周期，无重定向；控制台无错误、网络无 401/500、无"登录已失效"提示。

结论：缺陷已修复，存量登录态零感知，新签发令牌算法契约固定为 HS256。
